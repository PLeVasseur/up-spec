== Overview

[NOTE]
====
Scalable service-Oriented MiddlewarE over IP *(SOME/IP)* is a communication protocol used in the automotive industry for exchanging data between electronic control units (ECUs) in a vehicle.

SOME/IP provides a framework for communication between ECUs over IP networks. The protocol allows ECUs to discover and communicate with each other, exchange messages, and provide services in a distributed system.

SOME/IP is based on the Internet Protocol (IP) and uses UDP or TCP as the transport layer. It supports various communication patterns, including unicast, multicast, and broadcast. The protocol defines a set of message formats and procedures for encoding and decoding data, handling service discovery, and managing communication sessions.
By using SOME/IP, automotive ECUs can communicate with each other to exchange information related to vehicle functions, such as sensor data, control commands, diagnostics, and software updates. It enables the integration and interoperability of different ECUs from various automotive suppliers within a vehicle's network architecture.
====

The following specification will elaborate on how uProtocol shall be mapped to SOME/IP protocol so that mechatronics applications and services can be connected to non-mechatronics and cloud based applications and services.

== Transport Layer Translation

xref:README.adoc[Transport & Session Layer (uP-L1)] specifies how xref:../basics/umessage.adoc[uMessages] are sent and received between *uEntities* or between devices. In this section we will cover the SOME/IP service translation and event mapping.

Mapping of uTransport APIs to SOME/IP specific library *APIs* shall not be covered in this document given there are multiple open source libraries available for SOME/IP.

Although some limitations of *vsomeip* library are mentioned below as *NOTES*.

[[someip-service-translation]]
=== The SOME/IP service translation

[.specitem,oft-sid="req~up-transport-someip-service-translation~1",oft-needs="dsn,uman",oft-tags="SomeIpTranslator"]
--
*Standing.*
The SOME/IP binding of this chapter is a _service translator_, called the _translator_ in this chapter.
It ends each uProtocol message that it accepts and produces a stock SOME/IP message from it, and it produces a new uProtocol message from each SOME/IP message that it admits: it is the consumer of each uProtocol message that it accepts, and the producer of each uProtocol message that it reconstructs.
For a component that forwards a uProtocol message to it, the translator is that message's uProtocol endpoint.
A stock SOME/IP message has no field for a message's UUID, priority, TTL, token, permission level or trace context, or for the client's major version, so no exact carriage and no exact round trip is claimed across the translator.
What the translator promises instead is the directional table of <<common-umessage-attributes>>: for every field and payload state, in each direction, the value is carried, supplied from named context, lost with a stated loss, or refused.

* The translator's supplier *MUST* state, in the translator's released documentation, that the translator is a service translator under this chapter, and *MUST* name the tables of this chapter in it.
The translator *MUST* meet every row and every refusal of the items of this chapter, `+dsn~up-transport-someip-uri-mapping~1+` (<<uri-mapping>>) and `+dsn~up-transport-someip-subscription-mapping~1+` (<<eventgroup-entry-mapping>>) among them.
* The translator's supplier *MUST NOT* claim `+req~utransport-send-preserve-data~1+` (xref:README.adoc[Transport & Session Layer (uP-L1)]) for the conversion.
That requirement is neither amended nor waived: it binds each UTransport implementation unchanged, the transports that bring a message to the translator and take a reconstructed message away from it included, and it has no subject across the conversion, which is not a transmission.
* A component that drops or defaults an attribute that the tables of this chapter do not state as lost does not conform by being called a translator: it meets neither `+req~utransport-send-preserve-data~1+` (xref:README.adoc[Transport & Session Layer (uP-L1)]) nor this chapter.
* The translator may be reached through whatever call shape its language library gives a transport, such as xref:README.adoc#send[`send`] and xref:README.adoc#register-listener[`registerListener`], and no second application API is required.
Which duties of the UTransport call items it owes is stated item by item in <<someip-call-allocation>>: no duty is inferred from a method's name, a method named `send` establishes no UTransport conformance, and it removes no duty of validation, access control or delivery either.

*Who supplies what.*
Each rule of this chapter names the party that supplies what the rule needs:

* the _translator_, which is its own code and its SOME/IP stack together: where the stack meets a duty, the duty is still the translator's, and the translator's released documentation says which part meets it;
* the _author of a service contract_, for what the contract declares: the kind of each event, the identifier table, the payload slots, the failure representation of each method, the recipient bindings and the client identity agreement;
* the _deployment_, for its endpoints, its discovery configuration, its declarations of every route onto the translator's fixed service, and each premise that a rule calls declared.

*Identity and authorization.*
On the uProtocol side, the translator keeps the two access duties of the call items, as rows 3 and 18 of <<someip-call-allocation>> state.
On the SOME/IP side, it authenticates no stock peer.
The source of a reconstructed message is supplied: by the client identity agreement for a request (<<someip-client-identity>>), and by endpoint and discovery configuration for a service.
That is attribution by declared mapping context, and an identifier table or a client identity agreement is a mapping that proves no identity.
Authenticating the stock peers, and limiting which of them reach the translator's endpoints, is the deployment's duty under its SOME/IP configuration.
A `token` or a `permission_level` is refused or lost as <<common-umessage-attributes>> states, and is never treated as checked.

*Routes onto the translator's fixed service.*
Where a component forwards uProtocol messages to the translator on a route onto the fixed service that the translator translates, the route ends at that service, whose contract fixes the slots of its methods and events, and the translator is the uProtocol endpoint of each message on it ("Standing").
As a deployment premise, the deployment declares to the translator every route that forwards uProtocol messages onto the translator's fixed service, so that the setup refusal below covers every such route and is not narrowed to whichever declarations happen to arrive; this premise selects no new API, transport mechanism or payload behaviour.
A forwarding leg's duty to carry every attribute and payload unchanged (`+req~utransport-send-preserve-data~1+`, xref:README.adoc[Transport & Session Layer (uP-L1)], and xref:../up-l2/streamer.adoc#req-ssr-streamer-byte-identity[Carriage keeps the bytes]) holds up to the hand-over to the translator and makes no claim beyond it; across the conversion, <<common-umessage-attributes>> governs each field and payload state.
The translator *MUST* refuse at setup, by name, a route onto its fixed service whose declaration either leaves its payload encoding identifiers unrestricted or names an encoding identifier that no slot of the service admits, or promises unchanged carriage beyond the translator of an attribute that <<common-umessage-attributes>> states as lost, not carried, absent, refused, supplied from context, or projected by the status rules of <<commstatus-error-mapping>> and <<commstatus-inbound>> in the direction in which the route carries it.
An unrestricted opaque route onto the fixed service, which declares no limit on the encoding identifiers that it carries, is refused at setup under this rule.
By contrast, a forwarding route whose declaration limits its payload encodings to identifiers that the service's slots admit, and promises unchanged carriage only up to the translator hand-over (making no promise of unchanged carriage beyond the translator), is not refused by this rule: its forwarding leg keeps its unchanged-carriage duty up to the translator, and across the conversion the translator applies <<common-umessage-attributes>>.
A route that the translator admits does not change how each message on it is judged: a payload whose encoding identifier is not the selected slot's is refused, with no relabelling and no transcoding, as <<common-umessage-attributes>> and row 4 of <<someip-results>> state.

*The call items.*
Through each operation that it exposes, the translator owes the duty of each call item of xref:README.adoc[Transport & Session Layer (uP-L1)] as <<someip-call-allocation>> states it, read with these boundary terms:

* a _translated message_ is the SOME/IP message that the tables of this chapter produce from an accepted uProtocol message;
* an _admitted reconstructed message_ is a uProtocol message that the tables produce from a SOME/IP message that they admit, and a SOME/IP message that a row refuses is never one;
* _SOME/IP delivery_ is the message delivery mechanism of the translator's SOME/IP stack;
* _uProtocol delivery_ is the mechanism through which the translator gives a deliverable message to uProtocol receivers, and <<someip-delivery-acceptance>> says when it has accepted a message;
* a _deliverable message_ is an admitted reconstructed message, or a uProtocol response that the translator generates itself; the one response that it generates is the `DeadlineExceeded` response of row FW11 of <<someip-entry>>.
The deliverable message is the one subject of uProtocol delivery: rows 7, 8, 16, 18, 23 and 24 of <<someip-call-allocation>>, and <<someip-delivery-acceptance>>, apply to both kinds alike.

*The three outcomes of a hand-over.*
The translator makes hand-overs in both directions: a translated message to SOME/IP delivery, and a reconstructed or generated message to uProtocol delivery.
Each hand-over ends in exactly one of the three outcomes of <<someip-hand-over>>, and the translator *MUST* give the correlation state the effect that the outcome's row states.
The published note on xref:README.adoc#send[`send`] already says that an unsuccessful `send` "does not necessarily mean that the given message has not been sent at all"; the three outcomes turn that note into a contract.

.The outcomes of a hand-over
[[someip-hand-over]]
[cols="2,5,3,6",options="header"]
|===
| Outcome | When | What may be claimed | Effect on correlation state

| _Refused before exposure_
| A refusal that is decided before the message is given to the delivery mechanism: rows 1 to 7 of <<someip-results>>, or uProtocol delivery that does not accept the message for lack of a recipient or of room. Or a failed hand-over that the mechanism's contract, as the translator's released documentation cites it, states to leave nothing accepted and nothing transmitted.
| Nothing was exposed.
| As if the hand-over had not been attempted: nothing is created, and a state that the attempt had changed is restored. One thing is not undone: an answer that claimed the entry before the outcome of its request's hand-over was decided ("Order", in <<someip-entry>>). The party that the lifecycle names may try again: the caller of `send`, or the translator itself for an answer that it holds (row FW8).

| _Accepted_
| The delivery mechanism has accepted the message.
| The hand-over happened, and nothing about receipt or processing.
| The state advances.

| _Indeterminate_
| Every other failed hand-over.
| Nothing either way: a failure code alone is no proof that nothing was transmitted.
| As if accepted: the message may be exposed, so the state advances, and that hand-over is not repeated. The result of the call still reports the failure.
|===

An integration whose delivery interfaces fail only in the first way never meets the third outcome, and nothing requires one to exist.
That a call hands over nothing and leaves every entry as it was is promised for the first outcome and for no other.
"As if accepted" is a statement about correlation state and about nothing else: it does not say that the message was delivered, and it does not keep the failure from being observed, because a caller gets the failure as the result of its call, and <<someip-counts>> says which failed offers without a caller are counted.

*When uProtocol delivery has accepted a message.*
Acceptance is the event at which a deliverable message stops being the correlation's to deliver.
<<someip-delivery-acceptance>> defines it for each mechanism that the translator may use, and none of them is newly required.

.Acceptance by uProtocol delivery
[[someip-delivery-acceptance]]
[cols="2,4,4,2,6",options="header"]
|===
| Mechanism | Accepted when | Not accepted: a refusal before exposure | Indeterminate | After acceptance

| Push (rows 9 to 23 of <<someip-call-allocation>>)
| The translator has committed the message for the invocation of every listener that is registered and matches at that moment. The commitment is one decision: it covers every such listener, or none, and it does not wait for a callback.
| _No recipient_: no registered listener matches at that moment. _No capacity_: the mechanism's declared bound leaves no room to commit the message for every matching listener.
| Never: the decision is local.
| Row 16: each of those listeners is invoked at least once. Row 23 holds beside it: no listener is invoked after its unregistration has completed successfully. The translator keeps both by ordering them: the unregistration of a listener to which a committed invocation is still owed completes successfully only when that invocation has been made. How it does so is its own matter, and this chapter requires no blocking wait for it. Nothing here waives an owed invocation, makes acceptance wait for a callback to return, or changes or reopens an entry. When an invocation happens, in which order, and whether a callback is slow or fails, changes no entry and is reported to nobody. A listener returns no acknowledgement, and none is added.

| Pull (rows 6 to 8)
| The message is stored where a later matching `receive` returns it under rows 7 and 8.
| _No capacity_: the declared store has no room.
| Never.
| The message waits for `receive` until it expires. No queue design is prescribed; the bound is the one that the supplier declares.

| A UTransport leg that the translator itself sends on
| That leg's `send` completes successfully, which is its own row 5.
| The leg's `send` fails, and that transport's contract states that such a failure hands nothing over. A result code alone states no such thing.
| The leg's `send` fails otherwise.
| The leg carries the message under `+req~utransport-send-preserve-data~1+` (xref:README.adoc[Transport & Session Layer (uP-L1)]), and the translator no longer owns it.
|===

Where the translator offers both push and pull, its released documentation says which of them takes a message, and acceptance is that mechanism's.
The third row is for a translator that passes deliverable messages to another transport itself, and it does not replace the declaration of row 24.
A leg that a listener's own code sends on is that listener's business, and push acceptance applies.

What is counted when an offer is not accepted depends on the kind of message, and <<someip-counts>> is its one list.
A Publish or a Notification for which no listener matches is no refusal and has no count: nobody asked for it.
A reconstructed request that is refused is counted once (row RV3 of <<someip-entry>>), and so is a reconstructed event whose one offer fails.
A reconstructed response that is refused is kept and offered again: the refused offer is not counted, and only its terminal outcome is (rows FW8 to FW10).
A generated response is offered once, and a failed offer of it is counted once (row FW11).

*What this does not add.*
This chapter adds no second application API, no new runtime object, no duty to implement both delivery methods, no acknowledgement from a listener, no synchronous callback and no required queue or transport leg, and it maps the UTransport calls onto no SOME/IP library's calls.
A deliberate transcoding of application payloads is a separately selected operation with its own schema and resource contract, and it is no part of this translation.

[[someip-identifiers]]
=== Identifiers

[.specitem,oft-sid="dsn~up-transport-someip-identifiers~1",oft-needs="impl,utest",oft-covers="req~up-transport-someip-service-translation~1",oft-tags="SomeIpTranslator"]
--
A valid uProtocol identity and an identifier that the stock profile lets an ordinary service use are two different sets.
The core uProtocol ranges (xref:../basics/uri.adoc[UUri]; xref:../basics/uattributes.adoc[UAttributes]) do not change.

.Identifier domains
[[someip-identifier-domains]]
[cols="3,3,3,3,4",options="header"]
|===
| uProtocol field | Valid values in a message | SOME/IP field | Values that the profile reserves | Consequence for the direct mapping

| `ue_type_id` | `0x0000` to `0xFFFE` | Service ID | `0x0000`, `0xFFFE`, `0xFFFF` | Types `0x0000` and `0xFFFE` have no direct image
| `ue_instance_id` | `0x0001` to `0xFFFE` | Instance ID, in service discovery only | `0x0000`, `0xFFFF` | Every valid value maps
| `ue_version_major` | `0x00` to `0xFE` | Interface Version | None that a valid message can hold | Every valid value maps
| A method's `resource_id` | `0x0001` to `0x7FFF` | Method ID | `0x0000`, `0x7FFF` | `0x7FFF` has no direct image
| An event's `resource_id` | `0x8000` to `0xFFFE` | Event ID | `0x8000`, `0xFFFF` | `0x8000` has no direct image
| The client's `ue_type_id` | `0x0000` to `0xFFFE` | Client ID | Events carry `0x0000` (<<uuid-mapping>>) | Chosen by the client identity agreement, never by masking; the event rule reserves no Client ID for requests
|===

* *Direct mapping is the default.* The translator *MUST* map each identifier value for value, as `+dsn~up-transport-someip-uri-mapping~1+` states (<<uri-mapping>>), unless a declared identifier table maps it.
The mapping polices what the wire can represent, not how a deployment allocates identifiers.
* *Two special Service IDs.* The profile also allocates the Service ID `0x0101` to the Enhanced Testability Service and reserves `0x433F` for a camera interface.
Those are allocations for a purpose, not values that the wire cannot carry, and the translator does not refuse them.
A contract that maps a uProtocol type onto one of them, directly or through a table, has to be that purpose's service, and that is the contract author's to answer for, like every allocation.
* *No image.* The translator *MUST* refuse a value that has no direct image and that no declared identifier table maps: at setup, by name, where the route's declaration fixes the value (a topic, a method or a service), and at `send` with `UCode.OutOfRange` where the value appears only in a message.
* *A declared identifier table.* A service contract may declare, for a field, a finite table of pairs: a uProtocol identifier, and the SOME/IP identifier that stands for it.
The table is part of the declared mapping context on both sides, and the inverse uses the same table.
The translator *MUST* refuse at setup, naming both entries, a table in which a side holds one value twice, a method's image lies outside `0x0001` to `0x7FFE` or an event's outside `0x8001` to `0xFFFE`, an image is a reserved value, an image equals an identifier that the same translator maps directly for that service, or a uProtocol identifier has both a table image and a direct use.
So the kind stays readable from the identifier.
Nothing is masked, offset or allocated globally, and this chapter assigns no identifier to any service.

For example, the change Notification of xref:../up-l3/usubscription/v4/README.adoc[uSubscription] has the source type `0x0000` and the resource `0x8000`.
Both are valid uProtocol values, and both direct images are reserved.
Without a declared table, the route is refused at setup; with a table that pairs type `0x0000` with a declared Service ID and resource `0x8000` with a declared Event ID, the Notification is translated, and the inverse gives back `0x0000` and `0x8000`.

[[someip-client-identity]]
=== Client IDs: the client identity agreement

[.specitem,oft-sid="dsn~up-transport-someip-client-identity~1",oft-needs="impl,utest",oft-covers="req~up-transport-someip-service-translation~1",oft-tags="SomeIpTranslator"]
--
The _client identity agreement_ is an explicit, injective map between client uEntities, each named by its authority, type, instance and major version, and Client IDs.
It is part of the deployment's declared context, and two client instances of one type need two Client IDs.

* *Its domain is the network.* The map covers every client uEntity that the translator represents or reconstructs on the selected SOME/IP network, and it is injective over that whole set: one Client ID never stands for two client uEntities of that network, whichever endpoints they use.
A Client ID *MUST* be unique for the network.
* *The look-up key selects and does not partition.* Inbound, the translator finds an entry of the map by the remote endpoint and the Client ID, and that key does not make one map for each endpoint.
The translator *MUST* refuse at setup, naming both entries, a declaration that gives one Client ID to different clients at different endpoints of one network, as it refuses any map that is not injective.
* *Outbound.* The translator *MUST* take a request's Client ID from the agreement's entry for the request's source, and *MUST* refuse with `UCode.OutOfRange` a request whose source has no entry.
No Client ID is computed from a URI, by masking or otherwise.
* *Inbound.* The translator *MUST* supply the source of a reconstructed request, with its authority, type, instance and major version, from the entry that the remote endpoint and the Client ID select, and *MUST* refuse a `REQUEST` for which no entry exists (step 7 of the `REQUEST` list of <<someip-inbound>>).
The client's major version is never taken from Interface Version.
* *What it does not do.* The translator takes no census of the network and polices no stock peer.
That the stock clients outside the map keep to other Client IDs is the deployment's to ensure.
The map proves no identity (<<someip-service-translation>>, "Identity and authorization").
--

[[uuid-mapping]]
==== UUIDs

NOTE: xref:../basics/uuid.adoc[uProtocol UUID] specifications create a unique identifier for each message along with timestamp information.

[.specitem,oft-sid="dsn~up-transport-someip-request-correlation~1",oft-needs="impl,utest",oft-covers="req~up-transport-someip-service-translation~1",oft-tags="SomeIpTranslator"]
--
uProtocol correlates a response with its request by the request's UUID, which the response names in its `reqid` and which is not reused (xref:../basics/uattributes.adoc#response-attributes[RPC Response Message Attributes]).
SOME/IP correlates them by the `RequestID`: a 16 bit Client ID followed by a 16 bit Session ID.
The rules of this item concern the requests that the translator sends, except the clause "Requests that the translator receives".

*Terms.*

* A _transport association_ is one connection between the translator's client endpoint and one server endpoint, from its opening to its end; a binding without connections has none.
* A _correlation scope_ is one client and server combination as the wire has it: a Client ID together with the server endpoint that its requests address.
Under the `association` boundary every transport association is a scope of its own, which is what that boundary's premise makes sound.
Under `bound D` and `cycle` a scope outlasts its connections: a reconnection to the same server endpoint continues the scope, with its sequence, its held keys and its exclusions.
* A _key_ is a scope and a RequestID.
The Message ID and the Interface Version are not part of the key; they are compared with the entry.

*Session rules.*
The translator *MUST* keep these rules, whichever part assigns the Session IDs:

. A request uses active session handling. The candidates of a scope run `0x0001`, `0x0002` and so on to `0xFFFF`, and then `0x0001` again; `0x0000` is never one.
. The _next candidate_ of a scope is `0x0001` where the scope has used none, and otherwise the value after the one that it used last.
. _Strict next candidate._ A request takes the scope's next candidate and no other. Where that candidate is held or excluded (key rules 1 and 2), the request is refused with `UCode.ResourceExhausted`: nothing is transmitted, the candidate is not used, and the next request of the scope meets the same candidate. No other value is tried, even where one is free. Exclusion wins over the wrap: `0x0001` after `0xFFFF` is a candidate like any other.
. A candidate is _used_ when the hand-over of its request to SOME/IP delivery is accepted or indeterminate (<<someip-hand-over>>). A request that is refused before the hand-over uses none. Where the hand-over itself fails as a refusal before exposure, the translator's documentation says whether the candidate is used or met again; either is safe, because that key was never on the wire. The choice is the same where an answer claimed the entry before such an outcome ("Order", in <<someip-entry>>): the claim (row FW5) does not release the entry: the entry stays claimed, also where row FW8 keeps the answer, and its key held, until row FW7, FW9 or FW10 releases it, and the key's exclusion, and under `bound D` its time D, start at that release. A stale claim of a request that was never exposed does not by itself make the candidate used. Where the documentation says "met again", the next request meets that key under the scope's boundary: at once under `cycle`, and under `bound D` once D has passed since the release; "met again" bypasses neither a claim that still holds the key nor an exclusion that applies to it. Under `association` the case lies outside the premise.
. An event carries Client ID `0x0000` and Session ID `0x0000`, unless the contract declares session handling for it or the message is segmented; then the same start and wrap apply. A response never has a RequestID of its own: it copies the request's.
. _Settlement._ A candidate that has been given to a request stays assigned to it until rule 4 settles it, also where the request's entry has been released before the outcome of its hand-over: a release frees the entry's capacity and starts the key's exclusion, and it does not end that assignment. The translator *MUST NOT* give a candidate so assigned to a second request. A late outcome settles it: an accepted or indeterminate one uses it, and the next candidate then follows it (rule 2); a refusal before exposure keeps the choice that rule 4 lets the documentation make. Knowing that a request has been exposed rules out a refusal before exposure, and does not by itself use the candidate or advance the next candidate before the outcome settles. This chapter prescribes no result for a request whose next candidate is only so assigned: it neither requires a refusal for it nor excludes waiting for the settlement.

*Who assigns the value.*
The rules are duties of the translator whichever part assigns the Session IDs, and the stack may assign them.
Where the stack assigns them, the translator's declared configuration *MUST* determine the RequestID that the `REQUEST` carries on the wire, so that the entry is matchable under that key by the time an answer can arrive (<<someip-entry>>, "Visibility"), and *MUST* keep a `REQUEST` from being transmitted under a held or excluded candidate: to notice the collision after the transmission is not compliance.
The released documentation names the supplier's assignment domain and rule, and the reuse boundary that the configuration supports.
A configuration that cannot do both is refused at setup, or is not offered as conforming.
A counter that several scopes share is the plain example: no scope gets its own sequence from it, so it meets these rules only where it serves one scope.
No hook, interface or patch is prescribed; whether a given stack can be configured so is not decided by this chapter.

*Key rules.*
The profile lets a client reuse a RequestID as soon as the response has arrived or is no longer expected, and its UDP binding gives no guaranteed delivery.
So an answer to a released request can arrive after a later request holds the same key, and the stock header has no field that tells the two apart: matching alone cannot meet a duty to ignore every response to an expired request.
Reuse is permitted by the profile and is no violation.
The translator *MUST* keep these rules:

. _Live uniqueness._ No two entries of one scope that are not yet released hold the same RequestID. A RequestID that an unreleased entry of the scope holds is _held_.
. _Exclusion after release._ A RequestID that has been released in a scope is _excluded_: it is not assigned again in that scope before the scope's reuse boundary allows it. Every release counts, whatever caused it: an answer that was delivered, an expiry, an indeterminate hand-over of an answer, and a restart or a loss that ends the entry. An indeterminate hand-over of a request is no release: where no earlier answer has already claimed or released it (rows FW4 and FW13 of <<someip-entry>>), its entry stays open and its key held (<<someip-hand-over>>).
. _The reuse boundary of every scope is explicit_, and it is one of three, each with its premise and the party that supplies it:
+
[cols="2,4,6,4",options="header"]
|===
| Boundary | A released key may be assigned again | Premise, and its supplier | What is promised

| `association`
| Never on the same transport association
| _Answer affinity_: every answer, and every duplicate, that the peer produces for a request is sent on the association that carried the request, or is discarded once that association has ended; none is sent for the first time, or sent again, on a later association. Supplier: the selected binding and stack together with the peer's behaviour, as the contract that the deployment selects for that composition states it. The translator cannot verify a peer.
| While the premise holds, no late or duplicated answer is taken as another request's answer, on this association or on a later one. A later association is a new scope: its sessions start at `0x0001`, and it inherits no exclusion.

| `bound D`
| When the duration D has passed since its release
| No answer to a request of the scope reaches the translator later than D after that request's release, whatever released it. Supplier: the deployment, which declares D and answers for it. The translator cannot verify it.
| The same, while the premise holds. An answer later than D is outside the promise.

| `cycle`
| When the session cycle has returned to it: when it is the scope's next candidate and no unreleased entry holds it. The cycle itself adds no other condition, no time after the release and no further turn of the cycle: where the sequence came back to the key while a request still held it, the key is assignable as soon as that request is released, and only `bound D` counts a time from the release. The key stays subject to a candidate's assignment to a request whose hand-over has not settled (session rule 6) and to uniqueness or exclusion over a wider set than one scope (key rule 6): under `cycle` a next candidate is refused while it is held or excluded through such a set, and one that is only assigned is not given to another request.
| None
| Key rule 4 only. The deployment declares that it accepts the residual of key rule 5.
|===
. _What always holds._ An answer whose key matches no matchable entry (<<someip-entry>>, "Matchable entries") is _unmatched_. An answer whose key matches a matchable entry, but whose Message ID or Interface Version differs from the entry's, is _mismatched_, and the entry stays as it was. Both are ignored and counted, under every boundary (rows FW6 and FW12 of <<someip-entry>>).
. _The residual under `cycle`._ An answer to a released request that arrives after its key has been assigned again, by the cycle's return or after a restart, and whose Message ID and Interface Version equal the later request's, is taken as the later request's answer. This is the one deliberate exception to ignoring responses to an expired request, and it applies only where a deployment has declared `cycle`.
. _The size of a scope._ One Client ID leaves 65,535 Session IDs that are not zero. Under `association` a scope therefore has at most 65,535 uses for the life of its association, and fewer where the translator applies uniqueness and exclusion across a wider set than one scope, which it may do and need not. Once the sequence has come round to keys that were released on that association, they stay excluded for as long as it lives, and every further request of that scope is refused with `UCode.ResourceExhausted` by session rule 3. The translator may continue on a new association, which is a new scope, where the premise holds for it. Nothing here commands a connection to be closed at that count, and nothing makes a reconnection automatic. Uniqueness over a wider set than one scope stays permitted, and its cost under session rule 3 is this: where the sets of two scopes overlap, a scope whose next candidate is held or excluded on account of the other is refused with `UCode.ResourceExhausted` for as long as that lasts, and no other value is tried; under `association` that can be the life of the association. The cost depends on the whole identity that the wider set compares, so it is not the same for every such set: equal Session ID values alone do not make the sets of two scopes overlap. What the replacement of a shared connection does to the events and other services that use it is not decided by this chapter.
. _Restart, and the loss of correlation state._ A restart shortens no exclusion.
+
[cols="2,9",options="header"]
|===
| Boundary | After a restart of the translator, or the loss of its correlation state

| `association`
| A restart ends every earlier association. Where the state is lost while an association still lives, no further request is sent on that association: each of its keys counts as excluded. Requests go out on new associations, which are new scopes, and that is sound exactly as far as answer affinity holds for the peer, which is the premise. Nothing else is carried over.

| `bound D`
| Every key of the scope that was held or excluded counts as released at the restart at the latest. The scope resumes at once only where surviving or reconstructed information accounts for every key that may still receive an answer: the keys that were open or claimed when the state was lost, as well as those released less than D before. The key values and their remaining exclusion are enough, and no message has to survive. Each such key stays excluded until its own D has passed, counted from the restart for a key that was held. A record that covers released keys only does not qualify. Without full coverage the whole scope sends no request until D after the restart.

| `cycle`
| Sessions start again at `0x0001`, and the declared residual covers what follows.
|===
+
After a restart a scope that still exists takes as its next candidate the one that the surviving information gives, and `0x0001` where it gives none; the exclusions above apply to that candidate as to any other.
A restart loses the open entries themselves unless the translator declares that it keeps them, and for a lost entry nothing is delivered: a translator that no longer knows a request generates no timeout for it, and the requester's own expiry applies.

*No boundary by label.*
A connection-oriented transport keeps the bytes of one connection out of another, and that is not answer affinity.
A peer can produce the answer to an old request after the old connection has gone, and send it for the first time on the new one, and a reconnection can use the same addresses and ports again.
So the boundary of a scope is never taken from the name of its transport:

* `association` is a scope's boundary only on a binding that has connections, and only where the contract that the deployment selects for binding, stack and peer expressly states answer affinity; it is then explicit in that contract and needs no second declaration. "Connection-oriented" or "TCP" is no such statement.
* Where that contract does not state it, the deployment declares `bound D` or `cycle` for the scope.
* The translator *MUST* refuse at setup, by name, a scope with no explicit boundary, a declared `association` whose composition does not state answer affinity, and a declared `association` whose binding has no connections, and *MUST NOT* put one boundary in the place of another.

*What setup works from.*
The deployment selects one contract for the composition of binding, stack and peer, and the translator's documentation says how that selection is made.
Setup reads each scope's boundary from that contract or from the deployment's declaration, and for `association` it reads the contract's statement of answer affinity.
No second declaration, no further setup value and no reference field is required, and setup proves nothing about a peer: whether the statement is true is the deployment's evidence.
This chapter invents no value for D, and it does not claim that a finite exclusion rejects an arbitrarily late packet: the promise under `bound D` is conditional on a named premise.
It asks no peer to send at most one answer either: with answer affinity and no reuse on the association, any number of late duplicates stay unmatched.

*Requests that the translator receives.*
Assignment, exclusion and the reuse boundary do not apply to them, because the stock client assigns those keys; live uniqueness does.
The _received key_ of an inbound request is its remote endpoint, the server endpoint that it reached, and its complete RequestID.
The live uniqueness of a received key runs from the start of the reconstructed request's hand-over, its private preparation included, until its entry is withdrawn (row RV3) or released.
Within that interval the translator *MUST* refuse a further `REQUEST` with that key at step 7 of the `REQUEST` list (<<someip-inbound>>): it is counted, nothing is sent, no second entry and no second reconstructed request arise, and the first entry goes on unchanged.
A withdrawal is no release, and it starts no exclusion.
After the withdrawal or the release, a `REQUEST` with that key is a new request, also where the first hand-over has not returned: a late outcome of that hand-over belongs to the first entry (row RV13) and does not change the new one.

The residual is stated, not removed.
The translator cannot tell a retry or a network duplicate from a new call that reuses the RequestID, which the profile lets a client do as soon as it stops expecting an answer.
Where a stock client's own response timeout is shorter than the TTL that the contract supplies, the client may send a new request under a key whose entry is still live: that request is refused as above, and the answer to the earlier request, which goes out under the same RequestID, may be taken by the client as the answer to its newer one.
The translator promises a stock client neither at-most-once execution nor a way to tell its requests' generations apart, and a deployment that needs the two timeouts to agree chooses the supplied TTL to fit. This chapter defines no supersession of the first entry and no store of past requests.

==== Message Type

<<umessagetype-mapping>> table below maps uProtocol messages to SOME/IP message types, and <<umessagetype-inbound>> maps them back.

[.specitem,oft-sid="dsn~up-transport-someip-message-type-mapping~1",oft-needs="impl,utest",oft-covers="req~up-transport-someip-service-translation~1",oft-tags="SomeIpTranslator"]
--
*Payload slots.*
The type, the return code and the payload are decided together, and the payload rules apply to a _slot_, not to an operation.

* An event has one slot. A method has a request slot and a success slot and, where its contract declares a modelled error, an error slot.
* The service contract declares for each slot its presence, _always a payload_ or _never a payload_, and, where it is _always_, its one encoding ID: the registered or private-use identifier that the contract assigns to the encoding (xref:../basics/payload_encoding_registry.adoc[payload-encoding registry]), or `0` where the contract defines the concrete encoding without assigning it one.
An error slot is _always_.
The slots of one method are independent: a getter's request slot is _never_ and its success slot _always_, and an error slot may have another encoding ID than the success slot.
* The translator *MUST* refuse at setup, by name, a slot that would need both states, because the wire has no discriminator for it.
This is asked of one slot and never across slots: the type and the return code already tell success from failure.
* The translator *MUST* refuse a payload or a body of an _always_ slot whose encoding it cannot establish from the contract, as one that the slot does not admit.
* For each method the contract declares one _failure representation_: _code only_, which is the default, or _modelled error_, with its error slot.
* *Precedence.* The joint tables select the branch, and with it one slot or none.
The presence, encoding and byte rows of <<common-umessage-attributes>> apply to the selected slot and to nothing else.
A code-only failure has no slot: a payload of the uProtocol response is checked against no slot and is _lost_, and the reconstructed response has no payload.
That loss is declared; it is neither a preservation nor a refusal.

*The joint tables.*
The translator *MUST* map each uProtocol message as <<umessagetype-mapping>> states, and each complete SOME/IP message that reaches the joint tables as <<umessagetype-inbound>> states.

The wire cannot say more: an error that a stack generated without any detail, and a modelled error whose encoding is empty, are the same bytes.
The declared slot is the rule of interpretation, and it does not recover what the sender meant: what zero bytes mean is for the consumer's codec to say, and a consumer whose codec cannot decode them handles that as it handles any error payload that it cannot decode, the commstatus having already told it that the call failed.
A `RESPONSE` with a code other than `0x00` on the same method stays the branch with no payload. This chapter defines no fall-back to absence, no discriminator and no promise that the inbound side mirrors the outbound fallback.

=== Inbound admission

[.specitem,oft-sid="dsn~up-transport-someip-inbound-admission~1",oft-needs="impl,utest",oft-covers="req~up-transport-someip-service-translation~1",oft-tags="SomeIpTranslator"]
--
*Two control paths.*
The pipeline of this item is for application traffic: the RPC and event messages that arrive at the translator's endpoints.
Two kinds of control unit do not enter it.
The translator *MUST* take each of them out at the framing and demultiplexing boundary that its released documentation names, as <<someip-control-units>> states: a SOME/IP-SD candidate by its Message ID pair alone, for the SD path to validate, and a TCP magic cookie only in its complete form for the direction in which it arrives.

.Control units
[[someip-control-units]]
[cols="2,6,6,3",options="header"]
|===
| Control unit | How it is recognized | What happens to it | Counted

| A SOME/IP-SD message
| By the SD Message ID: Service ID `0xFFFF` with Method ID `0x8100`. That makes a unit a candidate for the SD path and nothing more.
| The stack's SOME/IP-SD handling takes it and applies the profile's checks for SD: the SOME/IP header first, then the SD length, the arrays of entries and options, and each entry. Eventgroup entries that this path admits reach the subscription mapping, `+dsn~up-transport-someip-subscription-mapping~1+` (<<eventgroup-entry-mapping>>). A near-cookie with Message Type `0x01` is a `REQUEST_NO_RETURN`, and is refused by name.
This chapter adds no duty to send cookies or to resynchronize by them; the framing and demultiplexing component that the translator's documentation names still removes every complete TCP magic cookie of the right direction that arrives.

[cols="1,8,6",options="header"]

| Step | Cause | Outcome

| 1
| A Return Code other than `0x00`

| 2

| 3

Steps 1 to 4 send nothing, so their order decides only which count a compound case gets.
Steps 2 and 3 stand before every generated reply, so a request without a usable session, or one addressed to an event or to a reserved identifier, is not answered, whatever else is wrong with it.
The set of declared major versions in step 5 may have one member: nothing here requires a translator to serve two versions of one service at once, and a contract that does so borrows no method across versions.
The five causes of step 7 are judged in the order in which its row lists them, so a compound case has one cause and one count there too.
The first four are decided before anything is reconstructed; the fifth is the only one that follows a reconstruction, and it is row RV3 of <<someip-entry>>.

*The generated reply.*
A generated reply is not a mapped application response: no uProtocol message stands behind it, the method's failure representation does not apply to it, and it creates no cache entry.
The translator *MUST* give every generated reply the one form of <<someip-generated>>.

[[someip-generated]]

|===
| Field | Value

| Message Type | `RESPONSE` `0x80`, on every method, also on one that declares a modelled error
| Return Code | As its cause states: step 5 or step 6 of the `REQUEST` list, or the declared expiry code below
| Payload | None; Length 8
| Protocol Version | `0x01`
| Message ID, RequestID, Interface Version | Copied from the `REQUEST` as received. A wrong Interface Version is echoed, not corrected.
|===

The translator *MUST* offer a generated reply to SOME/IP delivery once, and *MUST NOT* offer it again.
An accepted offer is not counted.
An offer that fails, as a refusal before exposure or indeterminately (<<someip-hand-over>>), is counted once as _generated reply offer failed_; after an indeterminate failure the reply may be on the wire, and the count does not say otherwise.
The form stays `RESPONSE` whichever type a stack would choose for the same cause; a stack that generates such replies itself, below the translator's code and in another type, does not change this form.

*The optional expiry reply.*
When a stock client's request gets no uProtocol answer within the supplied TTL, the default is silence: the stock client's own response timeout ends its call, and that indication is local to the client.
`E_TIMEOUT` is never sent.
A contract may declare an expiry code for a method: an interface-specific code or `E_NOT_OK`, and never `0x00`, a code that the profile keeps off the wire, or a reserved one.
The declaration is complete with that code, because the reply is a generated reply in the form above, with its fields copied from the entry; no body source exists for a modelled error at expiry, so none can be declared, and the translator *MUST* refuse at setup, by name, a contract that declares an expiry body.
A uProtocol answer that arrives after the release is refused with `UCode.NotFound` and counted (row RV11 of <<someip-entry>>).

*Segmentation on the way out.*
Outbound segmentation also happens below the joint tables, and every segment carries the original's Message ID, RequestID, versions and return code.
A segmented original has active session handling, also where it is an event, and every segment carries the original's Session ID, which the stack below the tables supplies.
A translator whose stack does not support segmentation says so in its declaration, and an outbound message that exceeds the unsegmented limit of its declared transport is then outside its intrinsic domain (row 4 of <<someip-results>>).

[[someip-entry]]
=== The two entry lifecycles

[.specitem,oft-sid="dsn~up-transport-someip-entry-lifecycles~1",oft-needs="impl,utest",oft-covers="req~up-transport-someip-service-translation~1",oft-tags="SomeIpTranslator"]
--
One cache serves a translator instance, and its size is a declared bound.
An entry is _open_, _claimed_ or _released_.
Release is terminal and happens once: it restores the cache's capacity and, for a forward entry, starts the key's exclusion (<<uuid-mapping>>, key rule 2); the exclusion record of a released key is not an entry and holds no message.
The translator *MUST* change an entry only as the two tables of this item state, and the other items of this chapter refer to their rows.
The tables use one more label, _in hand-over_, for a request whose hand-over has begun and whose outcome is not yet decided.
It is a label for reading the tables and asks for no state, object or interface of its own: a translator that creates the entry in one step with an accepted hand-over passes through it with nothing to observe.

*Preparation and activation.*
Before and during a hand-over a translator may prepare for the entry: reserve storage, take the candidate, write a record.
Preparation is private.
A prepared record is no entry of these tables: it matches nothing, it has no deadline, and dropping it is no release and starts no exclusion.
It still keeps its key from a second request: one candidate is never given to two requests, and a received key counts as live for row RV12 from the start of the hand-over.
An entry exists from its _activation_, the point from which it is matchable under its key.
An entry is active at the latest when its hand-over ends accepted or indeterminate; a translator may activate it earlier, inside the hand-over, and the visibility rule says when it has to.
The rows that judge an answer against an entry take one that is active in hand-over like an open one (rows FW5, FW6, RV5 and RV6), and no two active entries ever share a key.

*Matchable entries.*
An entry is _matchable_ for an answer while it is open, or active in its hand-over, and its original deadline has not passed, under its key and with the checks that the row which judges the answer states; a claimed or released entry, and a prepared record, are not matchable for a new answer.
Where the deadline passes while the hand-over's outcome is pending and the translator does not know that the request has been exposed, an answer that arrives before the outcome is decided claims nothing, and goes to the rows of an answer after the expiry (rows FW12 and RV11); the admission of the inbound pipeline, and rows 1 and 2 of <<someip-results>> for a response, still come first.

*Visibility.*
Whenever an answer that a request caused can be processed, the entry of that request *MUST* be active under the right key.
For a forward entry that key is the RequestID that the `REQUEST` carries on the wire, whichever part assigned it; for a reverse entry it is the reconstructed request's `id`.
So activation comes no later than the exposure of the request; it need not come at the beginning of the hand-over, and nothing makes a prepared record matchable before it.
How a translator achieves this is its own matter: publishing the entry together with the hand-over, a provisional state that takes effect at exposure, and holding back the processing of answers until the entry exists are all admissible, and none is prescribed.
One limit applies to all of them: a response that a listener sends from inside its callback is processed like any other, and it never waits for that callback, or for the call that delivered the request, to return.

*Order.*
A claim, and the decision of a hand-over's outcome, are single transitions on an entry and never interleave; either can come first.

* _The outcome first._ Rows FW2 to FW4 and RV2 to RV4 apply.
* _A claim first._ An answer that passes its checks before the outcome is decided claims the entry (rows FW5 and RV5). The outcome then changes nothing in the entry, whichever it is (rows FW13 and RV13): the answer goes on to its delivery by the rows for a claimed entry, the entry is released once, and a `send` that is in progress still returns its own result. This comes before the general effect of a refusal before exposure (<<someip-hand-over>>): what the attempt changed is restored, but a claim is not undone.

Where a claim came first and the outcome is then a refusal before exposure, the request cannot have caused that answer.
For a forward entry this is the declared residual under `cycle`, and under the other two boundaries the premise was broken; a translator that activates an entry only at exposure never meets it.
A reverse entry has no such residual: its key is the reconstructed request's `id`, which is not reused, so a response that claims it shows that the request reached a server, and a later report that nothing was handed over contradicts the contract that the report rests on. The claim stands there too, also where row RV8 later undoes the answer's claim: the entry is then open again, and the late outcome still changes nothing in it (row RV13).
Whether the candidate of such a forward request counts as used stays as session rule 4 of <<uuid-mapping>> states.

*Deadlines.*
An entry's deadline comes from its request and never moves: a forward entry ends when its request's TTL expires, and a reverse entry when the supplied TTL of the reconstructed request has passed.

. _No fresh lifetime._ A hand-over that ends accepted or indeterminate only after the deadline leaves an entry that is open and expires at once (rows FW11 and RV10).
. _No revival._ An entry that has been released is not created again, changed or counted again by an outcome or a result that arrives later (rows FW13 and RV13).
. _Preparation expires nothing._ A request whose hand-over ends as a refusal before exposure leaves no entry, no exclusion and no generated timeout (rows FW3 and RV3), whatever was prepared and however long the hand-over took, unless a claim came first. So the expiry rows apply to an entry in hand-over only where the translator knows that its request has been exposed, and both outcomes that are still possible then leave the entry open. Otherwise a deadline that passes during the hand-over is applied when the outcome is decided, and an answer that arrives in between claims nothing, as after an expiry (rows FW12 and RV11).

*Forward: a uProtocol client's request to a stock server.*
The key is the scope and the RequestID.
The entry holds the request's `id`, source, sink, priority and TTL, and the Message ID and Interface Version that were sent, and it lives until the request's TTL expires.

*The generated timeout is an ordinary response.*
The `DeadlineExceeded` response of row FW11 is a uProtocol message that the translator produces, so the published rules for an RpcResponse apply to it, and this chapter adds none (xref:../basics/uattributes.adoc#response-attributes[RPC Response Message Attributes]).
It has an `id` of its own, whose time is its creation time.
Its source is the invoked method and its sink the requester's reply-to address, which are the cached request's sink and source.
Its `reqid` is the request's `id`, and its priority and TTL are the request's; its commstatus is `DeadlineExceeded`.
Its TTL runs from its own creation time, so pull delivery judges it like any other deliverable message (row 8 of <<someip-call-allocation>>).
No rule of this chapter gives it a payload or forbids one: as for every message, the payload and `payloadEncodingId` are both present or both absent (xref:../basics/uattributes.adoc#common-attributes[UAttributes]).
The form of a generated SOME/IP reply (<<someip-generated>>) is a different construction, and does not carry over to it.

*Connection loss.*
The profile requires outstanding requests to be handled as timeouts when a TCP connection is lost.
That duty lies on the SOME/IP side: the translator's stack meets it as its documentation says, and the correlation rules neither replace nor suspend it.
What they add is this chapter's policy for the translator's own entries.

* Under `association`, an open entry whose association has ended can no longer be claimed. It stays open until its deadline, and then ends by row FW11.
* Under `bound D` and `cycle` the scope outlasts the connection, with its held and excluded keys. An open entry can be claimed by an answer that the selected composition actually exposes to the translator before the entry's deadline, on whichever connection of the scope it arrives, where it passes the checks of row FW5. Keeping the entry obliges no stack to expose such an answer: a stack that handles the request as timed out and discards a late answer leaves nothing to claim, and the entry ends by row FW11 at its deadline, as under `association`.

Under every boundary, row FW11 at the original deadline is how the timeout appears on the uProtocol side, so keeping a correlation scope and its keys across a reconnection is no departure from the profile's rule.
An integration whose SOME/IP side replaces or omits the timeout handling itself says so in its declaration, and does not claim the profile on that point.
Nothing in this clause reconnects automatically or extends a deadline.

*Reverse: a stock client's request to a uProtocol server.*
The key is the reconstructed request's `id`.

*Example: a reverse entry opened again.*
The initial hand-over of a reconstructed request is still pending when a genuine response claims the entry (RV5).
The response's own hand-over to SOME/IP delivery is refused before exposure (RV8), and the entry is open again, with the earlier claim in its history.
The initial hand-over then ends accepted or indeterminate: that late result changes nothing in the entry (RV13), which stays open and retryable until its original deadline.
A report that nothing was handed over would contradict the response's evidence, and "Order" still keeps that report from rolling back the earlier claim's evidence; this example adds no duty.

Row RV11 is row 3 of <<someip-results>> seen from the entry.
A response that fails validation, or that a determinable authority check refuses, gets row 1 or row 2 of that table first, whatever the state of any entry, and it is counted as _response refused_ like every refused response.

*A claimed entry at its deadline.*
The two directions differ, on purpose.
A reverse entry that is claimed when its TTL passes is judged when the outcome of the answer's hand-over is known: rows RV7 and RV9 release it, and row RV8 returns it to open, where it expires at once by row RV10.
That hand-over is the caller's own `send`, and its result is owed to the caller.
A forward entry is released by row FW10 at its deadline, also while an offer of the answer is under way on a transport leg; whatever that offer reports afterwards is a late result (row FW13): the entry is not released again, the answer is not offered again, and nothing more is counted.
The offer may have delivered the answer all the same: nothing here cancels a leg's `send`, and _answer not delivered_ records that no acceptance was confirmed by the deadline.
No general rule defers an expiry until a hand-over returns.

A reconstructed message is a new uProtocol message in both tables, so the response of row FW5 behaves as a native server's response does, and the entry of row RV2 lives by the TTL that the contract supplies, not by any lifetime of the stock client's.

*Capacity.*
Only a request needs a free entry.
A request that finds the cache full is refused: a uProtocol request with `UCode.ResourceExhausted` (row 6 of <<someip-results>>), and a stock request at step 7 of the `REQUEST` list, counted, with nothing sent.
A response uses the entry that it answers, and is never refused because the cache is full, also where that entry is the only one.
An event uses no entry.
Room in a delivery mechanism is a different bound, and it is judged where that mechanism accepts or refuses (<<someip-delivery-acceptance>>).

[[someip-delivery]]
=== Delivering a Notification to one destination

[.specitem,oft-sid="dsn~up-transport-someip-notification-delivery~1",oft-needs="impl,utest",oft-covers="req~up-transport-someip-service-translation~1",oft-tags="SomeIpTranslator"]
--
A uProtocol Notification has one destination.
A stock event goes to an event's subscribers, and its header names no receiver: events carry Client ID `0x0000`.
The translator *MUST* deliver a Notification to its destination only, or refuse it, and *MUST NOT* fan it out.

* *One kind for each event.* The contract declares each event as a Publish event or a Notification event, and it cannot be both, because the two kinds produce the same packet.
* *Plain event or field's notifier.* The contract also declares whether the stock event is a plain event or the notifier of a field.
The two differ in what a subscription causes.
A field has a valid value at all times, and its notifier sends that value to a new subscription as an initial event, and again after a stop that is followed by a new subscription; a plain event sends no initial value.
* *What the profile gives.* Where several subscribed clients sit on one ECU, the system replicates an event to them.
Sending an event to a subset of the subscribed clients is something that implementations should support, under the application's control, and not for the notification events of fields, and a service designed for selective sending is expected to keep working where the sender lacks the feature, by sending to all.
So selective sending is a capability that a stack may have, not a guarantee of the profile, and its fall-back is exactly the fan-out that a Notification may not have.
* *A recipient binding for each destination.* For a Notification event the contract names, for each admissible destination D, a delivery context that reaches D and no other uEntity, in one of three forms:
.. _Sole subscriber._ The deployment admits exactly one subscribed uEntity for that event: by static configuration or, for a plain event only, as the only active subscription. Delivery is unicast, with no multicast for the event and no second local subscriber behind the endpoint. This form uses no selective sending.
.. _Stock subset sending._ The event has several subscribers, and the contract declares that the sending stack supports sending that event to a subset. Delivery is unicast to D's subscriber endpoint, and no second local subscriber shares that endpoint's delivery. This form is not available for a notification event of a field, and a stack without the capability cannot have this binding declared.
.. _A declared selective extension_ of a named stack, such as one that puts the target's Client ID on the wire. It is not part of the stock profile, both sides must name it in the contract, and nothing here requires it.
+
A declared capability states a condition; whether a given stack and configuration meet it is deployment and implementation evidence.
* *A field's notifier needs one fixed recipient.* A field keeps its value after the subscriber that received it has gone, and sends that value to whoever subscribes next, so for a Notification event on a field's notifier, "the only subscriber at this moment" is not enough: two destinations D and D′ that take turns would each receive what was accepted for the other.
Such an event is admitted only under the sole-subscriber form in its static form: one destination D is the only admissible recipient for as long as the field's value can be retained.
An unsubscription, a reconnection, or a replaced endpoint or receiving context does not let that value pass to another destination.
A service that needs different recipients in turn uses a plain event; with one fixed recipient, field notifiers stay admitted.
* *An initial event is a new translated message.* Where the translator admits an initial event, it reconstructs it like any other event, with a new `id`, a new creation time and the contract's TTL.
It is not the uProtocol message that once set the value, it does not continue that message's TTL, and it is no second delivery of it.
So the same destination can receive the current value again after a stop and a new subscription.
The renewal of a subscription that is still valid causes no initial event, and nothing here relies on what a subscriber's control of initial data changes.
* *A Publish event on a field's notifier.* The contract says so, and two consequences come with it: a later subscriber receives the last value as a new message, and where the contract declares that the stack or its configuration suppresses unchanged updates, an update that equals the retained value causes no event.
Neither one stock event for each uProtocol Publish, nor one reconstructed message for each original, is promised.
* *Setup.* The translator *MUST* refuse at setup, naming the event, a Notification event with no declared recipient binding, and a Notification event on a field's notifier whose contract admits more than one destination or lets the destination change while the value can survive.
The one exception would be a contract that states explicitly why a value retained for an earlier destination cannot reach a later one; this chapter defines no such contract, and it assumes no capability of any stack to clear a field or to suppress its initial event.
* *Send.* A Notification whose sink has no recipient binding is refused with `UCode.OutOfRange`, because the declared context has no image for it, and one whose bound subscriber is not registered at that moment is refused with `UCode.Unavailable`, because that is the state of a peer and not a limit of the mapping (<<someip-results>>, rows 4 and 7).
In both cases nothing is sent.
* *Receive.* The reconstructed sink is the one uEntity that the recipient binding names for the receiving context, and where the context names none, or more than one, the translator *MUST* refuse the message locally.

[[someip-counts]]
=== Counted events

[.specitem,oft-sid="dsn~up-transport-someip-counted-events~1",oft-needs="impl,utest",oft-covers="req~up-transport-someip-service-translation~1",oft-tags="SomeIpTranslator"]
--
A count belongs to an event at a boundary, not to a message.
"Counted" means the same thing everywhere in this chapter: the event adds one to one count, once, at the point that <<someip-count-register>> names, and the translator *MUST* count each event of the register so, and no event twice.
Three kinds of event are counted, and they stay different events where they concern one message:

* an _admission refusal_: a stage, a step or a row refuses a unit, a message or a response, and a refusal has one cause, the first that applies, and one count;
* a _diagnostic of an accepted message_: the unlisted return code, after which the message goes on;
* a _terminal delivery outcome_: an offer ends without acceptance and is not made again.

So an answer with an unlisted code whose entry then expires before it is delivered has two counts, _unlisted return code_ and _answer not delivered_, for two events.

An offer _fails_ where it ends as a refusal before exposure or indeterminately (<<someip-hand-over>>), and the count of a failed offer records that no acceptance was confirmed.
Where the failure was indeterminate the message may have been delivered or sent, and no name in the register says otherwise.
An accepted offer is never counted.
Two failed offers are not counted where they happen, because the lifecycle goes on and observes what follows: a refused offer of a retained answer, which is made again (row FW8) and is counted only if the entry expires first (row FW10), however often it was refused; and an indeterminate hand-over of a reconstructed request, whose entry is open (row RV4).

The register is the complete list for the translation.
How a count is kept and read is the supplier's matter, and the translator's released documentation names, for each row, where the count can be observed, whether as a counter, a log record or a diagnostic interface, and which part counts it where the stack refuses a unit below the translator's own code.
This chapter adds no interface, and the register is no qualification claim.

Four things are not counted, on purpose.
Every refusal of a `send`-shaped call other than a refused response is returned to its caller, and that is its observation.
Steps 5 and 6 of the `REQUEST` list are answered on the wire.
A Publish or a Notification for which no listener matches was asked for by nobody.
And a control unit that framing or the SD path takes lies outside this translation register (<<someip-control-units>>): a magic cookie is no refusal, and of the SD path the register counts the declined subscription only; it adds no count for the SD path's other refusals and grants them no exemption from being observed, which the stack's documentation states.

== Application Layer Translation

NOTE: Application (or message payload) translation is the process of converting *SOME/IP-SD* subscription and discovery messages, to/from *uDiscovery* and *uSubscription* Messages.

=== uSubscription

The following section will elaborate only on the translation of *uSubscription* messages to/from *SOME/IP-SD* messages. Subscription state (persistent or not) is handled in the *uSubscription* services and not at the transport layer or this component.

The following section we will elaborate on how Eventgroup Entry types are mapped to xref:../up-l3/usubscription/v4/README.adoc[*uSubscription*] messages for the subscribe
and unsubscribe flows.

==== Common Fields and Eventgroup Entry Mapping

[.specitem,oft-sid="dsn~up-transport-someip-subscription-mapping~1",oft-needs="impl,utest",oft-covers="req~up-transport-someip-service-translation~1",oft-tags="SomeIpTranslator"]
--
The translator *MUST* map between each eventgroup entry type of SOME/IP-SD and the uSubscription message that <<eventgroup-entry-mapping>> pairs with it, with the common fields that <<common-field-mappings>> maps and with each identifier value mapped directly by default or through the service contract's declared identifier table and its inverse (<<someip-identifiers>>); a rule of these tables or of their notes that has its own key word keeps it, the translator is the actor of each rule of the tables and of their notes that names no other actor, and the inherited notes on ECU firmware and underlying SOME/IP libraries are non-normative.

<<common-field-mappings>> table below illustrates the common *SOME/IP-SD* EventGroup Entry fields that are present in all *SOME/IP-SD* Eventgroup entry types (`SubscribeEventgroup`, `SubscribeEventGroupAck`, `SubscribeEventgroupNack`, `StopSubscribeEventGroup`).
