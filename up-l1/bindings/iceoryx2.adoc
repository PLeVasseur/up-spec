[[classic-iceoryx2-v0-6-1]]
== Overview

[NOTE]
====
https://iceoryx.io[Eclipse iceoryx2&trade;] is a middleware for inter-process communication, built to be efficient and to have extremely low latency. Its library is designed to offer fast and reliable mechanisms of inter-process communication that are zero-copy and lock-free.

This document defines how uProtocol messages can be exchanged by means of iceoryx2 _Services_.
====

== iceoryx2 Version

[.specitem,oft-sid="dsn~up-transport-iceoryx2-protocol-version~1",oft-needs="impl",oft-tags="TransportLayerImpl"]
--
Each transport implementing this specification **MUST** use version `0.6.1` of the iceoryx2 protocol in order to ensure interoperability of different language libraries.
--

== iceoryx2 MessagingPattern

[.specitem,oft-sid="dsn~up-transport-iceoryx2-messaging-pattern~1",oft-needs="impl,utest",oft-tags="TransportLayerImpl"]
--
All types of uProtocol messages *MUST* be transferred using iceoryx2's PublishSubscribe MessagingPattern only. iceoryx2's RequestResponse API *MUST NOT* be used.
--

== UMessage Mapping

NOTE: A uProtocol message consists of _UAttributes_ and optional payload. The following sections define how these are mapped to/from iceoryx2 Services.

=== UAttributes

[.specitem,oft-sid="dsn~up-transport-iceoryx2-attributes-mapping~1",oft-needs="impl,utest",oft-tags="TransportLayerImpl"]
--
The value of an iceoryx2 Service that is used to convey a uProtocol message *MUST* have a https://docs.rs/iceoryx2/0.6.1/iceoryx2/service/builder/publish_subscribe/struct.Builder.html#method.user_header[user header] as defined in <<uAttributes Mapping to iceoryx2 user header>>.
--

==== uAttributes Mapping to iceoryx2 user header

[source,rust]
----
const MAX_FEASIBLE_UATTRIBUTES_SERIALIZED_LENGTH: usize = 1000; // choosing ~1000 u8s
                                                                // somewhat arbitrarily
                                                                // this should be confirmed

#[repr(C)]
#[derive(ZeroCopySend)]
struct UProtocolHeader {
    uprotocol_major_version: u8,
    uattributes_serialized: FixedSizeVec<u8, MAX_FEASIBLE_UATTRIBUTES_SERIALIZED_LENGTH>
}
----

.uAttributes Mapping to UProtocolHeader, iceoryx2 User Header
[%autowidth]
|===
| field | value

| `uprotocol_major_version`
a| *MUST* be set to a single byte representing the uProtocol major version (`0x01` for major version 1)

| `uattributes_serialized`
a| *MUST* be set to the bytes representing the protobuf encoding of the UAttributes object as defined by the link:../../up-core-api/uprotocol/v1/uattributes.proto[UAttributes Protocol Buffers definition]

|===

=== Payload Mapping

[.specitem,oft-sid="dsn~up-transport-iceoryx2-payload-mapping~1",oft-needs="impl,utest",oft-tags="TransportLayerImpl"]
--
An iceoryx2 `Sample` that is used to convey a uProtocol message *MUST* contain in its payload the unaltered value of the UMessage's _payload_ field.
--

[.specitem,oft-sid="dsn~up-transport-iceoryx2-payload-zero-copy~1",oft-needs="impl,utest",oft-tags="TransportLayerImpl"]
--
An iceoryx2 message that is used to convey a uProtocol message *MUST* be zero-copy and shared-memory compatible, in iceoryx2's sense:

* holds all of its data within itself: it uses no heap memory, and it has no pointer to anything outside itself and no handle to an outside resource, such as a file
* has the same memory representation wherever it is used
* organizes its internal structure without pointers
* has a lifetime of the entire program duration
--

The cleanest way to describe this is to say that the payload definition **MUST** have the link:https://docs.rs/iceoryx2/0.6.1/iceoryx2/prelude/trait.ZeroCopySend.html[`ZeroCopySend`] trait implemented for it if written in Rust.

That encapsulates the following additional properties in Rust:

* Rust `enum` and `struct` are marked  as `#[reprpass:[(C)]]`
* members don't implement `Drop` explicitly
* has a `'static` lifetime

== iceoryx2 Service Name Structure

NOTE: Message producers publish messages to the iceoryx2 inter-process communication using _ServiceNames_. Other clients can then use the same _ServiceName_ to receive the messages that are being published.

[.specitem,oft-sid="dsn~up-transport-iceoryx2-service-name~1",oft-needs="impl,utest",oft-tags="TransportLayerImpl"]
--
The ServiceName for sending a _Publish_ UMessage **MUST** consist of the following segments:

`up/[source.authority]/[source.ue_type_id]/[source.ue_instance_id]/[source.ue_version]/[source.resource]`

The ServiceName for sending a _Notification_ or _RPC Response_ UMessage **MUST** consist of the following segments:

`up/[source.authority]/[source.ue_type_id]/[source.ue_instance_id]/[source.ue_version]/[source.resource]/[sink.authority]/[sink.ue_type_id]/[sink.ue_instance_id]/[sink.ue_version]/[sink.resource]`

The ServiceName for sending an _RPC Request_ UMessage **MUST** consist of the following segments:

`up/[sink.authority]/[sink.ue_type_id]/[sink.ue_instance_id]/[sink.ue_version]/[sink.resource]`

Please refer to <<UUri Encoding Rules>> for details regarding the encoding of the `source` and `sink` UUris into the ServiceName's segments.

--

=== UUri Encoding Rules

The table below contains the rules for encoding a UUri's fields into an iceoryx2 ServiceName's segments.

[cols="2,2,6"]
|===
| ServiceName Segment
| UUri Field
| Encoding

|`authority`
|`authority_name`
a| The segment *MUST* contain the (UTF8) string representation of the 

1. name of the host/authority that the (local) uEntity is running on, if authority name is empty.
2. authority name, otherwise.

|`ue_type_id`
|`ue_type_id`
a| The segment *MUST* contain the (UTF8) string representation of the
upper-case link:https://www.rfc-editor.org/rfc/rfc4648#section-8[base16 encoding] of the uEntity type identifier with all leading `0` characters omitted.

|`ue_instance_id`
|`ue_instance_id`
a| The segment *MUST* contain the (UTF8) string representation of the
upper-case link:https://www.rfc-editor.org/rfc/rfc4648#section-8[base16 encoding] of the uEntity instance identifier with all leading `0` characters omitted.

|`ue_version`
|`ue_version_major`
a| The segment *MUST* contain the (UTF8) string representation of the
upper-case link:https://www.rfc-editor.org/rfc/rfc4648#section-8[base16 encoding] of the uEntity major version with all leading `0` characters omitted.

|`resource`
|`resource_id`
a| The segment *MUST* contain the (UTF8) string representation of the
upper-case link:https://www.rfc-editor.org/rfc/rfc4648#section-8[base16 encoding] of the resource identifier with all leading `0` characters omitted.

|===

|*Sink URI*

|===
====

====
[cols="2,8"]
|===
|*Source URI*

|*iceoryx2 ServiceName*
|`up/device1/CD/1/4/B`
|===
====

.Sending an RPC Response to a service client
====
[cols="2,8"]
|===
|*Source URI*
|`up://device1/CD/1/4/B`

|*Sink URI*
|`up:/3AB/4/3/0`

|*iceoryx2 ServiceName*
|`up/device1/CD/1/4/B/device1/3AB/4/3/0`
|===
====

.Subscribe to a specific Publish topic
====
[cols="2,8"]
|===
|*Source Filter*
|`up://device1/10AB/1/3/80CD`

|*Sink Filter*
|-

|*iceoryx2 ServiceName*
|`up/device1/10AB/1/3/80CD`
|===
====

.Subscribe to all Request messages for a given invokable method pointed to this uEntity
====
[cols="2,8"]
|===
|*Source Filter*
|`up://*/FFFF/FFFF/FF/FFFF`

|*Sink Filter*
|`up://device1/CD/1/4/B`

|*iceoryx2 ServiceName*
|`up/device1/CD/1/4/B`
|===
====

Note that subscribing to all Request messages pointed to this uEntity for a given invokable method
means that we **MUST** determine the source in order to send Response messages.

The source UUri **MUST** be determined by deserializing the `uattributes_serialized` in the UProtocolHeader
and then creating the appropriate fully-qualified ServiceName.

[[req-ssr-binding-iceoryx2-profile]]
=== The iceoryx2 binding follows one profile, stated for one release of iceoryx2

[.specitem,oft-sid="req~ssr-binding-iceoryx2-profile~1",oft-title="The iceoryx2 binding follows one profile, stated for one release of iceoryx2",oft-needs="uman",oft-tags="SafetyIceoryx2"]
--
*The iceoryx2 binding.*
The iceoryx2 binding is the binding that adapts the element to iceoryx2 (xref:interface.adoc#req-ssr-binding-scope[What a binding is, and the binding contract]).
iceoryx2 is its middleware.

*The profile.*
The iceoryx2 binding profile is the requirements that the up-rust SEooC requirement family allocates to the iceoryx2 binding: this one and the thirteen others that this list names.

* <<req-ssr-binding-depth-from-deployment,iceoryx2's service depth comes from deployment data>>
* <<req-ssr-binding-iceoryx2-event-ids,iceoryx2's event IDs come from the event service's static config>>
* <<req-ssr-binding-iceoryx2-panic-paths,iceoryx2's allowed panic paths are named, bounded and disclosed>>
* <<req-ssr-binding-iceoryx2-static-segments,On iceoryx2, every publisher has a static data segment>>
* <<req-ssr-binding-iceoryx2-expired-buffer,On iceoryx2, a receive route's retained budget fits twice in the expired-connection buffer>>
* <<req-ssr-binding-iceoryx2-arrival-reports,iceoryx2's arrivals are reported from its receive thread, and a failed notification is counted>>
* <<req-ssr-binding-iceoryx2-degradation-handler,On iceoryx2, each port has a degradation handler>>
* <<req-ssr-binding-iceoryx2-frame-layout,On iceoryx2, a frame is one header and one byte region, in a fixed layout>>
* <<req-ssr-binding-iceoryx2-frame-checks,On iceoryx2, a sample that is not a well-formed frame is refused before any of it is used>>
* <<req-ssr-binding-iceoryx2-frame-presence,On iceoryx2, an absent payload and a present empty payload stay apart>>
* <<req-ssr-binding-iceoryx2-frame-metadata,On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check>>
* <<req-ssr-binding-iceoryx2-frame-lifetime,On iceoryx2, a loan exposes only its metadata and its payload, and a receive view lives within its sample>>
* <<req-ssr-binding-iceoryx2-frame-wipe,On iceoryx2, the token of a loan that is not sent is wiped, and a sent frame is left as it was written>>

The duties of the binding contract bind the iceoryx2 binding beside the profile, as each of their statements says (xref:interface.adoc[binding interface], xref:lifecycle.adoc[binding lifecycle and waivers], xref:storage.adoc[binding storage and metadata admission] and xref:../route-observation.adoc[route observation, deadlines and TTL]).

*The release.*
The profile is stated for iceoryx2 0.9.3, with every crate of iceoryx2 at that release.
What its items say of iceoryx2 holds for that release.

*What the binding claims.*
The iceoryx2 binding *MUST NOT* claim the profile for a build in which a crate of iceoryx2 is at another release, or for a 32-bit target.
The record of the release that a build of the binding uses is stated in xref:../../safety/assurance.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures].

*Where the profile replaces the protocol chapter.*
For the iceoryx2 binding, and for it alone, the profile replaces four rules of <<classic-iceoryx2-v0-6-1,the v0.6.1 iceoryx2 transport protocol contract>> (xref:../../contract-generations.adoc#req-ssr-contract-transition[What a part declares and claims, and when a replacement takes effect]):

* `+dsn~up-transport-iceoryx2-protocol-version~1+`, the version of iceoryx2 that a transport uses, by the release of this profile;
* `+dsn~up-transport-iceoryx2-attributes-mapping~1+`, the user header of a service, by the header of <<req-ssr-binding-iceoryx2-frame-layout,On iceoryx2, a frame is one header and one byte region, in a fixed layout>>;
* `+dsn~up-transport-iceoryx2-payload-mapping~1+`, the payload of a sample, by the byte region of that item, which holds the frame's metadata before its payload;
* the rule after the chapter's examples that a responder determines a request's source by deserializing `+uattributes_serialized+` in the request's UProtocolHeader: for a request carried by this profile, the iceoryx2 binding takes that source from the frame's decoded metadata (<<req-ssr-binding-iceoryx2-frame-metadata,On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check>>), and still determines it, and builds the response's ServiceName from it, as the chapter states.

The replacement covers which release of iceoryx2 the iceoryx2 binding uses, how it carries a frame in a sample of a service of this profile, and where it finds a request's source, and nothing else.
The iceoryx2 binding *MUST NOT* claim conformance to those four rules for such a service.
--

[horizontal]
ID:: `+req~ssr-binding-iceoryx2-profile~1+`
ASIL:: B
Allocated to:: the iceoryx2 binding
Verification:: review (the binding's declaration and its qualification record: the release of every crate of iceoryx2 in each build for which the profile is claimed, and that build's target; that no claim of conformance names one of the four replaced rules of the protocol chapter for a service of this profile)

*Rationale.*
What iceoryx2 does on a path is a property of one release's source.
So the items state the binding's duties against one release, and a build that mixes releases has no one source that they were read in (source: https://github.com/eclipse-iceoryx/iceoryx2/tree/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4[iceoryx2 at the tag `+v0.9.3+`, commit `+6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4+`], the release that this profile names).
iceoryx2 itself opens a service's shared state only for a process of the same release (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2-cal/src/dynamic_storage/posix_shared_memory.rs#L264-L284[`+iceoryx2-cal/src/dynamic_storage/posix_shared_memory.rs+`, lines 264 to 284], where an opener of a service's dynamic storage is refused when the release recorded there differs from its own).

The chapter's mapping and this profile give a service different user headers and place a message's attributes differently, so one service cannot follow both: iceoryx2 opens an existing service only for a user header of the recorded type name and size (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/service/static_config/message_type_details.rs#L162-L172[`+iceoryx2/src/service/static_config/message_type_details.rs+`, lines 162 to 172], where the types that an opener requests are compared with those that a service records; https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/service/builder/publish_subscribe.rs#L310-L325[`+iceoryx2/src/service/builder/publish_subscribe.rs+`, lines 310 to 325], where an opener is refused an existing service whose recorded types fail that comparison).
The chapter's responder finds a request's source in that user header, which the profile's header does not hold, so that rule is named as well.
A replacement that names the four rules leaves every other rule of the chapter in force for the binding, and the whole chapter in force for every other transport implementation.

On a 32-bit target the index of the profile's one accepted panic path has 32 bits, which sends can exhaust (<<req-ssr-binding-iceoryx2-panic-paths,iceoryx2's allowed panic paths are named, bounded and disclosed>>), and iceoryx2 0.9.3 uses Rust's own 64-bit atomic type, which not every 32-bit target provides (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2-pal/concurrency-sync/src/atomic.rs#L114-L117[`+iceoryx2-pal/concurrency-sync/src/atomic.rs+`, lines 114 to 117], where iceoryx2's 64-bit atomic is that type).
So the profile is claimed for 64-bit targets only.

[[req-ssr-binding-depth-from-deployment]]
=== iceoryx2's service depth comes from deployment data

[.specitem,oft-sid="req~ssr-binding-depth-from-deployment~2",oft-title="iceoryx2's service depth comes from deployment data",oft-needs="impl,utest",oft-tags="SafetyIceoryx2"]
--
*The service's depth.*
A service's depth is the largest number of samples that the service lets a subscriber's queue hold, which iceoryx2 records with the service, and which every process that uses the service shares.

*From deployment data.*
The iceoryx2 binding *MUST* take each service's depth from deployment data, and create the service with it.

When it opens a service that already exists, it *MUST* compare that service's depth with the deployment's, and refuse a mismatch at setup, naming the route and both depths.
--

[horizontal]
ID:: `+req~ssr-binding-depth-from-deployment~2+`
ASIL:: B
Allocated to:: the iceoryx2 binding
Verification:: test (services created in both start orders; a stale depth refused)

*Rationale.*
iceoryx2 records with a service the largest queue that a subscriber of it may have, and lets a process open an existing service whose recorded value is at least the one that the process asks for (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/service/builder/publish_subscribe.rs#L373-L380[`+iceoryx2/src/service/builder/publish_subscribe.rs+`, lines 373 to 380], where a service is given that value, and https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/service/builder/publish_subscribe.rs#L484-L491[lines 484 to 491], where an opener is refused only an existing service whose value is smaller; https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/port/subscriber.rs#L226-L236[`+iceoryx2/src/port/subscriber.rs+`, lines 226 to 236], where a subscriber's own queue is bounded by it).
So two processes whose deployment data differ would share a service whose depth depends on which of them started first, and the binding compares the two depths itself and refuses any difference.

[[req-ssr-binding-iceoryx2-event-ids]]
=== iceoryx2's event IDs come from the event service's static config

[.specitem,oft-sid="req~ssr-binding-iceoryx2-event-ids~1",oft-title="iceoryx2's event IDs come from the event service's static config",oft-needs="impl,utest",oft-tags="SafetyIceoryx2"]
--
The iceoryx2 binding *MUST* read the event IDs from the event service's static config.

It *MUST* refuse at setup a route whose lifecycle events share the data ID, or whose data ID is above the service's `+event_id_max_value+`.
--

[horizontal]
ID:: `+req~ssr-binding-iceoryx2-event-ids~1+`
ASIL:: B
Allocated to:: the iceoryx2 binding
Verification:: test (the event IDs read from the event service's static config; a route whose lifecycle events share its data ID refused at setup; a data ID at the service's `+event_id_max_value+` admitted, and one above it refused at setup)

*Rationale.*
The event IDs, and the largest one that the service carries, belong to the event service's static config, not to the deployment data that xref:../../basics/configurations.adoc#req-ssr-config-validated[Deployment data is validated in full] checks (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/service/static_config/event.rs#L51-L65[`+iceoryx2/src/service/static_config/event.rs+`, lines 51 to 65] and https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/service/static_config/event.rs#L114-L138[lines 114 to 138], where the event service's static config holds its lifecycle event IDs and its largest event ID; https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/service/builder/event.rs#L593-L681[`+iceoryx2/src/service/builder/event.rs+`, lines 593 to 681], where an opener of an existing event service gets that service's own values).
So the binding reads them there and checks each route against them at setup.

[[req-ssr-binding-iceoryx2-panic-paths]]
=== iceoryx2's allowed panic paths are named, bounded and disclosed

[.specitem,oft-sid="req~ssr-binding-iceoryx2-panic-paths~5",oft-title="iceoryx2's allowed panic paths are named, bounded and disclosed",oft-needs="impl,utest",oft-tags="SafetyIceoryx2"]
--
*The accepted instance and the account.*
Under xref:interface.adoc#req-ssr-binding-no-panic[No panic on any peer input] and xref:lifecycle.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do], this item names the iceoryx2 binding's one accepted instance of a middleware panic path, with its five parts, the paths that are its known failures, and a path that a setup check excludes.
The binding's account of its middleware panic paths is stated in its qualification record, as xref:interface.adoc#req-ssr-binding-no-panic[No panic on any peer input] requires under "Each binding's account".

*The iceoryx2 release.*
The accepted instance applies only to the iceoryx2 binding built against iceoryx2 0.9.3, with every crate of iceoryx2 at that release (<<req-ssr-binding-iceoryx2-profile,The iceoryx2 binding follows one profile, stated for one release of iceoryx2>>).
On any other release of iceoryx2, the binding has no accepted panic path.

*The accepted instance: a history queue's index of pushes.*

* *The path.* A push into a publisher's history queue, at which the queue's index of pushes would overflow: a panic where the build checks integer overflow, and a wrap of the index otherwise.
* *Where it applies.* Every publisher of a service that keeps history.
* *What reaches it.* Only that overflow, which takes 2^64^ sends on one such publisher on a 64-bit target.
* *Its exclusions.* The index counts the publisher's own sends, and it lies in memory that the publisher's process allocates for itself, outside shared memory, so no peer input, death or restart and no write of a faulty peer into shared memory advances it, and an application reaches it only through that many sends.
* *Its bound.* A limit of the target: a 64-bit target, on which the index has 64 bits.
On a 32-bit target, a setup check: the binding *MUST* refuse a service that keeps history.

The binding *MUST* disclose this instance as a deviation in its qualification record (xref:../../safety/assurance.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures]).
The instance does not apply to a frame's drop, or to the deferred return that completes it.

*Declared middleware allocator exhaustion.*
Solely where a route admits a complete middleware permit and matching compiled-in waiver under xref:../../basics/resources.adoc#req-ssr-heap-declared[The heap class is declared, with no default], xref:lifecycle.adoc#req-ssr-waiver-scope[A waiver covers middleware and nothing else] and xref:interface.adoc#req-ssr-binding-no-panic[No panic on any peer input], process termination caused exclusively by allocator exhaustion at an exact declared permitted iceoryx2 connection-bookkeeping or lifecycle acquisition or resize operation is classified under the route's selected resource policy rather than as a known failure of the binding, unless a required recoverable-exhaustion, panic-free-cleanup or process-survival claim conflicts with it (xref:../../basics/resources.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name, and admitted or refused]).
That narrow resource-policy classification covers allocator exhaustion at those exact declared operations alone and grants no exemption to any non-allocator panic, error, logger, platform, mutex, refcount, socket, clock, `+close()+`, `+munmap()+` or sample-return failure path.

*Named paths that are known failures.*
Each of these middleware panic and non-allocator failure paths is a known failure of the binding:

* iceoryx2's per-port mutex, which guards each port of a service opened on iceoryx2's thread-safe service variant, and whose failure on lock or on unlock reaches a `+fatal_panic!+`.
A fault of the process-private lock reaches it, such as corrupted process memory, a recursion-count overflow or an OS error.
In stock iceoryx2 0.9.3 `+ipc_threadsafe+`, `+Sample::drop+` acquires that per-port mutex, reaches lock and unlock `+fatal_panic!+` paths, silently skips return when a connection key is absent or its `+sender_port_id+` mismatches, and logs `+RetrieveBufferFull+` without returning status; error, logger and platform closure on that path remain unestablished even while every publisher's data segment is static (<<req-ssr-binding-iceoryx2-static-segments,On iceoryx2, every publisher has a static data segment>>).
An unimplemented independent-return mechanism that splits sample return from subscriber traffic removes per-port mutex acquisition only from sample return: receive, send and connection-update paths still retain their applicable per-port mutex and unrelated non-allocator known failures, and no stock 0.9.3 repair or implemented independent-return mechanism is claimed here.
* iceoryx2's blocking send, which, on a service without safe overflow, reads the OS clock when it finds a receiver's queue full: its two `+unwrap+`s, which a failing clock call reaches, and its subtraction of two readings of the clock, which panics when the later reading is the earlier in time.
* The reference counts, private to the process, that iceoryx2 keeps of a publisher's samples: iceoryx2 reaches a `+fatal_panic!+` when it allocates a sample whose count is not zero, as when a buffer went back to its pool while still referenced, or was released twice.
* iceoryx2's `+unwrap+` on the descriptor of a socket that it has just created, which a failing `+fcntl+` reaches, as when other code in the same process closes the descriptor between iceoryx2's `+socket()+` and `+fcntl+` calls.
iceoryx2 creates such a socket when it connects a notifier to a listener, on a peer change among other times.
* `+close()+` or `+munmap()+` failing when iceoryx2 releases a departed peer's descriptor or mapping: a failing `+munmap()+`, and a `+close()+` that fails otherwise than by an interruption or an input/output error, reach a `+fatal_panic!+`.

*The clock check.*
The iceoryx2 binding *MUST* read at setup the OS clock that iceoryx2's blocking send reads, and *MUST* refuse setup, naming the clock, where that read fails.
A clock call that fails after setup still reaches the path of the blocking send, which stays a known failure.

*A path that a setup check excludes: the name of the global management segment.*
When a node is created, iceoryx2 puts the release's version in front of the suffix that the node's configuration gives the name of its global management segment, and reaches a `+fatal_panic!+` where the suffix cannot take it.
The iceoryx2 binding *MUST* refuse at setup, before it creates a node, a configuration whose suffix leaves no room for the release's version, naming the suffix.
That check makes the path unreachable for every node that the binding creates, and this item accepts no instance for it.

*Other paths.*
Every other middleware panic path that the binding can reach is a known failure of the binding as well, a path that a peer's input, death or restart can reach among them.
The binding's qualification record states its known failures (xref:../../safety/assurance.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures]), and what a deployment does with them is stated in xref:../../safety/elements/up-rust/assumptions-of-use.adoc#aou-seooc-iceoryx2-limits[A deployment on iceoryx2 accepts that binding's limits, and no known failure as one].

[[req-ssr-binding-iceoryx2-static-segments]]
=== On iceoryx2, every publisher has a static data segment

[.specitem,oft-sid="req~ssr-binding-iceoryx2-static-segments~2",oft-title="On iceoryx2, every publisher has a static data segment",oft-needs="impl,utest",oft-tags="SafetyIceoryx2"]
--
*The duty.*
The iceoryx2 binding *MUST* ensure that every publisher on each service that it uses for a route has a static data segment.

*The binding's checks.*
These four acts are necessary to the duty, and do not by themselves meet it:

* the binding *MUST* give each publisher that it creates a static data segment;
* it *MUST* record on each service that it creates that every publisher of the service has a static data segment;
* when it opens a service that already exists, it *MUST* require that record, and refuse the route at setup where the service does not carry it;
* at setup it *MUST* check every publisher that is present on the service, and refuse the route, naming the route and the publisher, where one of them has a data segment that is not static.

*What else the duty rests on.*
The first three acts hold every instance of the iceoryx2 binding to the duty, whenever it joins a service, and the fourth covers a publisher that another program created before the route was set up.
A publisher that a program other than the iceoryx2 binding adds to the service later is covered by the integrator's precondition that every such program creates its publishers with a static data segment (xref:../../safety/elements/up-rust/assumptions-of-use.adoc#aou-seooc-iceoryx2-limits[A deployment on iceoryx2 accepts that binding's limits, and no known failure as one]), and by no check of the binding.
So the binding *MUST* admit a route only where the deployment data of its service declares that precondition, and *MUST* refuse the route at setup, naming the service, where it does not.
The binding *MUST NOT* claim that every publisher of a service has a static data segment for a configuration that its qualification record does not state with the producer and environment premises on which that rests for publishers that other programs add later (xref:../../safety/assurance.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures]).
That the binding's own publisher has a static data segment does not show that the service's other publishers have one.
--

* *test*

*Rationale.*
A panic path inside the middleware is made unreachable by a setup check or by sizing (xref:interface.adoc#req-ssr-binding-no-panic[No panic on any peer input]).
A data segment that is not static can grow while its publisher runs, and a subscriber maps the added memory when it receives from it, in runtime mode: a mapping that fails there loses the sample, and a mapping that is given up can reach a panic when it is unmapped (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/port/details/data_segment.rs#L229-L300[`+iceoryx2/src/port/details/data_segment.rs+`, lines 229 to 300], where a subscriber opens and maps a publisher's segment of either kind; https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/port/details/receiver.rs#L440-L454[`+iceoryx2/src/port/details/receiver.rs+`, lines 440 to 454], where a sample of a dynamic segment whose mapping fails is given back and no sample is returned; https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2-bb/posix/src/memory_mapping.rs#L513-L519[`+iceoryx2-bb/posix/src/memory_mapping.rs+`, lines 513 to 519], where a failing `+munmap()+` reaches the panic).
That is dynamic segment growth and remapping of a publisher's backing, which differs from a subscriber establishing a bounded local view of a later-admitted publisher's already static data segment before exposing samples under xref:storage.adoc#req-ssr-binding-lent-storage[Lent storage is exclusive, disjoint and stable for as long as it is held], "Fixed before the transition".

iceoryx2 chooses the kind of segment for each publisher, from the publisher's own builder or the node's defaults, and has no setting of a service that forbids the other kind; a service carries attributes that its creator defines and that an opener can require, and it lists the kind of segment of each publisher present (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/service/port_factory/publisher.rs#L157-L172[`+iceoryx2/src/service/port_factory/publisher.rs+`, lines 157 to 172] and https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/service/port_factory/publisher.rs#L244-L261[lines 244 to 261], where a publisher's allocation strategy is chosen; https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/service/attribute.rs#L258-L287[`+iceoryx2/src/service/attribute.rs+`, lines 258 to 287], where a service's attributes are defined; https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/service/dynamic_config/publish_subscribe.rs#L48-L70[`+iceoryx2/src/service/dynamic_config/publish_subscribe.rs+`, lines 48 to 70], where each publisher's kind of segment is listed).
So the binding records the property on the service, requires it of a service that it opens, and reads each present publisher's kind there; for a program that joins later, only what that program does keeps the property, which is why the integrator's precondition carries it.

*Capacity variables and setup minimum.*
For each subscriber receiver, let `A` be the setup maximum publisher slots, `E` the effective retired-connection capacity, `Q` the per-connection submission-queue capacity in the one-channel publish-subscribe profile, and `H` the enforceable receiver-wide aggregate limit on all acquired samples sharing that receiver—counting in-progress acquisitions, physical and metadata refusals awaiting return, held and forgotten samples, pending returns and returns in service (<<req-ssr-binding-iceoryx2-frame-lifetime,On iceoryx2, a loan exposes only its metadata and its payload, and a receive view lives within its sample>>).
Where several routes share one subscriber receiver, the iceoryx2 binding *MUST* enforce their individual retained budgets within aggregate `H` (for example by bounding their sum by `H`); a per-route check alone does not establish `H`.
The iceoryx2 binding *MUST* refuse at setup a receive route unless `E >= 2H` holds for its subscriber receiver.
That inequality is a conservative setup minimum, not a tightness claim and not by itself proof of safe connection retirement.

*Stable incarnation identity and unique membership.*
The iceoryx2 binding *MUST* preserve stable connection-incarnation identity across replacement, failed creation and storage-key reuse:

* every live connection incarnation *MUST* belong to at most one active or retired membership at any time;
* an incarnation *MUST* transfer from active to retired membership at most once, with its active membership cleared before replacement;
* a failed replacement *MUST* leave the old incarnation retired once and its active slot vacant;
* sweep removal across retired entries *MUST* use the exact absolute inspected index and reconcile every membership;
* a reused numeric storage key *MUST NOT* authorize access to or removal of another incarnation (an unproven wrapping counter does not satisfy this rule).

*Preflight, construction schedule and bounded envelope.*
The iceoryx2 binding *MUST* serialize connection construction per subscriber and *MUST* reserve the active destination, connection, mapping, bookkeeping and fixed report state before any construction, eviction or acquisition:

* at full occupancy (`A + E` physical slots, counting active, retired, constructing, partially constructed, removed-not-yet-destroyed, sealed/destroying and failed-cleanup incarnations with no early decrement creating a vacancy), the binding *MUST* complete safe reclamation of an eligible retired victim before constructing a replacement (or, if an alternative constructs before reclamation completes, *MUST* explicitly declare and bound the extra `A + E + 1` slot table and `(A + E + 1)Q` plus completion-queue overlap envelope);
* the bounded envelope *MUST* account for `(A + E)Q` simultaneous submission-queue capacity and separate `(A + E)Kc_max` completion-queue capacity—where an independent-return endpoint establishes `Kc >= N` (such as checked `max(Q + B + 1, N)` with `B >= H` and validated setup-declared static publisher sample-slot count `N <= Nmax` across compatible sender and receiver endpoints)—together with `H` pre-reserved sample/lease/cell/fault records, per-slot atomic lifecycle and access state, mappings, descriptors and allocator overhead;
* reclamation *MUST* reclaim genuinely retired empty unborrowed connections first; where the declared QoS and loss policy permit, pressure *MAY* discard an unread unborrowed retired connection, and the binding *MUST* preserve the backing of every held, pending or forgotten borrowed owner;
* a full, missing or unproved reservation *MUST NOT* authorize entering a fatal overflow path, revoking a held sample, mutating route configuration or fabricating a receive result;
* a failed connection creation *MUST* retain its actual failure or deferred outcome and follow a finite retry and progress policy without an unbounded pending-incarnation list.

*Single-counted dropped-data-connection reporting.*
At each actual dropped-data-connection decision, the iceoryx2 binding *MUST* emit exactly one bounded, route- and incarnation-correlatable event through the runtime port's receive-failure interface, independent of logging level or filters (xref:interface.adoc#req-ssr-binding-arrival-reports[A binding reports each arrival within the latency that it declares, and each event as what it is]):

* the binding *MUST* reserve the event representation before the decision, and its callback and record path *MUST* be nonallocating, nonwaiting, nonreentrant and independent of locks that a stalled return could hold;
* the element counts that event once in `+receive_failed+` under xref:../route-observation.adoc#req-ssr-error-no-silent-loss[No silent loss, and each loss counted once], and the binding *MUST NOT* count it again;
* empty, safely completed resource reclamation is not automatically a dropped-data-connection event;
* the binding *MUST NOT* fabricate an unread-sample count, loss count or arrival count from a connection event;
* failed replacement-connection establishment retains its own receive-failure report (<<req-ssr-binding-iceoryx2-degradation-handler,On iceoryx2, each port has a degradation handler>>) and *MUST NOT* be conflated with an earlier dropped-data-connection event.

*Normal drainage, actual-completion charging and endpoint lifecycle.*
The iceoryx2 binding *MUST* drain existing queued data through normal physical, metadata, delivery and refusal admission after reserving owner and return capacity before acquisition:

* failed creation of a replacement connection *MUST NOT* indefinitely prevent drainage of existing connections;
* a maintenance receive *MUST NOT* silently consume or discard application samples;
* actual sample return ends only that sample's charge once, and safe connection retirement ends the separate connection and local-view charge once; a dormant retired connection *MAY* remain bounded and charged without holding a returned sample's credit, while service, port, node and startup infrastructure remain retained for the life of the process (xref:../runtime.adoc#req-ssr-release-none[Nothing is released in runtime mode]);
* for an independent-return endpoint over the stable `A + E` arena, the binding *MUST* use actual native lock-free bounded atomic operations, keep completion publication, `Acquire`-visible zero access count (`n = 0`) on a sealed endpoint, and `Release`-published `DONE` as distinct milestones, leave sealed-endpoint destruction and slot reuse to an explicit manager holding no protected traffic, return or observation dependency (never to a final sample or lease drop), and enforce cell-reuse and charging discipline: traffic authority observes `DONE` with `Acquire` before transitioning `DONE -> FREE` and alone transitions `FREE -> RESERVED` after reserving aggregate `H` capacity before writing new tenure fields, where `FREE` and `DONE` are uncharged, `RESERVED`, `LIVE`, `READY`, `RETURNING` and `FAULT_PENDING` are charged against aggregate `H`, and `DONE` ends the prior sample charge once while reclamation restores no second credit.

*Evidence before admission.*
The iceoryx2 binding *MUST NOT* claim conformance to this item for a build or configuration unless build and design evidence establishes every obligation above; neither a middleware resource permit nor `E >= 2H` alone supplies that evidence.

*Scoped replacement.*

[[req-ssr-binding-iceoryx2-arrival-reports]]
=== iceoryx2's arrivals are reported from its receive thread, and a failed notification is counted

[.specitem,oft-sid="req~ssr-binding-iceoryx2-arrival-reports~3",oft-title="iceoryx2's arrivals are reported from its receive thread, and a failed notification is counted",oft-needs="impl,utest",oft-tags="SafetyIceoryx2"]
--
*Arrivals.*
An arrival, and a binding's arrival latency, are what xref:../route-observation.adoc#req-ssr-qos-deadline[Deadlines are monitored] defines under "Terms".
This item specializes xref:interface.adoc#req-ssr-binding-arrival-reports[A binding reports each arrival within the latency that it declares, and each event as what it is] for the iceoryx2 binding, and that item holds beside it.
Where the iceoryx2 binding declares established arrival-reporting capability with a finite arrival latency `L` for a receive route, it *MUST* report an arrival to the element within `L` for every arrival on that route, also while a data connection of the route has failed.
One report *MAY* stand for every arrival since the report before it.
The binding *MUST NOT* report an arrival without evidence that a frame reached the route's queue since the previous report, or that the queue's overflow policy discarded one since then.

*From the receive thread.*
Where arrival-reporting capability is established on the receive thread, the binding *MUST* report arrivals from that thread, and its declared arrival latency `L` is that thread's period plus its established finite pass bound over the full admitted path.
An unbounded permitted middleware allocator wait on a receive pass, a worker period paired with an unbounded pass, completion publication, a stale ownership snapshot, a wake hint or an independent sample-return split alone establishes no finite arrival latency `L`.

*What the binding observes.*
On each pass where arrival reporting is declared, the receive thread takes as evidence of an arrival only an observation that establishes a frame that reached the route's queue since the previous report, or a discard by the queue's overflow policy since then.
Two observations do so:

* the route's queue turning non-empty since the previous pass;
* a drained notification of the route's data ID, together with a sample that the binding establishes reached the queue since the previous report, whether it is still in the queue or was taken from it.

A notification is a wake hint.
The binding *MUST NOT* report an arrival on a drained notification alone, and *MUST NOT* take a sample that was in the queue at the previous report as evidence together with a later notification.
A notification whose frame did not reach the queue, such as one of a publisher whose data connection is missing, is no evidence of an arrival.
Where arrival-reporting capability is declared, neither observation limits the duty of the clause "Arrivals": an arrival that neither shows is still owed its report.

*Unavailable arrival capability and QoS consequences.*
Where no separate mechanism establishes a finite arrival latency `L` for every arrival over the full admitted path of a receive route (including a pull configuration whose receive pass can wait in a declared middleware allocation domain), the iceoryx2 binding *MUST* declare arrival-reporting capability unavailable for that route (xref:interface.adoc#req-ssr-binding-arrival-reports[A binding reports each arrival within the latency that it declares, and each event as what it is], "The declared latency").
Under unavailable arrival capability:

* any declared deadline on that route is refused at setup under xref:../runtime.adoc#req-ssr-qos-invalid-refused[Meaningless QoS is refused at setup];
* E2E detector receive routes (topic receive, notification receive and RPC server request) require a deadline and cannot use `+event_only+`, and are therefore refused at setup at every integrity level and in every strict state;
* a non-detector ASIL receive route declaring neither a deadline nor `+event_only+` is refused in the Enforce and Locked states and reported as a finding in the Report state;
* an E2E RPC-client response route is not a detector route: declaring explicit `+event_only+` with no deadline clears this QoS setting gate, while declaring neither is refused in the Enforce and Locked states at every integrity level and reported in the Report state;
* an ordinary non-E2E QM receive route declaring explicit `+event_only+` with no deadline clears this QoS setting gate subject to all other admission conditions.

Declaring arrival capability unavailable lifts no failed-read, connection-failure, dropped-connection or failed-notification-call reporting duty of xref:interface.adoc#req-ssr-binding-arrival-reports[A binding reports each arrival within the latency that it declares, and each event as what it is], <<req-ssr-binding-iceoryx2-degradation-handler,On iceoryx2, each port has a degradation handler>>, <<req-ssr-binding-iceoryx2-expired-buffer,On iceoryx2, a receive route's retained budget fits twice in the expired-connection buffer>> or the clause below.

*A failed notification call.*
This clause applies where, after a send on a route, the sending side of the binding notifies the route's listeners with a notification call.
For that call, the queue holds samples when, at the beginning of the call, the queue of any recipient of that send is non-empty.
The binding *MUST* establish that by a queue-state observation that it declares, and *MUST NOT* take a wake hint for one.
When the queue holds samples and the call returns an error, the binding *MUST* increment the sending route's `+notification_call_failed+` counter exactly once for that call.
The counter's unit is the failed notification call: the binding *MUST NOT* count a sample, a listener or a read by it, and an error of the call shows neither that no listener was notified nor that a sample was lost (xref:interface.adoc#req-ssr-binding-arrival-reports[A binding reports each arrival within the latency that it declares, and each event as what it is], "Each event as what it is").
When the call returns the number of listeners that it notified, and an attempt on one listener reports a failure, the binding *MUST* record that failure as a `+listener_attempt_failed+` diagnostic, apart from the counter, and *MUST NOT* count the call as failed.
Where the binding cannot establish whether the queue holds samples on a route, it *MUST NOT* declare this count for that route, and the route is admitted or refused as its declared settings require (xref:interface.adoc#req-ssr-binding-qos-capability[A binding honors or refuses each declared setting]).

*Scoped replacement.*
Revision 3 of this item replaces revision 2 of this item for the iceoryx2 binding across all receive routes.

*Rationale.*
What every binding owes for its arrival reports, and why, is stated in xref:interface.adoc#req-ssr-binding-arrival-reports[A binding reports each arrival within the latency that it declares, and each event as what it is]; when, and on which evidence, the iceoryx2 binding reports an arrival is its own to state.
The duty covers every arrival, and not only those that one observation shows, for the reason that xref:../route-observation.adoc#req-ssr-qos-deadline[Deadlines are monitored] gives under "What is counted".
A notification says that a send was made, not that its frame is in this route's queue, so it is evidence of an arrival only together with a frame that the queue newly holds; a sample that was already there shows nothing new.

_A failed notification call._
iceoryx2's notification call returns the number of listeners that it notified: a listener whose connection reports that it is disconnected is removed, a failure on another listener's connection is logged, neither makes the call return an error, one error is raised before any listener is tried, and two can be raised after all were (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/port/notifier.rs#L499-L569[`+iceoryx2/src/port/notifier.rs+`, lines 499 to 569], where a notification call reaches its listeners and returns).
So neither the count nor an error of the call says whether a particular listener was notified, or whether a frame was received.
Where the call fails while a recipient's queue already holds samples, a listener that the call did not reach has no other sign of the new frame, since the queue did not turn non-empty; the count keeps that failed call from being silent, and infers neither which listener was reached nor which arrival was reported.

[[req-ssr-binding-iceoryx2-degradation-handler]]
=== On iceoryx2, each port has a degradation handler

[.specitem,oft-sid="req~ssr-binding-iceoryx2-degradation-handler~2",oft-title="On iceoryx2, each port has a degradation handler",oft-needs="impl,utest",oft-tags="SafetyIceoryx2"]
--
*The handler.*
The iceoryx2 binding *MUST* install, at setup, a degradation handler of its own for each port that it creates, and *MUST* apply its configured degradation policy through that handler.
Where iceoryx2 offers a degradation callback for a kind of port, the binding *MUST* attach its handler to it; for a kind of port on which iceoryx2 offers none, the binding *MUST* learn by another means that it declares of each connection that cannot be set up, and *MUST* deliver that failure to its handler.

*A receive route whose data connection could not be set up.*
The binding *MUST* report to the element, as a receive failure, each data connection that a receive route's subscriber could not set up, whether or not iceoryx2 returns an error for it; this specializes xref:interface.adoc#req-ssr-binding-arrival-reports[A binding reports each arrival within the latency that it declares, and each event as what it is], "Failed reads", which holds beside it, and the element counts the report as xref:../route-observation.adoc#req-ssr-error-no-silent-loss[No silent loss, and each loss counted once] states under "Pull bindings".
That report replaces no arrival report: <<req-ssr-binding-iceoryx2-arrival-reports,iceoryx2's arrivals are reported from its receive thread, and a failed notification is counted>> holds while the connection is missing, and a notification of the publisher whose connection is missing is no evidence of an arrival.

*A send route whose data connection could not be set up.*
The binding *MUST* count, once for each failure and on the sending route, under a counter that names the cause, each failure of the route's publisher to set up a data connection to a subscriber.

*A send that finds a connection corrupted.*
When a send operation finds its retained connection to a recipient corrupted, the binding *MUST* apply the configured degradation policy to it and *MUST* emit one `+corrupted_connection+` event on the sending route, keyed by the send operation, the recipient and the generation of the connection (not counted in `+receive_failed+`, as xref:../route-observation.adoc#req-ssr-error-no-silent-loss[No silent loss, and each loss counted once], "Sending-side connection faults", states).
A connection's generation changes each time the connection to that recipient is set up again.

* The binding *MUST* emit one event for one key, however often the operation observes the corruption.
A later send operation that finds the same connection corrupted is another event, also where the generation has not changed.
* The binding *MUST* keep the operation's result for the recipients that it reached, and *MUST NOT* repeat a send operation that reached some of its recipients.
* The binding *MUST NOT* classify the recipient that the operation left out as a sample loss, unless a separate observation of that recipient or of its queue establishes the loss.

While a subscriber's connection to one publisher is missing, a notification of that publisher's send is followed by no frame in the queue, so that notification is no evidence of an arrival, while frames of the route's other publishers still arrive and are owed their reports; the counted receive failure tells the application that one publisher's frames do not reach the route.

A send that finds one recipient's connection corrupted still reaches its other recipients, and iceoryx2 keeps the corrupted connection (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/port/details/sender.rs#L282-L318[`+iceoryx2/src/port/details/sender.rs+`, lines 282 to 318], where a corrupted connection goes to the handler, and https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/port/details/sender.rs#L369-L412[lines 369 to 412], where a send goes on to the other recipients).
So repeating the send would deliver the frame twice to the recipients that it reached, and the sender does not observe the queue of the recipient that it left out.

[[req-ssr-binding-iceoryx2-frame-layout]]
==== On iceoryx2, a frame is one header and one byte region, in a fixed layout

[.specitem,oft-sid="req~ssr-binding-iceoryx2-frame-layout~2",oft-title="On iceoryx2, a frame is one header and one byte region, in a fixed layout",oft-needs="impl,utest",oft-tags="SafetyIceoryx2"]
--
*A sample, the header and the byte region.*
An iceoryx2 sample is what a publish-subscribe service carries: a header of iceoryx2's own, then a user header, then a payload.
On the iceoryx2 binding, a sample's user header is the frame's _header_, and its payload is a sequence of bytes, the _byte region_.

*One frame, one sample.*
The iceoryx2 binding *MUST* place each frame in one sample: its header as the sample's user header, and its metadata, the gap, its payload and the tail in the byte region.
The binding *MUST* use for frames only services whose user header is the frame's header and whose payload is a sequence of bytes.
The layout that this item states is the iceoryx2 binding's envelope (xref:interface.adoc#req-ssr-binding-scope[What a binding is, and the binding contract]).

*The header.*
The binding *MUST* give the header a length of 40 bytes, an alignment of 8 and no byte of padding.
It *MUST* write each of its fields as an unsigned integer, in the native byte order of the processor that it runs on, at the place that this table gives:

[cols="1,1,4",options="header"]
|===
| Bytes | Width | Field

| 0 | 1 | The version of the header: `00`
| 1 to 7 | 7 | Reserved: written as `00`
| 8 to 15 | 8 | The length of the metadata
| 16 to 23 | 8 | The offset of the payload, from the byte region's first byte
| 24 to 31 | 8 | The length of the payload
| 32 to 39 | 8 | The alignment of the payload, a power of two
|===

*The metadata's byte order.*
In a frame of this profile, the numbers inside the metadata are least significant byte first, whatever the header's byte order: the metadata format that the route's selected wire states (xref:../wires/README.adoc#req-ssr-wire-metadata-format[A wire states the format of its frame metadata, and decodes it]) puts them so, and that wire decodes them (<<req-ssr-binding-iceoryx2-frame-metadata,On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check>>).
For frames of this profile, the decoding required by xref:../wires/README.adoc#req-ssr-wire-metadata-format[A wire states the format of its frame metadata, and decodes it] replaces the iceoryx2 binding's duty in revision 1 of this item to read the metadata's numbers in their specified byte order, whatever the header's byte order.

*Where each part stands.*
The metadata starts at the byte region's first byte, and its length is the header's metadata length.
The payload starts at the offset that the header gives, and its length is the header's payload length.
The bytes between the metadata's end and the payload's offset are the _gap_, and the bytes after the payload's end, to the end of the byte region, are the _tail_.
The binding *MUST* write each length, the offset and the alignment as the parts stand.

*The payload's place.*
The binding *MUST* choose the offset so that the payload's first byte is at an address, where the binding maps the sample, that is a multiple of the alignment, with a gap shorter than the alignment.

*The version.*
This item states version 0 of the header.
The version numbers this layout of the header: it is neither a release of iceoryx2 nor a version of uProtocol.
The binding *MUST* write `00`, and a sample whose header has another version is no frame of this profile's layout.

*Reserved bytes, the gap and the tail.*
The binding *MUST* write the reserved bytes, the gap and the tail as `00`.
The gap and the tail carry no meaning, and neither is part of the frame.
The binding *MUST NOT* rely on what the gap or the tail holds, in a check, a comparison or any other way.
--

[[req-ssr-binding-iceoryx2-frame-checks]]
==== On iceoryx2, a sample that is not a well-formed frame is refused before any of it is used

[.specitem,oft-sid="req~ssr-binding-iceoryx2-frame-checks~3",oft-title="On iceoryx2, a sample that is not a well-formed frame is refused before any of it is used",oft-needs="impl,utest",oft-tags="SafetyIceoryx2"]
--
*What is refused, and in which order.*
A received sample is checked in this order, and refused at the first check that it fails.
The iceoryx2 binding *MUST* make the first seven of these checks; the eighth is the element's (<<req-ssr-binding-iceoryx2-frame-metadata,On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check>>):

. its header's version is not `00`;
. one of its reserved bytes is not `00`;
. one of the four numbers of its header is greater than the largest size that the binding can address;
. its alignment is zero, not a power of two, or less than the receiving route's declared payload alignment;
. its payload's offset is before the end of its metadata, which ends at the metadata length that its header gives;
. its metadata length is greater than the receiving route's declared limit for metadata, its payload length is greater than the receiving route's declared limit for a payload, its byte region is longer than the receiving route's largest frame, or its payload's offset plus its payload's length overflows or ends past the end of its byte region;
. its payload's first byte is not at an address, where the binding maps the sample, that is a multiple of the alignment that its header gives;
. its metadata does not decode in the metadata format of the route's selected wire, which the element has that wire decode.

A sample whose byte region is within the receiving route's largest frame is still refused at the sixth check where its metadata length or its payload length is greater than the route's limit for it.

*The byte region's length, and a route's largest frame.*
A route's _largest frame_ is the length of the byte region that the route's longest frame needs: its declared limit for metadata, plus its declared limit for a payload, plus one less than its declared payload alignment.
The byte region's length is the one that iceoryx2 gives for the sample, and the binding *MUST NOT* rely on it before the sixth check has compared it with the receiving route's largest frame.

*Before any of it is used.*
The binding *MUST* make the first seven checks with arithmetic that cannot overflow, before it forms any range from the header, and *MUST* read no byte of the byte region before they pass.
These checks stand beside the binding's duty to keep a held frame at an address with the route's alignment (xref:storage.adoc#req-ssr-binding-lent-storage[Lent storage is exclusive, disjoint and stable for as long as it is held]).

*What a refusal becomes.*
For a sample that one of the first seven checks refuses, or whose frame the element refuses in its admission of the metadata (<<req-ssr-binding-iceoryx2-frame-metadata,On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check>>), the binding *MUST* complete the refusal decision immediately without allocating or waiting, and *MUST* return the whole sample to iceoryx2 inline if non-waiting or hand the whole sample immediately into its already pre-reserved return representation under xref:lifecycle.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do] and xref:../runtime.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]; the refused sample remains charged until actual return to iceoryx2 completes.
It *MUST* count a refusal by one of the first seven checks once, as a refused layout, and *MUST NOT* count a sample whose frame the element refuses: the element counts that refusal once, as <<req-ssr-binding-iceoryx2-frame-metadata,On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check>> states.
It *MUST* then take the next sample, within the work that the receive call is allowed (xref:lifecycle.adoc#req-ssr-binding-bounded[A binding bounds its own work and its waits]); each refused sample is one unit of that work, whichever part refused it.
It *MUST NOT* let any part of a sample that one of the first seven checks refuses reach the element, a wire or an application.
On a receive route that takes the copy route, one thing is excepted from that rule: the element's acquisition of the sample's header and metadata into storage of its own, before the first seven checks, as xref:../integrity.adoc#req-ssr-integrity-zero-copy[Zero-copy only from a writer at or above the reader], "Admission on the copy route", states.
That acquisition is a bounded raw copy within the frame's extent, and nothing of it is decoded, admitted, delivered or forwarded before the first seven checks have passed on the acquired header.
A refusal by one of those checks keeps its cause and its one count, and ends the sample's admission before its metadata is decoded.
Once the first seven checks have passed, the binding adopts the shared hand-over contract of xref:storage.adoc#req-ssr-binding-metadata-admission[For lending bindings that separate physical checks from metadata hand-over, the element admits metadata once in fixed order] and hands on only the metadata's extent and the payload length that the header gives, for the element's admission of the metadata (<<req-ssr-binding-iceoryx2-frame-metadata,On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check>>); that hand-over admits no frame.
It *MUST NOT* let any part of a sample whose frame the element refuses reach a wire's decoding of the payload or an application.
For a sample that the eighth check refuses, revision 3 of this item replaces the iceoryx2 binding's revision-1 duty to let no part of it reach the element or a wire (handing on only the metadata's extent and header payload length for element admission) and transfers to the element the refusal count that revision 2 of this item assigned to the iceoryx2 binding; the transfer takes effect, and a composition of an element and an iceoryx2 binding that stand on different sides of it is refused, as <<req-ssr-binding-iceoryx2-frame-metadata,On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check>> states in "Element and binding generations".
That a refusal causes no panic is stated in xref:interface.adoc#req-ssr-binding-no-panic[No panic on any peer input].

[[req-ssr-binding-iceoryx2-frame-presence]]
==== On iceoryx2, an absent payload and a present empty payload stay apart

[.specitem,oft-sid="req~ssr-binding-iceoryx2-frame-presence~2",oft-title="On iceoryx2, an absent payload and a present empty payload stay apart",oft-needs="impl,utest",oft-tags="SafetyIceoryx2"]
--
*Presence.*
Whether a frame has a payload is what its metadata says, in the metadata format of the route's selected wire (xref:../wires/README.adoc#req-ssr-wire-metadata-format[A wire states the format of its frame metadata, and decodes it]): a frame whose metadata has a payload encoding has a payload, and a frame without one has none.
The header's payload length gives only the length.

*An absent payload.*
The iceoryx2 binding *MUST* write a payload length of zero for a frame that the element sends without a payload, and *MUST NOT* give the element a payload extent to write for it.
The binding *MUST* report a received frame that the element admits, and that has no payload encoding, as a frame with no payload, never as a payload of length zero, and *MUST NOT* deliver bytes for it.
A received frame that has no payload encoding while its header gives a payload length other than zero is refused by the element before it is reported (<<req-ssr-binding-iceoryx2-frame-metadata,On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check>>).
Revision 2 of this item retires the iceoryx2 binding's revision-1 duty to report such a frame as a frame with no payload; it takes effect in the composition that <<req-ssr-binding-iceoryx2-frame-metadata,On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check>> names in "Element and binding generations".

*A present empty payload.*
The binding *MUST* write a payload length of zero for a frame whose payload is present and empty, and *MUST* report it as a present payload of length zero.

[[req-ssr-binding-iceoryx2-frame-metadata]]
==== On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check

[.specitem,oft-sid="req~ssr-binding-iceoryx2-frame-metadata~3",oft-title="On iceoryx2, the binding carries the metadata unchanged, and its identity is the element's to check",oft-needs="impl,utest",oft-tags="SafetyIceoryx2,SafetyUpRustCore"]
--
*Whose bytes.*
The metadata is the frame's metadata, which the element writes in the metadata format of the route's selected wire (xref:../wires/README.adoc#req-ssr-wire-metadata-format[A wire states the format of its frame metadata, and decodes it]).
The header gives its length, and the iceoryx2 binding *MUST* carry it unchanged, from the element that writes it to the element that receives it.

*What the sample-layout items rely on in that format.*
Of the fields that the selected wire states for that format (xref:../wires/README.adoc#req-ssr-wire-metadata-format[A wire states the format of its frame metadata, and decodes it], "The format"), the six sample-layout items of this profile rely on these:

* the prefix: the element's identity check below;
* the frame's source: the peer identity below;
* the byte order of its numbers: <<req-ssr-binding-iceoryx2-frame-layout,On iceoryx2, a frame is one header and one byte region, in a fixed layout>>;
* whether the frame has a payload: <<req-ssr-binding-iceoryx2-frame-presence,On iceoryx2, an absent payload and a present empty payload stay apart>>;
* the token: <<req-ssr-binding-iceoryx2-frame-wipe,On iceoryx2, the token of a loan that is not sent is wiped, and a sent frame is left as it was written>>.

*The hand-over.*
After the first seven checks of <<req-ssr-binding-iceoryx2-frame-checks,On iceoryx2, a sample that is not a well-formed frame is refused before any of it is used>> have passed, the iceoryx2 binding *MUST* hand the element the frame's metadata extent and the payload length that its header gives, and no byte of its payload, and *MUST* leave every comparison of the metadata's identity to the element.
The hand-over is not a delivery to an application, and that its metadata decodes does not make a frame the route's.
Within the same receive step, the element *MUST* admit or refuse the frame as the clause "The element's admission" states, and *MUST* hand its verdict back to the binding, with, for a frame that it admits, whether the frame has a payload and the frame's source.
For a frame that the element refuses, the binding *MUST* immediately transfer the whole refused sample into its already pre-reserved return representation (or complete non-waiting inline return) once without counting it again—the element's single count stands—keeping the sample charged until actual return to iceoryx2 completes; the same-step verdict, single count and ownership hand-off do not await physical return completion, and on a pull route the binding advances to the next sample within its work bound while genuine capacity remains without fabricating a receive error (<<req-ssr-binding-iceoryx2-frame-checks,On iceoryx2, a sample that is not a well-formed frame is refused before any of it is used>>; xref:lifecycle.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]; xref:../runtime.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]).

*The element's admission.*
Before a frame reaches its route, the element *MUST* perform the five-step common metadata admission, ordering, pull-route accounting and non-repetition duties of xref:storage.adoc#req-ssr-binding-metadata-admission[For lending bindings that separate physical checks from metadata hand-over, the element admits metadata once in fixed order], where the first step (metadata decode) is the eighth check of <<req-ssr-binding-iceoryx2-frame-checks,On iceoryx2, a sample that is not a well-formed frame is refused before any of it is used>>.
Revision 3 of this item transfers to the element two duties of the iceoryx2 binding: the count of a frame whose metadata does not decode (revision 2 of <<req-ssr-binding-iceoryx2-frame-checks,On iceoryx2, a sample that is not a well-formed frame is refused before any of it is used>>); and, for a frame with no payload encoding and a nonzero header payload length, refusal and counting in place of reporting a frame with no payload (revision 1 of <<req-ssr-binding-iceoryx2-frame-presence,On iceoryx2, an absent payload and a present empty payload stay apart>>).

*What the binding takes from it.*
From the element's hand-back the binding *MUST* take nothing but whether the frame has a payload (<<req-ssr-binding-iceoryx2-frame-presence,On iceoryx2, an absent payload and a present empty payload stay apart>>) and the frame's source.
It *MUST* take the frame's peer identity from that source; what makes an identity stable, and how its incarnation rises, is stated in xref:interface.adoc#req-ssr-binding-peer-identity[Peer identity is stable, and incarnations rise].

*Element and binding generations.*
The duties that this revision, revision 3 of <<req-ssr-binding-iceoryx2-frame-checks,On iceoryx2, a sample that is not a well-formed frame is refused before any of it is used>> and revision 2 of <<req-ssr-binding-iceoryx2-frame-presence,On iceoryx2, an absent payload and a present empty payload stay apart>> move between the iceoryx2 binding and the element take effect in a composition whose element and iceoryx2 binding both declare a revision of the specification that holds these revisions or later ones (xref:../../contract-generations.adoc#req-ssr-contract-transition[What a part declares and claims, and when a replacement takes effect], "The declaration").
The element and the iceoryx2 binding *MUST* each make a composition with a part of the other kind whose declared revision of the specification holds earlier revisions of these items either fail to build or be refused before runtime mode, naming that part.

Allocated to:: the iceoryx2 binding; the element, for its admission of a frame's metadata as the clause "The element's admission" states (having the route's selected wire decode it, and the checks of its fields, of its presence against the payload length that the header gives, of its identity and of a receive's filters, in that order, once and before any of the frame reaches a wire's decoding of the payload or an application), for delivering no frame to a receive whose filters its metadata does not match, for refusing, and returning or counting once, a frame that one of those checks refuses, and, on a route that the binding serves by pull, counting it once and not returning it as the error of the receive call, for handing its verdict, the frame's presence and its source back to the binding, and for its part in refusing a composition across the transfer
Verification:: test, fault-injection, review
* *test*
** Metadata carried byte for byte from sender to receiver.
** A frame whose metadata does not decode, and one whose prefix names a metadata layout that the selected wire's format does not define: refused once by the element at the first check, as refused metadata, with no presence taken from it, and not counted by the binding.
** A frame whose header passes the first seven checks of <<req-ssr-binding-iceoryx2-frame-checks,On iceoryx2, a sample that is not a well-formed frame is refused before any of it is used>>, whose metadata passes the first two metadata checks (decoding and required fields), and whose metadata names no payload encoding while its header gives a payload length of 1: refused once by the element at the third check as `+payload_presence_extent_mismatch+`, given back to iceoryx2 once, with no TTL count, payload processing, forwarding or answer; the same frame also expired, and the same frame whose metadata also names a wire that the route does not admit: the same refusal and count.
** A frame with a present payload of length zero and encoding identifier `0`: passes the second and third metadata checks (and is admitted to its route only when the remaining identity and filter checks pass as well).
** A frame whose metadata names another wire, another payload family or another metadata layout that the selected wire's format defines, with metadata that decodes: handed to the element, and refused there at the fourth check, before its payload is decoded.
** A frame whose metadata matches the filters of one receive of the route and not of another: delivered to the first only.
** A frame whose header passes the first seven checks of <<req-ssr-binding-iceoryx2-frame-checks,On iceoryx2, a sample that is not a well-formed frame is refused before any of it is used>>, whose metadata passes the first two metadata checks (decoding and required fields), and whose metadata names no payload encoding while its header gives a payload length of 1, on a route with a deadline: on a pull route, recorded as an arrival when it is read, then refused; where the binding serves a route by push, refused at delivery and recorded as no arrival; counted once in either case.
** An RPC request whose metadata decodes: the frame's source taken from the element's hand-back, and the response's ServiceName built from it.
** A frame admitted to its route and taken later: its metadata not admitted again.
** Each composition of an element and an iceoryx2 binding that stand on different sides of the transfer, in both directions: refused before runtime mode, naming the part, or not buildable.
* *fault-injection*: metadata that does not decode, in a frame that passes every other check, sent by a faulty peer: refused and counted once by the element, and not counted by the binding.
* *review*: at source level, that the binding hands the metadata on only after the first seven checks, takes nothing from the element's hand-back but presence and the source, decides nothing from the identity that the metadata names, and takes the frame's peer identity from the source; that the element makes its admission once, in the stated order, before the frame reaches its route; and the mechanism by which each part makes a composition across the transfer fail to build or be refused before runtime mode.

*Rationale.*
The metadata says what the frame is: the route's selected wire states its format and decodes it, and the element is the one that knows which wires the route admits.
The binding takes only what it needs to hand the frame over, so that no second reading of the identity stands beside the element's.
The element has the selected wire decode the metadata, so it also refuses and counts a frame whose metadata does not decode, and no such frame is counted twice.
Presence is compared with the header's payload length before the identity and the filters, so that a malformed frame is refused once, whatever else its metadata names.

[[req-ssr-binding-iceoryx2-frame-lifetime]]
==== On iceoryx2, a loan exposes only its metadata and its payload, and a receive view lives within its sample

[.specitem,oft-sid="req~ssr-binding-iceoryx2-frame-lifetime~3",oft-title="On iceoryx2, a loan exposes only its metadata and its payload, and a receive view lives within its sample",oft-needs="impl,utest",oft-tags="SafetyIceoryx2"]
--
*A loan.*
A loan is a sample that the iceoryx2 binding holds from a publisher, to be written, from the moment iceoryx2 lends it to the moment the binding publishes it or gives it back.

*Transmit.*
The iceoryx2 binding *MUST* fix the metadata's length, the payload's offset, the payload's length and the alignment when it creates a loan, and *MUST* write the header itself.
What it gives the element to write *MUST* be the metadata's extent and, for a frame with a payload, the payload's extent, and nothing else.
The two extents *MUST NOT* move or grow while the loan is held, and the metadata's extent *MUST NOT* shrink.
The payload's extent *MAY* shrink, and only when the element shortens it (shortenable transmit loans under xref:storage.adoc#req-ssr-binding-loan-sizing[A lending binding declares whether a transmit loan's payload extent can be shortened]).
The binding *MUST* then write the payload's new length into the header (<<req-ssr-binding-iceoryx2-frame-wipe,On iceoryx2, the token of a loan that is not sent is wiped, and a sent frame is left as it was written>>).

*Publishing.*
The binding *MUST* accept the element's record of the metadata that it wrote only where that record covers exactly the metadata's extent, with the token inside it where there is one (<<req-ssr-binding-iceoryx2-frame-wipe,On iceoryx2, the token of a loan that is not sent is wiped, and a sent frame is left as it was written>>).
It *MUST* publish a loan only on the route that it was lent for, and only once that record is made and both facts of xref:storage.adoc#req-ssr-binding-initialized-extent[A sample's bytes are initialized before a path needs them, each by the part that owns it] hold for each byte of the loan's byte region: the element's, for the metadata's and the payload's extents, and its own, for every other byte.

*Initialized extents.*
The byte region of a loan is its L elements, L being the element count of the byte-sequence loan.
The binding *MUST* declare all L elements as the required-initialized extent of its publish path, whatever payload length the header gives, and all L elements of a received sample as the delivered-initialized extent of its receive path, on the basis of iceoryx2's receive contract for the profile's service type (xref:storage.adoc#req-ssr-binding-initialized-extent[A sample's bytes are initialized before a path needs them, each by the part that owns it]).
Writing a shorter payload length into the header, or giving a shorter extent to write, does not shorten L.
The header, its reserved bytes included, is the binding's, which writes each of its fields (<<req-ssr-binding-iceoryx2-frame-layout,On iceoryx2, a frame is one header and one byte region, in a fixed layout>>), and the bytes of the byte region are of these classes:

* the metadata's extent: the element's, whose record covers exactly that extent;
* the gap: the binding's, written `00` (<<req-ssr-binding-iceoryx2-frame-layout,On iceoryx2, a frame is one header and one byte region, in a fixed layout>>);
* the payload's extent: the element's, each of its bytes, those that carry no meaning included;
* the bytes that a shortened payload gives up: the binding's, zeroed (<<req-ssr-binding-iceoryx2-frame-wipe,On iceoryx2, the token of a loan that is not sent is wiped, and a sent frame is left as it was written>>);
* the tail: the binding's, written `00` (<<req-ssr-binding-iceoryx2-frame-layout,On iceoryx2, a frame is one header and one byte region, in a fixed layout>>).

*Receive.*
A receive route's _retained budget_ is the number of received frames that the route can hold at once, as its declaration states; on a route of the Streamer it is the retained budget of the route's declared budget (xref:../../up-l2/streamer.adoc#req-ssr-streamer-containment[A fault stays on its route]).
The binding *MUST* keep a received sample for as long as the element's lease of the frame lasts, and *MUST* charge every received sample—in-progress acquisitions, physically or metadata-refused samples awaiting return, held samples, forgotten samples, pending returns and returns in service included—against both the route's retained budget and the subscriber receiver's aggregate budget `H` (<<req-ssr-binding-iceoryx2-expired-buffer,On iceoryx2, a receive route's retained budget fits twice in the expired-connection buffer>>) from before taking the sample from iceoryx2 until actual successful return completes.
Hand-off into a pending return representation is not physical return, and a Rust `+Drop+` implementation returning or writing a log message does not by itself establish successful return: the binding *MUST* establish actual completion either by proof that every admitted return necessarily succeeds on the valid path or through an evidenced status-bearing ownership interface that retains pending ownership and charge on noncompletion.
A view of the payload *MUST* cover exactly the payload's extent, and the binding's view of the metadata exactly the metadata's extent.
A view *MUST NOT* outlive the sample that holds it, and giving the sample back ends every view of it (xref:storage.adoc#req-ssr-binding-lent-storage[Lent storage is exclusive, disjoint and stable for as long as it is held]; xref:lifecycle.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]).

*Release in runtime mode.*
In runtime mode a service, a port and the node that holds them are process-lifetime infrastructure of the binding, which stay attached for the life of the process (xref:../runtime.adoc#req-ssr-release-none[Nothing is released in runtime mode]), so no loan, sample or view outlives the storage that it lies in.
Separately charged finite-lifetime local connection and view retirement on a subscriber receiver is governed strictly by <<req-ssr-binding-iceoryx2-expired-buffer,On iceoryx2, a receive route's retained budget fits twice in the expired-connection buffer>> and xref:../runtime.adoc#req-ssr-release-none[Nothing is released in runtime mode]; returning a last sample does not by itself imply connection destruction.
--

[horizontal]
ID:: `+req~ssr-binding-iceoryx2-frame-lifetime~3+`
ASIL:: B
Allocated to:: the iceoryx2 binding
Verification:: test, compile-fail, review
* *test*
** On transmit, the extents that a loan gives, compared with the offsets and lengths that the header gives; a loan published on another route, or before its metadata is recorded: refused; a record of the metadata that does not cover exactly the metadata's extent, or whose token lies outside it: not accepted, and the loan not published.
** On receive, the views' starts and lengths, compared with the same; a route that holds its whole retained budget: no further sample taken from iceoryx2.
** A native type with padding, on a route of this profile without protection: no loan published until all L elements are initialized, the metadata's and the payload's extents by the element, padding included, and the gap, the bytes given up and the tail by the binding.
** A protected native response whose loan has a payload extent of E, then a Control or a Failed response: the element shortens the payload to H; the binding zeroes the E − H bytes given up and writes the payload length H into the header; L unchanged; all L elements initialized at publication.
* *compile-fail*: a view used after its sample is given back.
* *review*: at source level, every way that the binding hands out an extent or a view, what ends it, and that no service, port or node is released in runtime mode; and the initialized extents that the binding declares for its publish and its receive paths, against iceoryx2's contract for the profile's service type.

*Rationale.*
A writer that could write the header could change where a reader finds the frame, and a view that outlived its sample would read storage that iceoryx2 may lend for another frame.
Charging a sample from before it is taken to after it is given back keeps what a route holds within its budget at every moment.

_All L elements._
The profile's services carry a byte sequence, and its L elements are the sample's payload for iceoryx2, whatever payload length the header gives.
So the publish path needs each of them initialized and a reader is given each of them; the element initializes what it is given, padding included, and the binding the rest.

[[req-ssr-binding-iceoryx2-frame-wipe]]
==== On iceoryx2, the token of a loan that is not sent is wiped, and a sent frame is left as it was written

[.specitem,oft-sid="req~ssr-binding-iceoryx2-frame-wipe~1",oft-title="On iceoryx2, the token of a loan that is not sent is wiped, and a sent frame is left as it was written",oft-needs="impl,utest",oft-tags="SafetyIceoryx2"]
--
*The token.*
A frame's token is the token of the message header that its metadata carries, where the message has one.

*A loan that is not sent.*
When a loan ends without being published, the iceoryx2 binding *MUST* zero the bytes of its token, where the element has recorded them, before it gives the loan back to iceoryx2.

*A payload that is shortened.*
When the element shortens a payload, the binding *MUST* zero the bytes that the payload gives up.

*A frame that is sent.*
The binding *MUST NOT* write into a frame once it has handed it to iceoryx2 to send, whether the send succeeds or fails.

*A received frame.*
The binding *MUST NOT* write into a received frame.
--

[horizontal]
ID:: `+req~ssr-binding-iceoryx2-frame-wipe~1+`
ASIL:: B
Allocated to:: the iceoryx2 binding
Verification:: test, review
* *test*: a loan whose metadata carries a token, ended without being published: its token's bytes are `00` before iceoryx2 can lend that storage again; a payload shortened before it is published: the bytes that it gave up are `00` in the frame that is sent.
* *review*: at source level, every way that a loan ends, and that no path writes into a frame after it is handed to iceoryx2, or into a received frame.

*Rationale.*
A loan that is not sent is the binding's alone, so it can clear the token before iceoryx2 lends that storage again.
Once a frame is handed to iceoryx2 its storage is no longer the binding's: receivers may hold it, in memory that iceoryx2 maps read-only for them (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/port/details/data_segment.rs#L229-L274[`+iceoryx2/src/port/details/data_segment.rs+`, lines 229 to 274], where a receiver opens its view of a publisher's data segment for reading only), and iceoryx2's publisher interface tells the binding nothing when the last of them gives it back: a send reports only how many receivers it reached, and the publisher takes returned samples back internally (source: the code of iceoryx2, release 0.9.3, https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/sample_mut.rs#L306-L338[`+iceoryx2/src/sample_mut.rs+`, lines 306 to 338], where a loaned sample is sent; https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/port/publisher.rs#L578-L900[`+iceoryx2/src/port/publisher.rs+`, lines 578 to 900], the publisher's interface; https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2/src/port/details/sender.rs#L491-L519[`+iceoryx2/src/port/details/sender.rs+`, lines 491 to 519], where returned samples are taken back).
Writing into it could change what a receiver reads.
So a sent frame's bytes, its token among them, stay in the service's shared memory, where a process that may open the service can read them, and xref:../../safety/elements/up-rust/assumptions-of-use.adoc#aou-seooc-peer-access[Only authorized processes reach the transport] is what limits who that is.
