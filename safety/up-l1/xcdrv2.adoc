= uP-L1 safety: The fixed-layout XCDR2 profile
:toc: preamble

The key words "*MUST*", "*MUST NOT*", "*REQUIRED*", "*SHALL*", "*SHALL NOT*", "*SHOULD*", "*SHOULD NOT*", "*RECOMMENDED*", "*MAY*", and "*OPTIONAL*" in this document are to be interpreted as described in https://www.rfc-editor.org/info/bcp14[IETF BCP14 (RFC2119 & RFC8174)]

Conventions and tags: xref:../README.adoc[the safety area's README].
This layer, and whom it binds: xref:README.adoc[safety at uP-L1].
The duties of every wire: xref:wires.adoc[allocated to each wire].
The duties of every serialized wire: xref:serialized-wires.adoc[serialized wires, and the values they own].

This page states one serialized format.
A value of a type with a fixed list of fixed-width fields is written as a four-byte prefix and its fields in order, in little-endian byte order, each field at a place that the type alone fixes.
The profile takes its name from XCDR2, version 2 of the extended Common Data Representation, and relies on no definition of it: an implementation of XCDR2 is not assumed to read its encodings.

This page holds the five requirements of the profile, allocated to each wire of the profile: each item's statement and "Allocated to" line say whom it binds (xref:../README.adoc#req-ssr-requirements-bind[A requirement binds the parts that it names]).

== Whom this page binds

* The five requirements bind each wire that is written against the element's wire contract and states this profile as its format (xref:serialized-wires.adoc#req-ssr-wire-serialized-format[A serialized wire reads and writes one stated format]).
* The duties of every wire and of every serialized wire hold beside them.
Where an item here cites one of those duties, it says what that duty is for this profile, and the length item also has every size stated as exact.
* A verification row says how a wire shows that it meets an item.
The item binds whether or not that evidence exists.
* The profile is a serialized format.
It states no rule for a native type, whose rules the native wire's page states (xref:native-wire.adoc[the native wire]).

[[req-ssr-xcdr2-types]]
== The profile encodes structures of fixed-width fields, and nothing else

[.specitem,oft-sid="req~ssr-xcdr2-types~1",oft-title="The profile encodes structures of fixed-width fields, and nothing else",oft-needs="impl,utest",oft-tags="SafetyXcdr2"]
--
*A structure of fields.*
A type of this profile is a structure with a fixed list of named fields, in a fixed order.
The list can be empty.

*What a field is.*
A field is one of these:

* an unsigned or a signed integer of 8, 16, 32 or 64 bits;
* a floating-point number of 32 or 64 bits;
* a boolean;
* an array of a fixed number of elements that all have one type of this list, an array of such elements included.
The number can be zero.

*Nothing else.*
A wire of this profile *MUST NOT* encode or decode a type that holds anything else, among them:

* a string, a sequence, a map, or any other field whose size depends on its value;
* an optional field, a union or an enumeration;
* a structure as a field of another;
* a character, or an integer or a floating-point number of a width that the list above does not name;
* a type that can gain, lose or reorder fields and still be read, whether by fields added at the end or by a number written before each field.
--

[horizontal]
ID:: `+req~ssr-xcdr2-types~1+`
ASIL:: B
Allocated to:: each wire of the fixed-layout XCDR2 profile
Verification:: test, compile-fail
* *test*: a type with a field of each kind, an array of arrays, a type with no field and an array of no elements, each encoded and decoded.
* *test* or *compile-fail*, as the wire refuses a type at setup or when it is built: a type with each kind of field that the profile leaves out, refused as a type of the profile.

*Rationale.*
Every field has one size, so a type has one length and each field has one place.
That is what lets a wire state its size exactly and decode without a count or a length that the input supplies.

[[req-ssr-xcdr2-encoding]]
== An encoding is a four-byte prefix and the fields in order, little-endian and aligned

[.specitem,oft-sid="req~ssr-xcdr2-encoding~1",oft-title="An encoding is a four-byte prefix and the fields in order, little-endian and aligned",oft-needs="impl,utest",oft-tags="SafetyXcdr2"]
--
*The prefix.*
An encoding *MUST* begin with these four bytes: `06 00 00 00`.

*The fields.*
After the prefix the fields *MUST* follow in the order of the type's list, each written as follows, with nothing between them but padding:

* an integer: in two's complement, least significant byte first;
* a floating-point number: its IEEE 754 binary32 or binary64 bit pattern, least significant byte first;
* a boolean: one byte, `00` for false and `01` for true;
* an array: its elements in order, with no count; padding comes before its first element only where alignment needs it.

*Alignment.*
Each value *MUST* start at the next offset that is a multiple of its alignment, whether it is a field or an element of an array.
The alignment of an integer or a floating-point number is its size in bytes, that of a boolean is one, and that of an array is the alignment of its elements, or one for an array of no elements.
Offsets are counted from the first byte of the prefix.
An array of no elements takes no byte.

*Padding.*
The bytes that alignment skips are padding.
An encoder *MUST* write each padding byte as `00`, and *MUST NOT* write any byte after the last field.
So an encoder writes one encoding of each value.
Which other inputs decode to that value is stated by <<req-ssr-xcdr2-decoding,Decoding refuses a wrong length, a wrong prefix or a wrong boolean byte>>.
--

[horizontal]
ID:: `+req~ssr-xcdr2-encoding~1+`
ASIL:: B
Allocated to:: each wire of the fixed-layout XCDR2 profile
Verification:: test
* *test*
** Encodings stated from this page before the wire runs, compared byte for byte with what the wire writes: a type with a field of each kind; a type with a value of 2, 4 and 8 bytes after each remainder of its alignment, among them a value of eight bytes after an offset that is a multiple of four and not of eight; an array of two-byte elements after a field of one byte; a type with no field; an array of no elements.
** The same encodings decoded by a decoder written from this page alone.
** Each padding byte of each encoding, checked to be `00`.

*Rationale.*
Two sides that hold the same type compute the same place for every value, so neither sends a description of the layout.
Zero padding makes an encoder write one encoding of each value, so values whose fields have equal bit patterns are written as equal bytes.

[[req-ssr-xcdr2-length]]
== The encoded length of a type is exact

[.specitem,oft-sid="req~ssr-xcdr2-length~1",oft-title="The encoded length of a type is exact",oft-needs="impl,utest",oft-tags="SafetyXcdr2"]
--
*Fixed by the type.*
The encoded length of a type is the offset at which its last field ends.
For a type with no field it is four.
Every value of the type has that length.

*Stated as exact.*
That length is the size of the largest encoding, which a serialized wire states for its type (xref:serialized-wires.adoc#req-ssr-wire-encode-decode[A serialized wire encodes once into the storage it is given, and decodes into a value that its slot owns], "Sizing").
A wire of this profile *MUST* also state it as the exact size of every encoding of the type.
--

[horizontal]
ID:: `+req~ssr-xcdr2-length~1+`
ASIL:: B
Allocated to:: each wire of the fixed-layout XCDR2 profile
Verification:: test
* *test*: the size that the wire states for each type in the test row of the encoding item, compared with the length computed from this page and with the number of bytes written.

*Rationale.*
A route can size its storage from the type, before any value exists.

[[req-ssr-xcdr2-decoding]]
== Decoding refuses a wrong length, a wrong prefix or a wrong boolean byte

[.specitem,oft-sid="req~ssr-xcdr2-decoding~1",oft-title="Decoding refuses a wrong length, a wrong prefix or a wrong boolean byte",oft-needs="impl,utest",oft-tags="SafetyXcdr2"]
--
*What is refused.*
Decoding *MUST* refuse an input:

* whose length is not the encoded length of the type, whether it is shorter or longer;
* whose first four bytes are not the prefix;
* in which the byte of a boolean, as a field or as an element of an array, is neither `00` nor `01`.

*Padding is not examined.*
Decoding *MUST* accept any value in a padding byte: an input whose padding is not zero decodes to the same value.

*Every other input is a value.*
Every bit pattern of an integer and of a floating-point number is a value, and decoding *MUST* yield the value with exactly the bit pattern of its bytes.
So an input that passes the three checks decodes, and decoding makes no other check of its bytes.
--

[horizontal]
ID:: `+req~ssr-xcdr2-decoding~1+`
ASIL:: B
Allocated to:: each wire of the fixed-layout XCDR2 profile
Verification:: test, fault-injection
* *test*
** An input one byte short and one byte long, and the empty input: each refused.
** A changed byte in each place of the prefix: each refused.
** A boolean byte of `02` and of `FF`, as a field and as an element of an array: each refused.
** An input with every padding byte changed: decoded to the same value.
** A floating-point field holding a negative zero and a NaN with a payload: decoded with the same bit patterns.
* *fault-injection*: truncated and malformed frames on a route, each refused as the rules for every wire say (xref:wires.adoc#req-ssr-wire-no-panic[Encoding and decoding never panic]), and returned as an error or counted as the element's rule on refused frames says (xref:../seooc-up-rust/errors.adoc#req-ssr-error-no-silent-loss[No silent loss, and each loss counted once]).

*Rationale.*
The length is known before the input is read, so a wrong length can be refused before any field is read, and no field is read past the end.
A boolean is the only kind whose byte can hold a pattern that is no value.

_Padding._
A reader that refused non-zero padding would refuse bytes that another reader of this page accepts.
One rule for every reader keeps them the same.

[[req-ssr-xcdr2-identity]]
== The bytes name no type, and a changed type is another type

[.specitem,oft-sid="req~ssr-xcdr2-identity~1",oft-title="The bytes name no type, and a changed type is another type",oft-needs="impl,utest",oft-tags="SafetyXcdr2"]
--
*The bytes name no type.*
An encoding holds no name, no identifier and no description of its type.
The prefix is the same for every type.

*What agrees the type.*
The type of a payload is the type that its route declares at the sender and at the receiver.
Of that declaration the bytes show only the encoded length, which decoding checks (<<req-ssr-xcdr2-decoding,Decoding refuses a wrong length, a wrong prefix or a wrong boolean byte>>).

*A changed type is another type.*
A change to the list of fields makes another type: a field added, removed, moved, renamed or given another kind, or an array given another number of elements.
The bytes do not show such a change.
Where the two encoded lengths are equal, a reader of one list can decode an encoding of the other without an error, and what it reads need not be what was written.
A wire of this profile *MUST NOT* state, in its README or in what it declares, that it reads an encoding of a type with another list of fields.

*Its version.*
A wire states the version of the profile by naming its five requirements by their identifiers, each with the revision that it ends in, for example `req~ssr-xcdr2-types~1` (xref:serialized-wires.adoc#req-ssr-wire-serialized-format[A serialized wire reads and writes one stated format]).

*The identifier.*
This page assigns no payload encoding identifier, and the registry has none for the profile, so a wire of the profile states one of the private-use range (xref:../../basics/payload_encoding_registry.adoc[the payload encoding registry]).
--

[horizontal]
ID:: `+req~ssr-xcdr2-identity~1+`
ASIL:: B
Allocated to:: each wire of the fixed-layout XCDR2 profile
Verification:: test, review
* *test*: two types of equal encoded length, each decoding the other's encoding without an error.
* *review*: the wire's statement of the type that a route declares and of what it checks; the version of the profile that it states; and that neither its README nor what it declares says that it reads another list of fields.

*Rationale.*
Nothing in the bytes names their type, and their length tells apart only types of different lengths.
A decode that succeeds shows that the bytes fit the reader's type, and nothing about what the sender meant.
