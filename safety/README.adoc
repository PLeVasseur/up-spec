= Safety requirements for traceability
:toc: preamble

This area holds the requirements of the up-rust SEooC, and of the transports, wires and Streamer that work with it, which their repositories trace with OpenFastTrace (OFT).
It is laid out like the protocol specification: what is shared comes first, then a part for each protocol layer, then a part for each SDK element.

* *What the area holds.*
The area is named for its safety requirements and assumptions of use.
It also holds what they rest on: the up-rust SEooC's ordinary functional contract, and its resource and fault obligations.
* *Beside the protocol chapters.*
Most items add to the protocol chapters, and some differ from them on purpose.
How an item and a rule of the protocol chapters meet: <<req-ssr-contract-transition,What a part declares and claims, and when a replacement takes effect>>.

=== Where a new item goes

* *Protocol requirements*, which every SDK of a kind must meet, stay in the protocol chapters (`basics/`, `up-l1/`, `up-l2/`, `up-l3/`), tagged as those chapters tag them.
* *A safety obligation of a protocol layer* goes in that layer's part here.
A restriction that only one binding has goes in that binding's file, beneath its layer.
* *An SDK element's own scope, boundary and implementation-specific rules* go in a directory of their own here, named `seooc-<sdk>/`.
They name one element and its parts.
* *A concept or fault model that several parts rely on* is described on this page, with its scope.
* *A part is added when it has content.*
No empty directory mirrors a protocol chapter.

[[filing]]
=== Filing and scope

Where an item is filed says which protocol responsibility it concerns.
The item states whom it binds, wherever it is filed: for a requirement, <<req-ssr-requirements-bind,A requirement binds the parts that it names>>; for an assumption of use, xref:seooc-up-rust/assumptions-of-use.adoc#aou-seooc-assumptions-bind[An assumption of use binds the integrator who claims the scope, and replaces no requirement].

* *Every item here was written for the up-rust SEooC* and for the parts that work with it.
The items name that element and those parts, so an item in `up-l1/` or `up-l2/` is no requirement on every transport, or on the SDK of another language.
An SDK or a transport that no requirement of this area names is bound by one only once it declares that it follows the items of this area, which its repository then covers under their tags.
* *An assumption of use keeps `seooc` in its ID wherever it is filed.*
It is that element's assumption (xref:seooc-up-rust/assumptions-of-use.adoc#aou-seooc-assumptions-bind[An assumption of use binds the integrator who claims the scope, and replaces no requirement]).
* *A language-agnostic safety requirement*, if one is added, gets a tag of its own and says whom it binds.
* *The protocol chapters.*
The protocol chapters stay in force for what they cover (<<req-ssr-contract-transition,What a part declares and claims, and when a replacement takes effect>>).

[[req-ssr-requirements-bind]]
=== A requirement binds the parts that it names

[.specitem,oft-sid="req~ssr-requirements-bind~2",oft-title="A requirement binds the parts that it names",oft-needs="uman",oft-tags="SafetyUpRustCore,SafetyStreamer,SafetyBinding,SafetyWire"]
--
*Whom it binds.*
The statement of each software safety requirement of this area names the part or parts that answer for each of its duties, and states the conditions, qualifiers and exclusions that determine the reach of each duty.
The requirement binds those parts and no other part, wherever it is filed.
Each of them *MUST* meet each duty that the statement gives it, within that duty's reach, which only the statement determines.
A part is one that the statement names explicitly: the element, a binding, a wire, a platform backend, the Streamer, or another part.

*The "Allocated to" line.*
Each requirement of this area has an "Allocated to" line, its explicit, reviewable allocation.
The line *MUST* agree with the statement and *MUST NOT* introduce a part, a condition, a qualifier or an exclusion that the statement lacks.
A disagreement between the statement and the line is a defect of the requirement and *MUST* be corrected by a reviewed revision of this repository.

*Assumptions of use.*
Whom an assumption of use binds is stated by xref:seooc-up-rust/assumptions-of-use.adoc#aou-seooc-assumptions-bind[An assumption of use binds the integrator who claims the scope, and replaces no requirement].
--

[horizontal]
ID:: `+req~ssr-requirements-bind~2+`
ASIL:: B
Allocated to:: each part that a requirement of this area binds
Verification:: review (each requirement's statement names the part or parts that answer for each of its duties, with the conditions, qualifiers and exclusions that determine each duty's reach; each requirement has an "Allocated to" line that agrees with the statement and introduces nothing that the statement lacks)

*Rationale.*
A requirement is read on its own, so whom it binds, and how far, is read from its statement.
One text then decides that scope, and a claim or a safety manual that quotes the statement carries all of it.
The "Allocated to" line keeps the allocation explicit, so that a review can check it against the statement.
Pages, tags, tracing runs and repositories change as the specification is organized and traced.
If whom a requirement binds depended on them, such a change could move a duty to another part or leave it with none.

NOTE: An item's tags and tracing records are coverage data.
Repository paths, ownership, and the status that a record keeps of an item's adoption or qualification are governance data.
The tags, and the repositories that cover them, are listed under <<tags>>, and an implementation keeps its own record of where it implements each item (<<spec-first>>).

[[req-ssr-contract-transition]]
=== What a part declares and claims, and when a replacement takes effect

[.specitem,oft-sid="req~ssr-contract-transition~1",oft-title="What a part declares and claims, and when a replacement takes effect",oft-needs="uman",oft-tags="SafetyUpRustCore,SafetyStreamer,SafetyBinding,SafetyWire"]
--
*The declaration.*
A part that a requirement of this area names is bound by it as <<req-ssr-requirements-bind,A requirement binds the parts that it names>> states, at the revision in force for that part, whether or not it has declared; a claim of a safety-assurance scope changes whom a requirement binds only where the requirement's own stated condition names such a claim.
Each such part *MUST* declare which part it is, the adopted revision of this repository that its claims rest on, and each named profile that it follows.
What a part declares does not change which requirements bind it.
A named profile is one that an item of this repository names, with each of its items by identifier or link, and a declaration *MUST NOT* name any other; the profile's own statement of its version is read at the declared revision.
The dependency closure of an item is each item that its statement names or links, and each item that those name or link in turn; that of a named profile is that of its items.
For the part's claims, the declared revision fixes the revision of each item and of its closure, and the closure adds no duty.

*Claims.*
A claim of conformance to the items of this area *MUST* name the part's declaration and each item that it rests on, at the revision that the declared revision of this repository states.
A claim that rests on an item rests on its dependency closure too, and a claim that rests on fewer than all the requirements that bind the part *MUST* rest on a named profile that the part declares.
Its evidence is evidence for those revisions only.
A tracing or coverage run does not change which items of this area bind a part.

*Replacement.*
A rule of the protocol chapters, or an item of this area at a revision, stays in force for the implementations and the behaviour that it covers until an adopted replacement takes effect for them.
A replacement is an item of this area, or a change of a protocol chapter, that names the rule that it replaces or retires, and the implementations and the behaviour for which it does, and it takes effect only for those.
A new revision of an item replaces its earlier revision for each part that both revisions name; for a part that only the earlier revision names, the earlier revision stays in force until a text retires it for that part.
A text is adopted when it is stated in a revision of this repository that normal adoption produced; that is no status of its adoption in the sense of <<req-ssr-requirements-bind,A requirement binds the parts that it names>>, and no status that a record keeps decides it.
An item of this area lifts a rule of the protocol chapters, a security requirement included, only where it is such a replacement.
A rule of the protocol chapters keeps its own reach, whether or not an implementation that it covers also follows the items of this area.

*Where an item meets a chapter's rule.*
An item and a chapter's rule meet in one of three ways.

* Where one implementation can meet both, both hold.
* Where one implementation cannot meet both for a behaviour, a part that the item binds *MUST* say so, naming the item at its revision, and *MUST NOT* claim conformance to the chapter's rule for that behaviour.
A claim of conformance *MUST NOT* name both rules for that behaviour.
* Where the two texts do not settle whether one implementation can meet both, a claim of conformance to one is no claim about the other and *MUST NOT* rest on an answer to that question.
--

[horizontal]
ID:: `+req~ssr-contract-transition~1+`
ASIL:: B
Allocated to:: each part that a requirement of this area names
Verification:: review (each part's declaration names the part, the revision of this repository and each named profile that it follows; each claim of conformance names the declaration and each item that it rests on, with their dependency closure, at their revisions, and rests on a named profile where it rests on fewer than all the requirements that bind the part; where one implementation cannot meet an item and a chapter's rule, the part says so with the item's revision and claims no conformance to the chapter's rule, and no claim names both rules; no claim rests on an answer that the two texts do not settle)

*Rationale.*
A claim is read against an exact text, so it names that text and the part that it is made for.
The protocol chapters cover implementations that the items of this area do not name, so only a text that names a rule, and those for whom it replaces it, can lift that rule.
A tracing run is arranged for coverage, so what binds a part does not depend on how a run is arranged.

=== Integrity levels

A transport declares one integrity level: QM, A, B, C or D, in that order.

* *Scope.*

* *A level is a label.*
Setup checks it.
It neither raises an element's capability nor qualifies the process that declares it.

[[req-ssr-peer-fault-model]]
=== The requirements hold against a faulty peer

[.specitem,oft-sid="req~ssr-peer-fault-model~1",oft-title="The requirements hold against a faulty peer",oft-needs="impl,utest,uman",oft-tags="SafetyUpRustCore,SafetyStreamer,SafetyBinding,SafetyWire"]
--
*The faulty-peer model.*
Every peer is treated as faulty, never malicious.

* A peer may send any content, at any time and in any volume, and may choose any source URI.
* A faulty peer includes one that writes values its own middleware never writes, into shared memory it can write.
* A peer below a reader's level may write its own shared memory at any moment, and the route that its reader then takes is stated in xref:up-l1/integrity.adoc#req-ssr-integrity-zero-copy[Zero-copy only from a writer at or above the reader].

*The duty.*
Each bound part *MUST* meet each requirement of this area that binds it, for every peer input and shared-memory write allowed by this model.

*The model's scope.*
The peers of the up-rust SEooC, on every transport.
The model applies within the access restriction that the integrator provides: only the processes deployed to use a transport's resources reach them (xref:up-l1/deployment.adoc#aou-seooc-peer-access[Only authorized processes reach the transport]).

*The boundary between safety and security.*
Only deliberate exploitation, such as engineering a peer-ID hash collision, is out of scope, as security.
That exclusion is the model's boundary between safety and security: it does not say that a peer that exploits deliberately is harmless, or that the requirements hold against it.

*Rules left in force.*
The model bounds only the safety argument.
It leaves in force the protocol's security requirements, such as those of xref:../up-l1/README.adoc[uP-L1] against address spoofing and unauthorized access.
It also does not make a lower-assurance process harmless because it runs apart: the rules for lending and copying cover what such a process can write into shared memory.
--

[horizontal]
ID:: `+req~ssr-peer-fault-model~1+`
ASIL:: B
Allocated to:: the element; each platform backend; each binding; each wire; the Streamer; any other part that a requirement of this area names
Verification:: fault-injection, review
* *fault-injection*
** Malformed and truncated frames, and frames with any bytes in their header, their envelope and their payload.
** Arbitrary byte strings, decoded by each wire.
** A flood on every receive kind, and one peer that fills a route's depth, its slots or its peer table.
** Frames at any time, frames that carry an earlier incarnation of their peer included.
** Frames from undeclared sources, and from any source URI.
** A peer process that writes values its own middleware never writes, into shared memory that it can write.
** A peer process below the reader's level that writes its shared memory while it is read.
* *review*
** For each part, that the verification of each requirement that binds it covers the faults of this item that bear on that requirement.
** That the safety manual of each repository that covers this item states the model, its scope and the boundary between safety and security.
ISO 26262:: 6-Annex D.2.2, 6-Annex D.2.3, 6-Annex D.2.4 (part-clause numbers only)

*Rationale.*
Peers run in other processes, often over middleware this project does not control.
A requirement that held only for well-formed input would leave a process open to every peer that fails.

The element, the bindings, the wires and the Streamer handle the same frames and the same shared memory, so a fault that one of them does not withstand reaches the others.

[[process-failure]]
=== Process failure and restart

A process leaves runtime mode only by exit, crash or kill.
There is no recovery inside the process: a supervisor outside it restarts the whole process or partition, or takes the item to its safe state.
A peer's death or restart is normal input to the processes that stay up.

* *Scope.*
Every process that uses the up-rust SEooC, the Streamer included.
* *Stated in.*
xref:seooc-up-rust/assumptions-of-use.adoc#aou-seooc-supervisor-restart[A supervisor outside the process restarts it] for the supervisor.
xref:seooc-up-rust/runtime-modes.adoc#req-ssr-mode-no-shutdown[No shutdown in runtime mode] and xref:seooc-up-rust/runtime-modes.adoc#req-ssr-mode-restart[A restart is an initialization] for the element, xref:up-l1/peers.adoc#req-ssr-peer-failure-normal[Peer failure is normal input] for the survivors, and xref:up-l1/bindings.adoc#req-ssr-binding-predecessor-cleanup[A binding cleans up after a dead predecessor, in initialization] for a binding.

[[memory-separation]]
=== Memory separation

The requirements assume that a faulty process cannot write another process's private memory.
Shared memory exists only where a binding maps it, and what a peer may write there is stated in <<req-ssr-peer-fault-model,The requirements hold against a faulty peer>>.

* *Scope.*
Every process or partition that uses the up-rust SEooC.
* *Who provides it.*
The integrator, through the memory protection of the OS or, on an MCU, the partition boundary its configuration states.
The element can neither provide nor check it.
* *Stated in.*
xref:seooc-up-rust/assumptions-of-use.adoc#aou-seooc-process-isolation[Processes or partitions are isolated], and <<req-ssr-peer-fault-model,The requirements hold against a faulty peer>> for what a peer may write in shared memory.

[[violation]]
=== How a violated assumption shows up

A violated assumption of use is refused at setup, counted, or undetectable by the element.
Where the contract only requires no check of something, an assumption's text says that instead, and gives the violation none of these classes.

* *Scope.*
The assumptions of use of the up-rust SEooC, wherever they are filed.
* *Stated in.*
xref:seooc-up-rust/assumptions-of-use.adoc#violation-classes[The element's assumptions of use].

[[claims-model]]
=== Claims and guarantees

Functional communication, native resource behaviour, a finite timing bound and safety assurance are four independent properties.
A stronger resource guarantee is reported as required or not, established or not, and admitted or not, and it is admitted only where it is both required and established.

* *Scope.*
The up-rust SEooC, and each route of it.
It is that element's model, and no rule of a protocol layer.
* *Stated in.*
xref:seooc-up-rust/README.adoc#claims[The SEooC's claims] and xref:seooc-up-rust/heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name].

[[spec-first]]
== Specification and implementation

The items here say what an implementation must satisfy.
An implementation's code, tests and reviews trace to the items.

* No statement, rationale or verification entry rests on an implementation's source files, internal names, review records or current state.
* A rationale cites what <<markup>> allows.
* A statement may name something the element must provide, such as an operation, a setting, a counter or a crate.
That name is part of the specification, not a citation of code.
* An SDK that implements an item keeps its own record of where it does so, outside this repository, as non-normative traceability.

== Why this area cannot break an SDK's run

An OFT run keeps the items in the files its patterns name and its tag filter selects, and reports each kept item that lacks coverage.
So:

* *An SDK reads this area only by naming it.*
Each SDK names up-spec files and directories in its OFT patterns.
One that adopts these items names the parts that hold them, as up-rust names `safety/up-l1`, `safety/up-l2` and `safety/seooc-up-rust`, and no SDK names `safety/` as a whole.
Nothing here sits at the top of the repository, where a pattern such as `up-spec/*.adoc` would reach it.
* *Every item here carries a tag from the table below, and no tag of the protocol chapters.*
A run that keeps untagged items (`_`), or items tagged `LanguageLibrary`, `TransportLayerImpl` and the like, keeps none of them.
The patterns are the first guard: a run whose tag filter is missing keeps every item its patterns reach, and still none from here.
* *A layer part holds items of several repositories.*
A run that names one keeps only the items whose tags its filter selects.
So the tags, not the directories, decide what a repository covers.
* *Nothing here links to the protocol chapters through OFT,* so they gain no coverage obligations from it.

`req` for a software safety requirement, `aou` for an assumption of use, the types up-spec already uses.

=== IDs

`+req~ssr-<area>-<name>~<revision>+` and `+aou~seooc-<name>~<revision>+`.

* A name is never changed or reused.
* A revision rises when the meaning of an item changes, and not for a wording fix.
A repair that only brings a requirement's statement and its "Allocated to" line into agreement, and changes nothing that the requirement binds, is a wording fix.
* An item filed in another part or file keeps its name and its revision.

[[markup]]
=== Markup

As in the protocol chapters: a block attribute line that gives the item its `specitem` role and its `oft-sid`, `oft-title`, `oft-needs` and `oft-tags` attributes, then an open block that holds the statement.

* Inside the block, a statement may use short paragraphs, labels in bold and lists.
All of it is the statement.
* Text after the block is not part of the statement: the `ID` row, which repeats the item's identifier for readers, the ASIL, the allocation, the verification methods, the ISO 26262 references and the rationale.
A requirement's statement says whom the requirement binds (<<req-ssr-requirements-bind,A requirement binds the parts that it names>>).
* A rationale gives the product or safety reason for the rule as it stands.
It does not recount earlier revisions: an item's history is kept outside these pages (<<source>>).
* A rationale cites only public sources: up-spec, public standards by part and clause number, and the published documents and code of other projects, each at a fixed version.
It does not cite the code of the SDK that implements the item (<<spec-first>>).

=== References to an item

* *By title.*
Text that refers to an item links to it, and the text of the link is the item's heading.
* *To the item as it stands.*
The link points at the item's anchor, which is its type and name without its revision: `req-ssr-heap-declared` for `+req~ssr-heap-declared~N+`.
So a reference always means the current revision of the item.
* *Identifiers.*
An item's identifier and revision are in its block attribute line and in its `ID` row.
Code and tests cite that identifier in their coverage tags (<<tracing>>).
* *A change of meaning is reviewed with its references.*
When an item's meaning changes, its revision rises, and each item that links to it is read again against the new text.

=== Key words

Statements use the key words of BCP 14 as up-spec does (xref:../basics/payload_encoding_registry.adoc[the payload encoding registry], "Requirement Ownership"):

* *MUST* and *MUST NOT* for the element and its parts;
* *SHALL* and *SHALL NOT* for an assumption of use, whose duty falls on the integrator.

Both keep BCP 14's meaning of an absolute requirement.
An item whose statement uses no key word binds just the same; a new or revised statement states each duty with a key word.

=== Needs

* A requirement met in code needs `impl,utest`: the code that meets it, and the tests that show it, carry coverage tags.
* A requirement shown only by reviewing a document needs `uman`.
* A requirement met in code that also makes the element state something for integrators needs `impl,utest,uman`.
* An assumption of use needs `uman`: the safety manual states it.
A document covers it with an item of its own that covers the assumption, because OFT reads no coverage tag in a Markdown file.

== Tags

A requirement carries the tag of a part that its "Allocated to" line names, and `SafetyBindingPull` as well where its statement holds a duty of pull bindings only; an assumption of use carries the tag `SafetyManual`.
A tag says which repositories cover an item.
The column "Items allocated to" summarizes which items carry each tag.
A requirement's own statement governs over its row: it may name parts that the row does not name, or only some of those that the row names.

=== Gate tags

Each repository that covers items here gets one gate tag, named after it: `SafetyGateUpRust`, `SafetyGateStreamer`, `SafetyGateIceoryx2`, `SafetyGateXcdrV2`, and so on.

* An item gets a repository's gate tag once that repository covers it in OFT's sense, with at least one coverage link of each type the item needs.
* Coverage in OFT's sense says nothing about whether an item is verified, which its verification methods decide.
* A repository's gating runs keep only the items that carry its gate tag, so they stay green while it covers the rest, and a report-only run keeps them all.
* Bindings and wires share items, so each gets a gate tag of its own.
* Gate tags present on items record the repository mappings admitted with them.

[[tracing]]
== How a repository starts tracing these items

. Its OFT patterns add the parts that hold the items it covers, for example `up-spec/safety/up-l1`, `up-spec/safety/up-l2` and `up-spec/safety/seooc-up-rust` for up-rust.
. Its gating runs add its gate tag to their filter, for example `SafetyGateUpRust`, and not the tags of the table.
Every item they keep is then covered, and every coverage tag in the repository resolves.
. A report-only run, which fails nothing, adds the tags of the table it covers as well, for example `SafetyUpRustCore`, and shows every item still to cover.
. Code and tests carry OFT's own coverage tags, `+[impl->req~ssr-…~N]+` and `+[utest->req~ssr-…~N]+`, only for items its gating runs keep, because a tag naming an item the run did not keep is a broken link.
A review log in the repository records who mapped each tag.
. The up-spec change that defines or gates an item lands first.
The repository moves its copy of up-spec, a submodule or a pinned copied snapshot as that repository packages it, to that change in the same merge as the commit that tags the item.
It records which change it copied, so that no run sees a tag without its item.
. A change that files items in another part lands the same way.
The repository's patterns name the new part in the same merge, so that no run loses an item it kept before.

== ISO 26262

Items and text in this area cite ISO 26262 by part and clause number only, written `part-clause`, for example `6-7.4.13`, or `part-Table n`.
No text of the standard appears here, quoted or closely paraphrased, and no table that maps it.

A reference is trace metadata: it names a clause that an item relates to.
It claims no compliance of an item, of the element or of a deployment with the standard.

[[source]]
== Source

The items of this area were first written outside this repository, for the up-rust SEooC, and are being rewritten for publication.

* A rewritten item's statement uses the key words above, with its meaning unchanged.
* Its rationale is written from public sources alone: up-spec, public standards, and the published documents and code of other projects, each linked at a fixed version.
ISO 26262 is cited by part and clause number only.
* A rationale names each source where it uses it, and an item ID is one of up-spec's.
* A rationale does not cite the code of the SDK that implements the item (<<spec-first>>).

An item not yet rewritten keeps only the rationale sentences that cited public sources, so its rationale may be short or absent.

The decisions each item rests on, the reviews that shaped it and its history are kept outside this repository, with the rationale sentences that cited them.
Rationale sentences that cited ISO 26262 were left out, and their part-clause numbers are kept in each item's ISO 26262 line.
