[[req-ssr-unsafe-sound]]
== Safe code cannot cause undefined behaviour

[.specitem,oft-sid="req~ssr-unsafe-sound~1",oft-title="Safe code cannot cause undefined behaviour",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
A sequence of safe calls through the element's public API, including items hidden from the documentation but reachable from safe code, *MUST NOT* be able to cause undefined behaviour:

* no use of a slot or frame after its release;
* no two live mutable references to one value;
* no data race;
* no read of an invalid value.
--

[horizontal]
ID:: `+req~ssr-unsafe-sound~1+`
ASIL:: B
Allocated to:: the element
Verification:: miri (Stacked Borrows and Tree Borrows, over the tests and over programs of safe calls that attempt undefined behaviour, at least one for each kind that the statement lists and every one that demonstrated a defect), compile-fail (each misuse of the public API from which undefined behaviour would follow and that the element's types rule out, every misuse that a fix ruled out among them), review (a sweep of each defect class)
ISO 26262:: 6-Annex D.2.3 (part-clause numbers only)

*Rationale.*
Undefined behaviour can corrupt memory in ways that no later check can see, which runtime code must never risk.

In Rust, `+unsafe+` marks only code whose memory safety the compiler cannot check (source: the Rust Reference, Rust 1.98.1, chapter The unsafe keyword, rule unsafe.intro, and chapter Behavior considered undefined, rule undefined.soundness).
So safe callers rely on the element to keep that promise for them, hidden items included.

The promise holds under the faulty-peer model too (xref:../README.adoc#req-ssr-peer-fault-model[The requirements hold against a faulty peer]).

Miri, tests and target builds are evidence at their own scope.
None replaces the source-level argument for each obligation.

[[req-ssr-unsafe-inventory]]
== Every `+unsafe+` is inventoried and justified

[.specitem,oft-sid="req~ssr-unsafe-inventory~3",oft-title="Every `unsafe` is inventoried and justified",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*The element.*
Every `+unsafe+` site in the element *MUST* state the memory-safety obligation it relies on, and sit under a reviewed row of the inventory.
CI *MUST* refuse a new, changed or vanished site until the inventory is updated.

*Wires.*

* Implementing, wrapping or composing a wire *MUST NOT* need hand-written `+unsafe+`.
* The wire crates this project ships *MUST* contain none.
* The `+unsafe+` a derive generates *MUST* be inventoried in the derive's crate.

*Bindings.*
Each binding this project ships *MUST* keep its own inventory under the same gate (xref:../up-l1/bindings.adoc#req-ssr-binding-unsafe-inventory[A binding this project ships inventories its own `+unsafe+`]).

*Outside these inventories.*
Only a wire or binding from elsewhere with `+unsafe+` code of its own, such as a wire over a C codec, falls outside these inventories, as a separate element whose integrator qualifies its `+unsafe+`.
--

[horizontal]
ID:: `+req~ssr-unsafe-inventory~3+`
ASIL:: B
Allocated to:: the element; each wire crate and each binding that this project ships
Verification:: gate (the `+unsafe+` inventory check; a lint that denies an `+unsafe+` block or function without the documentation of its obligations), compile-fail (a derive under `+forbid(unsafe_code)+`)

*Rationale.*
An `+unsafe+` operation requires its author to establish the memory-safety obligations that the compiler cannot prove.
Ordinary type, reference and borrowing rules still apply (source: the Rust Reference, Rust 1.98.1, chapter The unsafe keyword, section Unsafe blocks; the Rustonomicon, Rust 1.98.1, chapter Meet Safe and Unsafe).

Each site states those obligations, and a lint denies an `+unsafe+` block or function without that documentation.
A gate fails when the code's `+unsafe+` sites and the checked-in inventory disagree.

Keeping wires free of hand-written `+unsafe+` lets anyone write one without taking on memory-safety obligations.

[[req-ssr-unsafe-wire-untrusted]]
== No wire can break the element's memory safety

[.specitem,oft-sid="req~ssr-unsafe-wire-untrusted~1",oft-title="No wire can break the element's memory safety",oft-needs="impl,utest",oft-tags="SafetyUpRustCore,SafetyGateUpRust"]
--
The element's memory safety *MUST NOT* depend on a wire's code being right.

Where memory safety depends on a byte count, a length or a claim, the element *MUST NOT* take it from wire code on trust:

* it *MUST* check the writer after encoding and refuse one that was replaced;
* it *MUST* give decoding only a valid mutable reference to an initialized value.
--

[horizontal]
ID:: `+req~ssr-unsafe-wire-untrusted~1+`
ASIL:: B
Allocated to:: the element
Verification:: test (a replaced writer is refused), miri

*Rationale.*
A wire can be written in safe code alone, against a safe interface.
So its code can be wrong without any `+unsafe+`, and the element cannot rely on what it reports.

Encoding goes through a checked writer that keeps the count of the bytes written itself.
So a safe wire cannot claim more initialized bytes than it wrote.

[[req-ssr-unsafe-binding-untrusted]]
== No binding written in safe code can break the element's memory safety

[.specitem,oft-sid="req~ssr-unsafe-binding-untrusted~1",oft-title="No binding written in safe code can break the element's memory safety",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element's memory safety *MUST NOT* depend on a binding's safe methods returning correct values.

* Where it relies on a claim from a binding, the element *MUST* take the claim through an `+unsafe+` trait with stated obligations, listed in the inventory.
* The element *MUST* check, or treat as untrusted, everything else that a binding hands over, such as lengths, slices, route handles and peer references.
--

[horizontal]
ID:: `+req~ssr-unsafe-binding-untrusted~1+`
ASIL:: B
Allocated to:: the element
Verification:: review, miri
* *review*: every value taken from a safe binding method into `+unsafe+` code.
* *miri*: adversarial safe doubles: a frame whose lengths or slices change between calls, a route handle out of range, a reused peer reference.

*Rationale.*
A safe trait's implementation can return any value without breaking Rust's rules.
So `+unsafe+` code cannot rely on it for memory safety, while an `+unsafe trait+` makes its implementer take on stated obligations (source: the Rustonomicon, Rust 1.98.1, chapter How Safe and Unsafe Interact; the Rust Reference, Rust 1.98.1, chapter The unsafe keyword, rule unsafe.trait.intro).

The binding contract therefore keeps its interfaces safe, with their values checked.
It puts each claim that memory safety relies on, such as the exclusivity of lent transmit storage, behind an `+unsafe trait+`.

.Claims made through an unsafe trait
====
The element's memory safety relies on a binding's claim that lent storage is exclusive, disjoint and stable, so the element takes that claim through an `+unsafe+` trait.

up-spec's iceoryx2 chapter asks the same of a Rust payload's author, through iceoryx2's `+ZeroCopySend+` (xref:../../up-l1/iceoryx2.adoc[the iceoryx2 transport]), which iceoryx2 declares as an `+unsafe trait+` (https://github.com/eclipse-iceoryx/iceoryx2/blob/6ef7c55176a8487ae7ca53c2e0649d5df9a1b3b4/iceoryx2-bb/elementary-traits/src/zero_copy_send.rs#L32[`+zero_copy_send.rs+` in iceoryx2 0.9.3, its declaration of the trait]).
====
