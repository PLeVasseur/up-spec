[[req-ssr-build-panic-abort]]
== The ASIL build aborts on panic and checks overflow

[.specitem,oft-sid="req~ssr-build-panic-abort~4",oft-title="The ASIL build aborts on panic and checks overflow",oft-needs="impl,utest,uman",oft-tags="SafetyUpRustCore,SafetyStreamer"]
--
*Profile settings.*
The ASIL release profile *MUST* set `+panic = "abort"+` and `+overflow-checks = true+`.

*The binary refuses an unwinding build.*
A build of the ASIL Streamer binary *MUST* refuse to compile unless `+cfg(panic = "abort")+` holds.
The refusal sits in that binary, which has `+test = false+` and no integration tests in its package, so that no test build compiles it: Cargo builds tests, and every dependency of a test, with unwinding.

*An application's own binary.*
The element *MUST* provide its ASIL build check for an application's own binary.
Placed there, it *MUST* give that binary the check that the ASIL Streamer binary has.

*Every other build still compiles.*
Every other build of the workspace *MUST* still compile, `+cargo build+`, `+cargo clippy --all-targets+` and `+cargo doc+` among them.

*Development builds.*
Cargo cannot set `+panic+` for one package.
So the development profile *MUST* set `+panic = "abort"+` as well, or the binary's package *MUST* be left out of the workspace's default members.
--

[horizontal]
ID:: `+req~ssr-build-panic-abort~4+`
ASIL:: B
Allocated to:: the Streamer binary; the element, for its ASIL build check for an application's own binary
Verification:: gate
* A build of the binary with unwinding fails to compile.
* The release profile's settings.
* `+cargo test+` on the workspace still compiles.
* `+cargo build+`, `+cargo clippy --all-targets+` and `+cargo doc+` on the workspace still compile.
* An application's own binary that carries the element's ASIL build check fails to compile with unwinding, and compiles with `+panic = "abort"+`.

*Rationale.*
With `+panic = "abort"+`, a panic ends the process at once instead of unwinding through code that may hold half-changed state.
Overflow checks turn an arithmetic overflow into that panic instead of a wrong value.

_Why the refusal sits in the binary._
Cargo builds tests with unwinding.
In a library crate, the refusal would stop that crate's tests, and every test that uses the crate, from compiling.

_Why the development profile matters._
Unless the development profile aborts on panic too, or the binary is left out of the default members, a development build of the workspace compiles the binary with unwinding, and fails.
Confirm Cargo's behaviour against the toolchain in use.

_What aborting does not do._
Aborting contains an unexpected defect.
It does not permit a reachable panic, which stays a defect (xref:errors.adoc#req-ssr-refuse-no-panic[No panic on runtime paths]).
It establishes no panic-free cleanup: a route that requires that guarantee is admitted on evidence or refused (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]).

[[req-ssr-build-specified-functions-only]]
== The ASIL build contains only specified functions

[.specitem,oft-sid="req~ssr-build-specified-functions-only~1",oft-title="The ASIL build contains only specified functions",oft-needs="impl,utest",oft-tags="SafetyUpRustCore,SafetyStreamer"]
--
The ASIL build *MUST* contain only specified functions.

Instrumentation, benchmark code and test hooks *MUST* be absent from it, or be specified and shown unable to affect any software safety requirement.
--

[horizontal]
ID:: `+req~ssr-build-specified-functions-only~1+`
ASIL:: B
Allocated to:: the element; the Streamer
Verification:: gate (a symbols check on a final ASIL image, for test and benchmark entry points), review
ISO 26262:: 6-10.4.6 (part-clause numbers only)

*Rationale.*
Code in an image that no requirement specifies is code that no requirement's verification covers, yet it can still run and change state.

Hidden test hooks are the usual case.
An ASIL image would contain them unless they are removed or specified (<<req-ssr-no-test-hooks,The shipped element contains no test hook>>).

[[req-ssr-no-test-hooks]]
== The shipped element contains no test hook

[.specitem,oft-sid="req~ssr-no-test-hooks~1",oft-title="The shipped element contains no test hook",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Every item of the element that exists only for tests *MUST* compile only under the `+up_rust_test_hooks+` configuration, which no shipped build sets.

The async layer's seam is not a test hook; <<req-ssr-async-seam,The asynchronous interface has a written, executor-independent contract>> states it.
--

[horizontal]
ID:: `+req~ssr-no-test-hooks~1+`
ASIL:: B
Allocated to:: the element
Verification:: gate
* The source scan refuses a hidden public function that is neither under the configuration nor one of the seam's names.
* Built without the configuration, a probe naming each test hook fails to resolve.

*Rationale.*
A test hook that changes hidden protocol state must not become an operation available in a shipped build.

[[req-ssr-async-seam]]
== The asynchronous interface has a written, executor-independent contract

[.specitem,oft-sid="req~ssr-async-seam~3",oft-title="The asynchronous interface has a written, executor-independent contract",oft-needs="impl,utest,uman",oft-tags="SafetyUpRustCore"]
--
*A written contract.*
An asynchronous interface to the element's runtime operations, and the seam it uses to learn when a route or a call can make progress, *MUST* have a written contract, stated with the element, that holds whichever scheduler runs it.

For each operation the contract names:

* its submission event;
* its acceptance event and the clock of its deadline;
* the contexts that may call it;
* what it requires of a scheduler.

It *MUST* keep the seven properties below.

*1. Progress.*

* A progress step returns a completion or a pending result.
* It *MUST NOT* wait for a peer, for middleware, in a blocking operating-system call or in an overflow wait, and its work is bounded as xref:bounded-work.adoc#req-ssr-bound-work[Work per call is bounded by setup data] states.
* On a serialized or owned route whose declared heap class admits allocation, a step can wait inside the declared allocation domain only as xref:bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded] states.
Each non-waiting guarantee limits its own operation in a step, and neither limits the other's (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]):
** An acquisition in a step does not wait on a route that requires non-waiting acquisition.
On a route that does not, it can wait as the route's declared policy states.
** A release in a step that could wait leaves the step as pending cleanup on a route that requires non-waiting release.
On a route that does not, it can wait in the step as the route's declared policy states.
* A step that returns pending has arranged a notification of the event it waits for, with no window in which that event can be missed, and it does not poll in a loop or notify itself instead.
* An operation that needs a blocking wait is offered synchronously, not as an asynchronous step.

*2. Concurrent waiters.*

* Every pending operation that the admitted capacity of its route or call table allows keeps its own notification path.
Registering, replacing its own registration, completing or abandoning one operation never removes or overwrites another's.
* Registration storage is part of the admitted capacity (xref:startup-memory.adoc#req-ssr-memory-computable[Startup storage is computable before start]).
* A notification is a hint, never an arrival (xref:qos.adoc#req-ssr-qos-deadline[Deadlines are monitored]), and the operation rechecks its state after every notification.

*3. Abandonment and commit.*

* Abandoning an operation before its submission event leaves nothing submitted.
* Abandoning it afterwards never recalls submitted traffic or undoes anything at a peer.
* Each owner the operation held is returned or released exactly once under its route's rules (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]; xref:heap.adoc#req-ssr-heap-slot-types[Decoded values and their destructors]), or stays charged until that can complete.
* Abandonment follows the rule of a drop: the element's own work in it neither waits nor panics.
On a route that requires non-waiting release, a release that may wait leaves the abandoning step as pending cleanup.
On a route that does not, what the operation owned is released under the route's declared policy on the abandoning path.
* A completion offered after the operation was abandoned, or for an earlier tenure of its slot, completes nothing (xref:../up-l2/interaction.adoc#req-ssr-peer-rpc-correlation[A response reaches only its own call]).

*4. Lifetime.*

* An operation abandoned without its cleanup running, because safe code forgot it, leaves no notification or callback able to reach storage that is no longer valid.
It keeps its capacity charged instead of letting its slot be reused while still owned.
* Dropping an asynchronous handle to an activated role stops no service and releases no runtime resource (xref:release.adoc#req-ssr-release-inert-drop[Dropping a runtime handle does nothing]).

*5. Deadlines.*

* A scheduler's timer only causes another progress step.
It never extends, shortens or replaces an operation's deadline, its clock or its acceptance event (xref:bounded-work.adoc#req-ssr-bound-wait[Every wait is bounded]).
* A result committed at its acceptance event before the deadline stands however late it is observed.
* A completion whose acceptance event falls after the deadline is refused even when a timer or a timeout wrapper reports the operation ready.

*6. Ownership and resources.*

* A native transmit loan is submitted or given back before its operation returns pending, so no pending operation holds one.
* A native receive borrow stays tied to its retained owner while suspended.
* Abandoning an operation revokes no other borrower and never copies or serializes its payload.
* On a native path the contract covers the registration, replacement, notification, abandonment, completion and timer work that an operation causes.
That work keeps xref:heap.adoc#req-ssr-heap-none[No heap in runtime mode] and xref:errors.adoc#req-ssr-refuse-no-panic[No panic on runtime paths] only in a configuration whose package establishes that for its scheduler.
Elsewhere a native asynchronous operation is not offered or is refused at setup by name, and is never replaced by a serialized one.

*7. Service.*

* The element's deadline accounting, expiry and deferred release do not depend on whether an application polls its asynchronous operations.
* Using the asynchronous interface adds no service duty to the application.
* Pending cleanup never runs on, holds or occupies a scheduler context or other execution resource that progress steps, notifications, deadline and expiry accounting or other owners' returns need (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]).
* Where a configuration's scheduler cannot keep pending cleanup off such a resource, an asynchronous composition that needs it is refused at setup by name (xref:release.adoc#req-ssr-release-lease-drop[A lease gives back its slot and nothing else]).
A composition needs pending cleanup where its route requires non-waiting release over a dependency that can wait, or where its binding defers a retained owner's return (xref:../up-l1/bindings.adoc#req-ssr-binding-frame-drop[What a received frame's destructor may do]).
* A release that runs inline is not pending cleanup.
On a route that does not require non-waiting release, a release runs on a path of that route as xref:heap.adoc#req-ssr-heap-slot-types[Decoded values and their destructors] states, such as the step or the abandoning path that ends its value, and can wait there under the route's declared policy.
No composition is refused because that release can wait, or because its configuration has no release service.

*No scheduler or timing bound is required.*
Asynchronous use needs no particular scheduler and no finite timing bound.

*Verification and status of the contract.*
Tests verify the contract against core and against each scheduler that a configuration supports.
From the API freeze, the contract is a documented part of the element's API.
--

[horizontal]
ID:: `+req~ssr-async-seam~3+`
ASIL:: B
Allocated to:: the element's seam; the asynchronous layer that implements the interface
Verification:: test, miri, review
* *test*: the contract's controls against core and under each supported scheduler.
** Readiness before, during and after registration.
** Spurious and coalesced notifications.
** Several waiters on one route and on one call table, with an older waiter abandoned after a newer registration.
** Abandonment before and after submission and during completion.
** A completion offered late or for an earlier tenure.
** A forgotten operation.
** A timer that fires before, at and after the deadline, and a timeout wrapper that reports ready past the deadline.
** A release held pending while progress steps, notifications, expiry and other owners' returns continue.
** On a route that does not require non-waiting release, an abandoned operation's owned value released on the abandoning path under the declared policy.
** On a route that requires only non-waiting acquisition, a step that ends an owned value, with its declared release waiting in the step and the route not refused for it.
** On a route that requires only non-waiting release, a step whose declared acquisition waits, with a release that could wait left as pending cleanup.
** Under a scheduler that cannot isolate pending cleanup, a route that requires non-waiting release over a dependency that can wait refused by name, and the same route without that requirement admitted with its inline release reported.
** Native paths inside heap windows.
* *miri*: the seam's registration storage.
* *review*: the contract against the code, and each scheduler's causal resource behaviour against its package.

*Rationale.*
An asynchronous layer can miss a notification, overwrite another operation's, keep storage alive incorrectly or accept a late result unless registration, progress, abandonment, lifetime and deadline responsibilities are explicit.

_An observable contract._
The item states the observable contract that an executor-independent layer keeps, so any scheduler can drive it.
It names no hidden function and no wake-storage type of one scheduler integration, which would tie the requirement to that integration's shape.
The seam's names, the language's future and wake-up types, and the integrations with particular schedulers belong in the implementation's guidance and evidence.

_Waits in a step and in an abandonment._
The element's own work in a step and in an abandonment is free of waits and panics.
A route's declared allocation domain behaves as its policy states.
Pending cleanup is kept for a route that requires non-waiting release (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]), and for a return that a binding defers, on whatever route.
Requiring it everywhere would need a release service for every owned value an operation could hold.

_Timeouts._
A generic timeout wrapper may report an operation ready after its own deadline has passed.
So the element's acceptance rule, not the wrapper, decides lateness.

_Schedulers and native claims._
A scheduler's wake-up mechanism can allocate, panic or run other code.
So a native resource claim for an asynchronous path rests on the package that supplies the scheduler, never on the interface alone.

_Pending cleanup._
A release that waits on a scheduler's own worker would stop every task that worker drives.
So pending cleanup is kept off the contexts that progress needs.

An inline release is a different case.
A route that does not require non-waiting release has declared that its release can wait, and its report shows it.
That wait delays the step that ends the value, and an item that cannot accept the delay requires the guarantee.

_Separate guarantees._
Non-waiting acquisition and non-waiting release are required separately (xref:heap.adoc#req-ssr-heap-guarantees[A stronger resource guarantee is required by name]).
So a step applies each to its own operation, and a route that requires one is not refused over the other.

[[req-ssr-strict-init-only]]
== Strict mode checks in initialization only

[.specitem,oft-sid="req~ssr-strict-init-only~1",oft-title="Strict mode checks in initialization only",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*When checks run.*
Every strict-mode policy check *MUST* run in initialization mode, before the transition: at a route's build for the rules that concern one route, and at the transition for the rest.

*Cost of checking.*

* Its findings are fixed-size values that can be copied.
* Its reports are written into storage the caller provides.
* Nothing it does allocates, blocks or panics.

*Runtime paths.*
Runtime paths do not execute the strict-policy checker, consult its policy or produce its findings.

*Initialization-selected runtime behaviour.*
Settings fixed during initialization may select runtime behavior explicitly required elsewhere, including the strict ASIL RPC older-incarnation refusal in xref:e2e-wire.adoc#req-ssr-e2e-resync[A restart resynchronizes, stale frames are refused, and no arrival order locks a sender out].
That E2E behavior retains the runtime no-heap and bounded-work requirements.
Initialization-only policy checking does not mean identical E2E receive semantics in every configuration.
--

[horizontal]
ID:: `+req~ssr-strict-init-only~1+`
ASIL:: B
Allocated to:: the element's strict mode
Verification:: test, heap-window, review
* *test*: each rule's finding at setup, with a negative control per rule.
* *heap-window*: setup and the transition in the Enforce state.
* *review*: no runtime path runs the policy checker or reads its policy; initialization-selected E2E behavior is distinguished from policy checking and retains the runtime bounds.

*Rationale.*
Admission findings must be complete before runtime starts, so policy checking cannot add runtime allocation or configuration work.

The admitted configuration can still select a specified E2E receive rule that executes during runtime.
That clause binds only a route with the E2E wire, which is deferred and not part of this delivery.
The initialization-only rule binds every strict-mode check now.

[[req-ssr-strict-lock]]
== The locked build allows only enforcement

[.specitem,oft-sid="req~ssr-strict-lock~2",oft-title="The locked build allows only enforcement",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Only Enforce.*
Under `+--cfg up_rust_strict+`, set only in the integrator's build configuration, strict mode *MUST* have only its Enforce state:

* code that names another state fails to compile;
* deployment data that names one is refused at setup.

Every transport carries a strict-mode policy.

*Refusal outside the declared graph.*
A crate or route that the configuration's declared safety dependency graph does not admit *MUST* be refused under the configuration, at build time where the crate can tell and otherwise at setup, naming the crate or route and its replacement.

*What the refusal follows.*
The refusal follows the actual dependency graph and each route's declared heap class, not a crate's name:

* a wire that uses the heap is refused on a native route and admitted on a serialized route that declares its allocation;
* classic routes stay outside the two-mode contract (xref:runtime-modes.adoc#req-ssr-mode-classic-excluded[Classic routes never enter runtime mode]);
* code that the claimed graph does not contain keeps its ordinary use.
--

[horizontal]
ID:: `+req~ssr-strict-lock~2+`
ASIL:: B
Allocated to:: the element's strict mode
Verification:: gate, test
* *gate*
** A crate that the declared graph does not admit fails to build or set up under the configuration, naming its replacement.
** A probe naming another state fails to compile.
* *test*
** Deployment data naming another state is refused at setup.
** A transport without a policy is refused.
** An allocating wire is refused on a native route and admitted on a serialized route that declares its allocation.

*Rationale.*
An integrator-selected build lock prevents a development setting or convenience dependency from silently restoring an unsupported runtime surface.

Refusing every crate of a kind, such as every allocating wire or the whole `+up-rust+` facade, would refuse configurations the safety case can support.
It would also force ordinary users to migrate only to keep communicating.
Judging the claimed graph and each route's declared class refuses what the claim cannot support and nothing else.

Native guarantees cannot be relaxed by a route label or by a serialized route's permission, and a previously accepted middleware deviation keeps exactly its stated scope.

[[req-ssr-strict-rules]]
== The rules that strict mode checks

[.specitem,oft-sid="req~ssr-strict-rules~1",oft-title="The rules that strict mode checks",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
*Refusals in the Enforce state.*
In its Enforce state, strict mode *MUST* refuse at setup:

* a transport or route at C or D, unless `+above_capability+` names the integrator's measures (xref:assumptions-of-use.adoc#aou-seooc-capability-ceiling[Data above ASIL B relies on measures outside the element]);
* C or D data whose only protection is an end-to-end mechanism of ASIL B capability, unless `+decomposition+` names the argument (xref:assumptions-of-use.adoc#aou-seooc-capability-ceiling[Data above ASIL B relies on measures outside the element]);
* an ASIL route over a transport that the integrator classifies as a black channel, with no protection named (xref:assumptions-of-use.adoc#aou-seooc-e2e-protection[The integrator decides which routes need end-to-end protection]);
* an ASIL RPC route that selects the E2E wire and whose clients are not declared increasing from a counter (xref:assumptions-of-use.adoc#aou-seooc-e2e-protection[The integrator decides which routes need end-to-end protection]);
* an integrator platform that names no contract-test evidence (xref:assumptions-of-use.adoc#aou-seooc-integrator-platform[A custom platform keeps the platform's rules]);
* a setup still alive and not entered when `+enter_runtime_all+` returns (xref:assumptions-of-use.adoc#aou-seooc-build-order[Applications build every transport and role before the last transition]);
* a binding or wire that is not on the integrator's qualified list (xref:../up-l1/deployment.adoc#aou-seooc-qualified-bindings-and-wires[Bindings and wires pass their contracts]).

*Checks on every configuration.*
In the Enforce state, with or without `+--cfg up_rust_strict+`, strict mode *MUST* apply the target, dependency, ownership, known-failure and deviation checks to every configuration (xref:assumptions-of-use.adoc#aou-seooc-target-environment[The target environment is verified]).
Its known-failure and deviation checks are those of <<req-ssr-strict-ack-revision,An acknowledgement names a deviation by ID and revision>>.

*An ASIL process built with unwinding.*
Strict mode *MUST* refuse at setup an ASIL process built with unwinding (xref:assumptions-of-use.adoc#aou-seooc-build-configuration[The ASIL binary is built from its claimed graph, with the ASIL profile]).
--

[horizontal]
ID:: `+req~ssr-strict-rules~1+`
ASIL:: B
Allocated to:: the element's strict mode
Verification:: test
* Each refusal in the Enforce state, with a negative control per rule: the same configuration admitted with `+above_capability+` or `+decomposition+` named, with a protection named, with its clients declared increasing from a counter, with contract-test evidence named, with every setup entered, or with the binding or wire on the qualified list.
* Each of the five checks, in the Enforce state with and without `+--cfg up_rust_strict+`, on a configuration that it refuses and on one that it admits.
* An ASIL process built with unwinding, refused at setup, and neither a QM process built with unwinding nor an ASIL process built with `+panic = "abort"+` refused for it.

*Rationale.*
Each rule checks a declaration or a condition on which an assumption of use rests, so that the Enforce state refuses a configuration that lacks it instead of relying on it.
Meeting the assumption stays the integrator's duty, as the assumption states.

[[req-ssr-strict-ack-revision]]
== An acknowledgement names a deviation by ID and revision

[.specitem,oft-sid="req~ssr-strict-ack-revision~2",oft-title="An acknowledgement names a deviation by ID and revision",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
A strict-mode acknowledgement *MUST* name one deviation by its ID and its revision, never by its type, with a reference, an approver and a date.

When a deviation's revision rises, an acknowledgement of its earlier revision no longer holds.
So its finding refuses again in the Enforce state until it is acknowledged anew.

In the Enforce state, strict mode *MUST* refuse each route that a known failure affects, whatever is acknowledged.
--

[horizontal]
ID:: `+req~ssr-strict-ack-revision~2+`
ASIL:: B
Allocated to:: the element's strict mode
Verification:: test (an acknowledgement of an earlier revision refuses again; one that names an unknown ID is refused; in the Enforce state, each route that a known failure affects refused whatever is acknowledged, and a route that it does not affect not refused for it)

*Rationale.*
Acknowledging an earlier deviation cannot establish acceptance of a later change to its scope or consequences.
A known failure is not an accepted limit, so no acknowledgement admits a route that it affects (xref:../up-l1/deployment.adoc#aou-seooc-qualified-bindings-and-wires[Bindings and wires pass their contracts]).

[[req-ssr-strict-report]]
== Strict mode reports on every run

[.specitem,oft-sid="req~ssr-strict-report~3",oft-title="Strict mode reports on every run",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
Whenever strict mode is in its Report or Enforce state, setup *MUST* produce a compliance report.
The report holds:

* every finding, with its rule, its route, the requirement IDs it serves and its fix;
* the acknowledged deviations;
* for each monitored route, its detection bound with J where a supported configuration establishes J, or a statement that no finite bound is established (xref:qos.adoc#req-ssr-qos-deadline[Deadlines are monitored]), and any servicing or watchdog range that its configuration's representation needs;
* the timing and assurance claims each route requested and was admitted under, with the configuration and the evidence state each rests on;
* for a route or process with no admitted assurance scope, that its assurance is Draft and unassessed, which refuses nothing;
* the assumptions of use that apply to the features configured;
* each cited item's revision and status, so that a run before the requirements are signed off says that its rules rest on draft items.

*Routes.*
The report also holds:

* for each route, its TTL, against the reaction budget the integrator declares for it (xref:assumptions-of-use.adoc#aou-seooc-timing-budgets[Timing claims rest on a supported configuration, and the item's budgets are the integrator's]);
* the end-to-end protection named for each route (xref:assumptions-of-use.adoc#aou-seooc-e2e-protection[The integrator decides which routes need end-to-end protection]);
* for each E2E route, its senders, data IDs, `+resync_frames+`, start declarations with their duty, and thread duties (xref:assumptions-of-use.adoc#aou-seooc-e2e-protection[The integrator decides which routes need end-to-end protection]);
* for each route, the counters the application reads and what each means, the E2E figures included (xref:assumptions-of-use.adoc#aou-seooc-application-reacts[The application reacts to what the element reports]);
* every route's capacities (xref:assumptions-of-use.adoc#aou-seooc-capacity-sizing[Capacities are sized for the worst case]);
* each route's declared peers and the shared-memory permissions its binding requests (xref:../up-l1/deployment.adoc#aou-seooc-peer-access[Only authorized processes reach the transport]);
* each shared route, with what one faulty peer can starve there (xref:assumptions-of-use.adoc#aou-seooc-peer-rates[Peer rates on shared routes are the integrator's]);
* which ASIL routes an operator can disable (xref:../up-l2/streamer.adoc#aou-seooc-operator-access[Only authorized operators reach the Streamer's operator interface]);
* every route that a Streamer monitor trips and that only a Streamer restart clears (xref:../up-l2/streamer.adoc#aou-seooc-monitor-thresholds[Monitor thresholds allow for peers' restarts]).

*The deployment.*
The report also holds:

* the transports that share each process (xref:assumptions-of-use.adoc#aou-seooc-process-isolation[Processes or partitions are isolated]);
* the restart path that the integrator declares, a supervisor or, on an MCU, a partition restart (xref:assumptions-of-use.adoc#aou-seooc-supervisor-restart[A supervisor outside the process restarts it]);
* the time-sync source, where one is declared (xref:assumptions-of-use.adoc#aou-seooc-clock[The platform provides the clocks]);
* the startup memory that each setup computes (xref:assumptions-of-use.adoc#aou-seooc-capacity-sizing[Capacities are sized for the worst case]);
* what was declared in the deployment data, and what was checked (xref:assumptions-of-use.adoc#aou-seooc-deployment-data[Deployment data is in range, verified and protected]);
* each binding's limits, deviations and known failures, as its qualification record states them (xref:../up-l1/bindings.adoc#req-ssr-binding-readme[A binding's qualification record states its limits and its failures, and its README points at it]; xref:../up-l1/deployment.adoc#aou-seooc-qualified-bindings-and-wires[Bindings and wires pass their contracts]).

*Duties.*
The report also holds:

* both duties for data above ASIL B, the integrator's measures and the argument for a decomposition (xref:assumptions-of-use.adoc#aou-seooc-capability-ceiling[Data above ASIL B relies on measures outside the element]);
* the coherence duty on multi-core parts, and the stack-sizing duty (xref:assumptions-of-use.adoc#aou-seooc-target-environment[The target environment is verified]);
* overflow checks, as a checklist item (xref:assumptions-of-use.adoc#aou-seooc-build-configuration[The ASIL binary is built from its claimed graph, with the ASIL profile]);
* for an integrator platform, the entropy duty and the platform contract test (xref:assumptions-of-use.adoc#aou-seooc-integrator-platform[A custom platform keeps the platform's rules]).

*Warnings.*
The report also holds:

* a warning of every QM transport in an ASIL process, with the coexistence duty that follows (xref:assumptions-of-use.adoc#aou-seooc-process-isolation[Processes or partitions are isolated]);
* where no restart path is declared, a warning that none is declared (xref:assumptions-of-use.adoc#aou-seooc-supervisor-restart[A supervisor outside the process restarts it]);
* a warning when the wall clock at setup reads earlier than the element's release date, a sign that it is not yet synchronised (xref:assumptions-of-use.adoc#aou-seooc-clock[The platform provides the clocks]);
* a warning of each transport that the integrator has not classified, as a black channel or not (xref:assumptions-of-use.adoc#aou-seooc-e2e-protection[The integrator decides which routes need end-to-end protection]);
* a warning of each ASIL route with several declared senders and no declared per-peer rate (xref:assumptions-of-use.adoc#aou-seooc-peer-rates[Peer rates on shared routes are the integrator's]);
* a warning of each ASIL receive route that admits undeclared peers (xref:../up-l1/deployment.adoc#aou-seooc-peer-access[Only authorized processes reach the transport]).

In the Enforce state every finding is still reported, so one run shows everything to fix.

The report *MUST* say that passing its checks is neither a safety qualification nor an assessment.

* *test*
** A run's report with findings of every severity.
** The cited-items line before and after sign-off.
** A monitored route with and without an established J.
** A route's requested and admitted claims.
** An ASIL-labelled configuration with no assurance package, reported Draft and unassessed and not refused.
** Each entry of the lists on routes, on the deployment and on duties, on a configuration that has what it lists, and an entry with a condition, such as a declared time-sync source or an integrator platform, with and without that condition.
** Each warning, on a configuration that draws it and on one that does not.
* *review*: the report's fields against this item.

*Rationale.*
A compliance report makes declarations, deviations and outstanding duties inspectable.
A Draft citation must remain distinguishable from a signed-off requirement.

A check can only show that its observable predicates held.
So the report keeps claims, the evidence they rest on and the checks that passed apart (xref:README.adoc#claims[the SEooC's claims]).
