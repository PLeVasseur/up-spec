[[req-ssr-crate-isolated]]
== The safety crate cannot be tainted

[.specitem,oft-sid="req~ssr-crate-isolated~1",oft-title="The safety crate cannot be tainted",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The crate that holds the element's runtime path *MUST* be `+no_std+`, use no `+alloc+`, have no dependencies and declare no Cargo features.
So no other crate in a build can switch `+std+` or `+alloc+` on inside it.

Tokio, Protobuf and anything else that needs `+std+` *MUST* live in other crates.
--

[horizontal]
ID:: `+req~ssr-crate-isolated~1+`
ASIL:: B
Allocated to:: the element
Verification:: gate (the manifest has no `+[features]+` and no `+[dependencies]+`; the crate builds on a sysroot with neither `+alloc+` nor `+std+`)

*Rationale.*
Cargo turns a crate's feature on for the whole build once any crate asks for it (source: the Cargo Book, Rust 1.98.1, chapter Features, section Feature unification).
So only a crate with neither features nor dependencies keeps `+std+` off inside it, whatever other crates ask for.

With no `+alloc+`, the crate's URIs keep their authority inline, so this crate does not allocate a separate heap-owned authority representation.
That representation does not determine where a caller stores an enclosing object.

[[req-ssr-crate-sync-path]]
== Traffic is synchronous or polled

[.specitem,oft-sid="req~ssr-crate-sync-path~1",oft-title="Traffic is synchronous or polled",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The runtime path *MUST* offer every traffic operation in synchronous or polled form, and *MUST* use none of `+core::future+`, `+core::task+` or `+core::pin+`.

Any async layer *MUST* sit above it, in a separate crate.
--

[horizontal]
ID:: `+req~ssr-crate-sync-path~1+`
ASIL:: B
Allocated to:: the element; each asynchronous layer, for its place above the runtime path, in a separate crate
Verification:: gate (a token scan for `+async+`, `+.await+`, `+Future+`, `+Pin+`, `+Poll+`, `+Waker+` and `+Context+`, and for grouped `+use core::{…}+` paths, with a negative control for each)

*Rationale.*
Offering traffic in synchronous or polled form, with no futures, tasks or pinning, keeps it independent of any executor and of library modules that a given qualification scope may not cover.

Which compiler releases, targets, library modules and options a qualification covers is stated by its supplier for an exact release (for example https://ferrous-systems.com/blog/ferrocene-26-05-0/[the Ferrocene 26.05.0 release notes]).
Neither the availability of a language feature nor a successful build is a qualification of the compiler or the library.

[[req-ssr-crate-core-only-binary]]
== The checked policy stays in the safety crate, and no admitted optional layer bypasses or reimplements it

[.specitem,oft-sid="req~ssr-crate-core-only-binary~3",oft-title="The checked policy stays in the safety crate, and no admitted optional layer bypasses or reimplements it",oft-needs="impl,utest",oft-tags="SafetyUpRustCore"]
--
The element *MUST* keep its checked policy in the safety crate and usable without any optional allocation, host, application, scheduler or memory-provider layer.

An optional layer that a configuration admits *MUST NOT* bypass or reimplement that policy.
--

[horizontal]
ID:: `+req~ssr-crate-core-only-binary~3+`
ASIL:: B
Allocated to:: the element; each optional layer that a configuration admits, for not bypassing or reimplementing the checked policy
Verification:: test, review
* *test*: a link fixture that uses only the safety crate, a binding and a wire.
* *review*: each check of the element's checked policy, which stands in the safety crate; each optional layer that a configuration admits, which neither bypasses those checks nor reimplements them.

*Rationale.*
The safety crate's own build, and so the checked policy in it, cannot be changed by another crate's features (<<req-ssr-crate-isolated,The safety crate cannot be tainted>>).
Usable without any optional layer, the policy applies in full to a configuration that admits none.

_Optional layers._
With the checked policy in the safety crate, a claimed configuration can admit an independently specified optional layer, such as an allocation-aware or asynchronous layer, for functions outside that policy.
A layer that bypassed the policy would let a configuration run without its checks, and a layer that reimplemented it would run checks that the element's requirements and evidence do not cover.
A layer that no configuration admits stays out of every claimed graph (xref:assumptions-of-use.adoc#aou-seooc-build-configuration[The ASIL binary is built from its claimed graph, with the ASIL profile]; xref:build.adoc#req-ssr-strict-lock[The locked build allows only enforcement]).
An admitted optional layer carries its own allocated requirements and evidence.

No configuration admits an optional layer at this revision.
So every current claimed graph is the safety crate with qualified bindings, wires and platform backends.

[[req-ssr-crate-streamer-isolated]]
== The ASIL Streamer is its own untaintable crate

[.specitem,oft-sid="req~ssr-crate-streamer-isolated~3",oft-title="The ASIL Streamer is its own untaintable crate",oft-needs="impl,utest",oft-tags="SafetyStreamer"]
--
The ASIL Streamer's route table, admission, validation and forwarding loop *MUST* live in their own crate:

* `+no_std+`;
* no `+alloc+`;
* no Cargo features;
* no dependency other than `+up-rust-core+`;
* no 64-bit atomic type.

No feature, dependency or build setting outside it can bring classic routes, `+std+`-only paths or heap use into it.

The `+std+` loader *MUST* only parse deployment data, and validation happens in this crate.

Bindings and wires are linked by the binary that uses the crate, not by the crate.
--

[horizontal]
ID:: `+req~ssr-crate-streamer-isolated~3+`
ASIL:: B
Allocated to:: the Streamer
Verification:: gate (the same gates as `+up-rust-core+`: manifest, restricted sysroot, and its own panic-link fixture; a build for a bare-metal 32-bit target without 64-bit atomics), review (the `+std+` loader, which only parses deployment data, with all validation of it in this crate)

*Rationale.*
Separating the data plane keeps a convenience dependency, or a feature that another crate turns on for the whole build, from bringing heap use into it (source: the Cargo Book, Rust 1.98.1, chapter Features, section Feature unification).
